# P1：生产级业务系统

## 项目定位

实现一个预约与订单系统，训练缓存、消息、幂等、并发一致性、可观测性、压测和故障恢复。项目应先采用模块化单体，只有在出现明确边界和收益时再拆分服务。

项目仓库、业务模块、应用入口、契约、迁移、部署、测试和运维目录按 [企业级后端项目工程结构](企业级项目工程结构.md) 组织，并根据所选语言裁剪，禁止为了“看起来专业”创建没有职责的空目录。

系统中的支付使用可控的模拟服务，禁止接入真实资金流程。

## 用户故事

- 用户可以查询可预约的资源或库存。
- 用户可以通过幂等请求创建订单并占用资源。
- 超时未确认的订单会自动释放资源。
- 模拟支付成功后订单进入已确认状态。
- 状态变化会异步触发通知，失败可以重试和追踪。
- 运营人员可以查询任务、消息和订单异常状态。

## 核心模块

- 用户与权限。
- 资源/商品、库存与缓存。
- 订单、状态机和幂等键。
- 模拟支付回调与回调验签。
- 事务事件、消息队列、重试和死信处理。
- 通知、审计和后台查询。

## 必做能力

### 正确性

- 数据库约束、事务边界和明确的订单状态机。
- 并发扣减不超卖，重复请求和重复消息不产生重复副作用。
- 数据库提交与事件发送之间使用 Outbox 或等价可靠方案。
- 缓存策略包含一致性窗口、失效补偿和热点保护。

### 可靠性

- 连接、请求和任务超时，带预算的有限重试。
- 限流、熔断、降级、并发隔离和优雅停机。
- 消息积压、死信、重放和人工修复路径。
- 数据备份、迁移、回滚和一致性校验脚本。

### 可观测性与交付

- 结构化日志、业务指标、RED/USE 指标和 Trace。
- 仪表盘、告警规则、Runbook 和服务目标。
- 自动化测试、构建、镜像和部署流程。
- 压测方案包含负载模型、环境、数据、结果和瓶颈。

## 推荐里程碑

1. 完成需求、容量估算、架构图、状态机和数据模型。
2. 实现订单、库存和模拟支付的事务流程。
3. 加入幂等、Outbox、消息消费和任务恢复。
4. 加入缓存、限流、超时、重试和降级。
5. 建立日志、指标、Trace、仪表盘和告警。
6. 完成压测、故障注入、恢复演练和事故复盘。
7. 完成部署、回滚、ADR 和项目面试材料。

## 必须演练的故障

- 客户端超时后重试创建订单。
- 数据库提交成功但事件暂未发送。
- 消息重复、乱序、积压和死信。
- Redis 不可用或热点 Key 失效。
- 数据库连接池耗尽、慢 SQL 和依赖延迟。
- 发布新版本后错误率或 P99 上升。

每次演练记录发现、影响、止损、恢复、数据修复和防复发，不只记录“重启后恢复”。

## 验收门槛

- [ ] 并发测试证明不会超卖，说明测试环境和并发模型。
- [ ] 重复 API、回调和消息不会产生重复副作用。
- [ ] 仪表盘能区分流量、错误、延迟和资源饱和问题。
- [ ] 至少完成三种故障注入并形成一份事故复盘。
- [ ] 压测报告包含 P50/P95/P99、吞吐、错误和资源数据。
- [ ] 完成发布、迁移和回滚演练。
- [ ] 至少记录两个重要 ADR 和三个已知限制。
- [ ] 其他人可以根据文档复现核心流程和测试。

## 面试证据

完成后整理一分钟概述、十分钟深挖、架构图、容量估算、状态机、压测报告、事故复盘和关键 ADR。
