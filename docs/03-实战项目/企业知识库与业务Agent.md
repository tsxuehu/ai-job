# 带权限控制的企业知识库与业务 Agent

> 项目等级：P2；建议先完成 P0 和 P1。该项目用于证明 AI 应用后端能力，不是只封装一个聊天接口。

## 1. 项目目标

用户可以上传或同步企业文档，在权限范围内检索并获得带引用的答案；Agent 可以调用受控业务工具，高风险动作需要人工审批，所有操作可追踪和审计。

## 2. 核心模块

### 传统后端

- 用户、组织、租户、角色和权限。
- 文档上传、对象存储、异步解析和任务状态。
- PostgreSQL/MySQL、Redis 和消息队列。
- API 鉴权、限流、幂等、重试和审计。
- Docker、CI/CD、日志、指标和 Trace。

### RAG

- 文档解析、清洗、Chunk、元数据和 embedding。
- 关键词 + 向量混合检索及 rerank。
- 检索前可信权限过滤、来源引用和拒答。
- 增量更新、删除、重建和索引版本。

### Agent

- 结构化工具调用和服务端参数校验。
- 工具最小权限、状态、超时、幂等和补偿。
- 高风险操作审批、沙箱、步骤/token 预算。
- 可恢复任务、执行轨迹和审计记录。

## 3. 推荐迭代顺序

1. 单体 API、用户与文档 CRUD。
2. 异步解析、对象存储和任务重试。
3. 基础检索、引用和小型评测集。
4. 混合检索、重排、权限与增量索引。
5. 一个只读工具和一个需审批的写工具。
6. 限流、超时、降级、观测与成本记录。
7. 压测、故障演练、回归评测和部署。

## 4. 必须演练的故障

- 文档解析失败或消息重复消费。
- 数据库提交成功但异步事件发送失败。
- 模型超时、限流、输出格式错误或供应商不可用。
- 向量索引更新滞后或权限元数据错误。
- Agent 重复调用、无限循环或越权请求。
- 单一租户突发流量拖慢系统。

每个故障都应记录：发现方式、影响范围、止损、恢复、数据修复和防复发措施。

## 5. 最小产品边界

第一版只支持一个明确文档来源、有限文件类型和两个受控业务工具：

- 一个只读工具，例如查询工单或订单状态。
- 一个需要人工审批的写工具，例如创建工单或提交退款申请。

第一版暂不追求多 Agent、自主规划、复杂记忆和大量模型供应商。先保证权限、引用、评测、审计和失败恢复正确。

## 6. 统一交付物

- 需求边界、威胁模型、架构图、数据流和权限模型。
- 可复现的文档、查询、身份和安全评测数据集。
- 索引构建、增量更新、删除和版本回滚流程。
- RAG 检索、回答、拒答、引用和权限分组报告。
- Agent 工具契约、审批记录、执行轨迹和审计查询。
- 模型、Prompt、知识库和评测集的版本记录。
- 质量、首 token 延迟、总延迟、安全与单位成功任务成本仪表盘。
- 至少两个 ADR、一份故障复盘和完整演示脚本。

## 7. 验收门槛

- [ ] 不同租户和角色的文档权限在检索前生效，并有越权测试。
- [ ] 每个答案提供可验证引用；无答案场景可以按门槛拒答。
- [ ] 数据集版本固定，可以对同一变更重复运行评测。
- [ ] 报告区分检索失败、上下文使用失败和生成错误。
- [ ] 工具参数在服务端校验，写操作需要审批且具备幂等保护。
- [ ] Agent 有步骤、时间和 token 预算，可以取消、恢复和审计。
- [ ] 模型超时、限流、格式错误和供应商不可用时有明确降级。
- [ ] 同时报告质量、P50/P95/P99、成本和安全测试结果。
- [ ] 新环境可以根据 README 启动核心依赖并运行回归评测。
- [ ] 能说明至少三个已知限制，以及为什么没有采用更复杂方案。

## 8. 面试证据

准备一分钟产品概述、十分钟架构深挖，并能回答：

- 为什么选择 RAG，而不是长上下文或微调？
- 权限过滤发生在哪一层，如何证明不会越权？
- 如何区分检索问题、模型问题和工具执行问题？
- 如何设置上线门槛，以及质量、延迟和成本如何取舍？
- Agent 重复执行、高风险操作和执行中断分别如何处理？

指标定义和报告格式参见 [项目指标与评测](项目指标与评测.md)，表达结构参见 [项目面试讲解模板](项目面试讲解模板.md)。
