# 企业级后端项目工程结构

企业级工程结构不是“目录越多越专业”，而是让多人长期协作时仍能回答：代码属于哪个业务边界、谁可以依赖谁、配置和数据如何演进、怎样测试发布、故障时去哪里排查。

本文给出一套语言无关的组织原则，以及 C++、Rust、Go、Java、Node.js/TypeScript、Python 的落地目录。配套的语言边界原理参见 [六门语言的模块化设计对比](../01-技能学习/01-编程语言/comparisons/modularity.md)。

## 1. 先选架构形态，不先选目录

| 形态 | 适用阶段 | 优点 | 主要成本 |
| --- | --- | --- | --- |
| 单体应用 | 需求较小、团队很小、边界未稳定 | 开发和部署简单 | 容易逐渐失去内部边界 |
| 模块化单体 | 多数企业项目的推荐起点 | 保留本地事务和简单部署，同时训练边界 | 需要架构规则防止跨模块调用 |
| 多进程/少量服务 | 部分任务需要独立扩缩容或隔离 | 可按负载拆 API、Worker、调度器 | 增加进程通信、部署和观测 |
| 微服务 | 业务边界、数据所有权和团队边界已稳定 | 独立部署、扩缩容和故障隔离 | 网络、数据一致性、平台与组织成本高 |

个人项目和新业务默认选择模块化单体。可以包含 API、Worker 等多个进程入口，但共享清晰的领域与应用模块。只有在独立部署、容量、权限、故障隔离或团队自治收益明确时才拆服务。

## 2. Monorepo 还是多仓库

| 问题 | Monorepo | 多仓库 |
| --- | --- | --- |
| 跨模块修改 | 一次变更和一次 CI 容易保持原子性 | 需要版本、发布顺序和兼容策略 |
| 依赖可见性 | 容易统一，也容易无边界引用 | 物理隔离更强，但共享代码治理复杂 |
| 工具和规范 | 容易统一 | 每仓库可能漂移 |
| CI 规模 | 需要按影响范围增量执行 | 单仓库较小，但跨仓联调复杂 |
| 权限与自治 | 需要目录所有权和规则 | 仓库天然形成权限边界 |

学习项目、单团队产品和模块化单体优先 Monorepo。多仓库适合已经具有独立产品生命周期、权限、发布节奏和负责团队的服务。不要只因为目录多就把每个模块拆仓库。

## 3. 推荐的企业级仓库骨架

```text
repository/
├── apps/                    # 可运行应用：API、Worker、Scheduler、CLI
│   ├── api/
│   └── worker/
├── modules/                 # 业务模块/限界上下文
│   ├── order/
│   ├── inventory/
│   └── notification/
├── platform/                # 少量稳定的跨业务技术能力
│   ├── observability/
│   ├── database/
│   └── messaging/
├── contracts/               # OpenAPI、事件、RPC 等跨边界契约
│   ├── http/
│   ├── events/
│   └── rpc/
├── migrations/              # 数据库/消息 schema 迁移
├── tests/                   # 跨模块集成、契约、E2E、性能测试
│   ├── integration/
│   ├── contract/
│   ├── e2e/
│   └── performance/
├── deploy/                  # 容器、编排、发布和环境清单
│   ├── local/
│   ├── qa/
│   └── production/
├── ops/                     # 仪表盘、告警、Runbook、演练脚本
├── docs/                    # 架构图、ADR、API 约定、开发说明
│   ├── architecture/
│   ├── adr/
│   └── runbooks/
├── tools/                   # 构建、代码生成、校验和本地开发工具
├── scripts/                 # 少量明确入口脚本，不作为业务代码目录
├── .ci/                     # CI/CD 定义；也可用平台约定目录
├── README.md
└── 语言构建与依赖文件
```

这是一张责任地图，不要求机械创建所有空目录。只有出现真实内容时才创建；小项目可以把 `platform`、`contracts`、`ops` 保持为少量文件。

## 4. 顶层目录的职责

### apps：进程入口，不放核心业务

`apps/api`、`apps/worker` 等只负责：

- 读取和校验配置。
- 创建数据库、消息、HTTP client 等资源。
- 将具体 adapter 注入 application。
- 注册路由、消费者和后台任务。
- 启动健康检查、观测和优雅停机。

入口是 composition root，可以知道所有具体实现；业务规则不能散落在 main、controller 和消息回调中。

### modules：按业务能力组织

业务模块围绕订单、库存、用户、通知等能力，而不是全局 controller/service/model 技术层。每个模块拥有自己的规则、用例、端口和数据转换。

```text
modules/order/
├── domain/                  # 实体、值对象、状态机、领域错误
├── application/             # 用例、命令/查询、端口、事务编排
├── adapters/
│   ├── inbound/             # HTTP、消息、CLI 等入口适配
│   └── outbound/            # 数据库、缓存、外部服务实现
├── public/                  # 对其他模块开放的最小 API/事件
└── tests/
```

不必为每个模块强制创建五层目录。模块较小时可以使用文件表达同样边界；关键是依赖方向和公共 API，而不是层数。

### platform：只放稳定的跨业务能力

适合放日志/Trace 适配、数据库连接工厂、消息基础设施、时钟、ID 生成等。不能放订单工具、用户 DTO 或任何“不知道放哪里”的代码。

创建 platform/common 前回答：它是否真正服务多个业务？语义是否稳定？是否会迫使所有模块依赖同一个庞大包？

### contracts：管理跨边界兼容

- HTTP OpenAPI/JSON Schema。
- 事件名称、版本和 payload schema。
- RPC IDL、生成代码输入与兼容检查。
- 错误码、分页和幂等等公共协议约定。

生成代码与手写业务代码分开；生成命令、工具版本和产物策略必须可复现。契约变化进入兼容测试和发布说明。

### migrations：数据结构是发布的一部分

- 迁移脚本只追加或按团队规则演进，不能修改已在共享环境执行的历史。
- 使用 expand → migrate/backfill → contract 方式处理不兼容变更。
- 迁移、回滚/前滚、校验与耗时估算进入发布流程。
- 数据修复脚本需要审计、幂等、限速和 dry-run，不混进普通 migration。

### deploy 与 ops：部署和运行同样属于项目

`deploy` 保存容器构建、环境模板和发布资源；`ops` 保存仪表盘、告警、SLO、Runbook 和故障演练。二者都引用构建版本，不能复制一套脱离源码的配置长期漂移。

密钥不提交仓库。仓库保存配置 schema、非敏感默认值、环境变量说明和本地示例；真实密钥来自部署平台的密钥管理能力。

## 5. 服务内部的依赖规则

```text
inbound adapter ──> application ──> domain
                         ▲
                         │ implements port
outbound adapter ────────┘

apps/bootstrap 负责把具体对象组装起来
```

允许：

- application 使用 domain 类型与规则。
- inbound adapter 把协议 DTO 转为 application command。
- outbound adapter 实现 application/domain 定义的端口。
- bootstrap 同时依赖端口和具体实现完成组装。

禁止：

- domain 导入 Web 框架、ORM、消息 SDK 或具体数据库。
- application 直接创建具体 client 或读取全局配置。
- 业务模块导入另一个模块的 persistence/entity/internal 文件。
- adapter 之间互相调用并绕过 application。
- 使用全局 Service Locator 隐藏真实依赖。

## 6. 模块之间如何协作

| 情况 | 推荐方式 |
| --- | --- |
| 同一事务内必须保持强一致 | 通过一个 application 用例协调，边界仍保持清晰 |
| 只需查询少量稳定能力 | 调用对方 public application API |
| 一个事实触发多个后续动作 | 发布领域/集成事件，由其他模块订阅 |
| 跨进程或跨服务 | 使用有版本的 HTTP/RPC/事件契约 |
| 需要批量分析数据 | 通过只读模型、数据管道或明确查询端口 |

不能让模块直接读写另一个模块的表。即使部署在同一个数据库，也应明确表的数据所有者，并通过公共用例或事件协作。

## 7. 配置组织

建议分为四层：

1. 代码中的安全默认值。
2. 可版本化的环境模板。
3. 部署环境注入的非敏感配置。
4. 密钥管理系统提供的敏感配置。

应用启动时一次性加载为强类型配置并完整校验，失败立即退出。业务代码通过构造参数获得所需配置片段，不在各处直接读取环境变量。

配置必须包含单位和范围，例如 `request_timeout: Duration`，不能使用含义不明的裸数字。动态配置要定义刷新、失败、审计和回滚语义。

## 8. 测试目录不是源码目录镜像

| 测试 | 放置位置 | 主要目标 |
| --- | --- | --- |
| 单元测试 | 模块附近 | 领域规则、值对象、状态机、纯函数 |
| 组件测试 | 模块 tests | application + 内存/受控 adapter |
| adapter 集成测试 | adapter 或 tests/integration | SQL、协议、序列化、消息行为 |
| 契约测试 | tests/contract | API、事件和调用方兼容 |
| E2E | tests/e2e | 关键用户流程，不追求覆盖所有分支 |
| 并发/故障 | tests/integration 或专项目录 | 幂等、竞争、超时、重试、恢复 |
| 性能 | tests/performance | 固定负载下的容量与回归基线 |

测试夹具、数据工厂和容器启动能力放在 testing 支撑模块，但不要让生产业务依赖测试模块。

## 9. 文档和治理文件

企业项目至少应有：

- 根 README：定位、架构、启动、测试、部署入口。
- 每个业务模块 README：职责、公共 API、数据所有权、依赖与限制。
- ADR：记录重要决策、替代方案和后果。
- Runbook：告警判断、止损、恢复和升级路径。
- API/事件文档：版本、兼容和示例。
- OWNERS/CODEOWNERS：模块负责人和评审责任。
- 变更日志或发布说明：用户可见变化、迁移与回滚要求。

文档应链接自动化入口，不能复制容易过期的命令和配置。关键架构规则尽量由 lint、依赖检查或架构测试执行。

## 10. CI/CD 按风险分层

```text
格式/静态检查
    → 单元测试
    → 组件与契约测试
    → 构建不可变产物 + SBOM/依赖信息
    → 集成/迁移/安全检查
    → 部署 QA + 冒烟
    → 渐进发布 + 指标判断
    → 完成或回滚
```

- 同一个 commit 只构建一次，环境间提升同一不可变产物。
- 根据依赖图执行受影响模块测试，但主干仍定期执行完整验证。
- 数据库迁移与应用兼容窗口进入发布编排。
- 发布门禁依赖真实错误率、P95/P99、饱和度和业务指标。
- 生产回滚不能假设数据库 schema 可以瞬间回退。

## 12. 从一个项目演进到企业结构

### 阶段 A：单进程模块化单体

- 一个仓库、一个数据库、一个部署单元。
- 业务按模块划分，数据库表明确所有者。
- 建立测试、迁移、观测、ADR 和发布基线。

### 阶段 B：多个进程入口

- API、Worker、Scheduler 根据负载与生命周期拆进程。
- 复用 domain/application，不复制业务代码。
- 加入消息、任务幂等、失败恢复和独立容量。

### 阶段 C：独立构建模块

- 通过语言构建系统强化依赖边界。
- 按影响范围执行 CI，公共契约版本化。
- 团队责任和模块 README 稳定。

### 阶段 D：按明确收益拆服务

- 业务和数据所有权稳定。
- 服务拥有独立数据库或明确的数据治理方案。
- 建立 RPC/事件兼容、超时、重试、幂等、Trace 和发布平台。
- 拆分前后都有容量、故障和团队收益证据。

## 13. 常见错误结构

### 全局技术分层

```text
controllers/
services/
repositories/
models/
```

业务规模变大后，一个需求需要横跨所有目录，模块边界和负责人不清。应改为按业务能力分组，模块内部再按需要分层。

### common/utils 大包

任何代码都可以依赖，最终成为无语义耦合中心。代码应回到拥有该语义的模块；真正通用能力形成小而稳定的 platform 模块。

### 过早多模块或微服务

大量空层、转发接口、版本和网络调用，却没有独立演进需求。先保持一个构建/部署单元内的清晰边界，再用数据证明拆分收益。

### 框架对象穿透全系统

ORM entity、HTTP Request、框架 Context 和 SDK Model 进入 domain，导致核心无法独立测试和替换。边界 adapter 负责转换。

### 隐藏依赖

全局单例、Service Locator、import/init 副作用和静态注册让构造关系不可见。依赖应通过构造参数或明确工厂组装。

## 14. 企业项目验收清单

### 结构

- [ ] 顶层目录都能用一句话说明责任，没有空架构和大杂烩目录。
- [ ] 业务按能力组织，公共 API 小于内部实现。
- [ ] 依赖图有向无环，核心不依赖框架和具体基础设施。
- [ ] API DTO、领域模型、持久化记录和事件 schema 边界清楚。

### 工程

- [ ] 新环境可一条文档路径完成安装、迁移、启动和测试。
- [ ] 配置有 schema、单位、范围和启动校验，密钥不进入仓库。
- [ ] 迁移、契约、生成代码和依赖版本可复现。
- [ ] 单元、集成、契约、E2E 和性能测试职责清楚。

### 生产

- [ ] API、Worker、连接池、队列和缓存有容量与关闭策略。
- [ ] 日志、指标、Trace、仪表盘、告警和 Runbook 可以定位故障。
- [ ] CI 构建不可变产物，支持渐进发布、迁移和回滚/前滚。
- [ ] 关键模块有负责人、ADR、已知限制和故障复盘。

## 15. 面试时如何讲工程结构

不要只说“使用 DDD/整洁架构”。按以下顺序说明：

1. 项目有哪些业务模块，为什么这样划分？
2. 一个请求从入口到 domain、数据库经过哪些边界？
3. 接口定义在哪里，具体实现怎样注入？
4. 数据库表、事件和 API 契约由谁拥有？
5. 如何阻止循环依赖和跨模块内部调用？
6. 为什么选择模块化单体，而不是微服务？
7. 测试、迁移、发布和故障定位如何配合这个结构？
8. 随着团队和流量增长，下一步会拆什么，证据是什么？

能结合真实目录、依赖图、测试和一次演进决策回答，才说明真正理解企业级工程结构。
