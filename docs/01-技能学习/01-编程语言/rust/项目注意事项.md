# Rust：项目特性与注意事项

这篇不是第十三个公共分类，而是 Rust 项目中特别容易被误解的所有权、异步和共享状态规则。Rust 的编译器能证明内存级安全，却不会自动设计正确的任务生命周期、锁范围、背压和业务一致性。

## async 不等于必须使用 Arc

`Arc<T>` 表示“多个所有者可以跨线程共同拥有 T”，不是 async 关键字的附属语法。

通常需要 `Arc` 的情况：

- 多个 `tokio::spawn` 任务需要共同拥有一份配置、客户端或服务状态。
- spawn 的 Future 需要满足 `Send + 'static`，不能借用当前栈帧中的局部数据。
- 数据需要比创建任务的当前函数活得更久。

通常不需要 `Arc` 的情况：

- Future 只在当前作用域内 await，没有被独立 spawn。
- 使用 `join!` 等在当前 Future 内并发轮询，借用关系仍能被编译器证明。
- 可以把数据所有权直接 move 给唯一任务。

```rust
// 当前作用域内并发，可以借用 client
let (left, right) = tokio::join!(
    fetch(&client, left_id),
    fetch(&client, right_id),
);
```

## Arc、锁和可变状态

| 形式 | 表达什么 | 不表达什么 |
| --- | --- | --- |
| `Arc<T>` | 跨任务/线程共享所有权 | 不自动允许修改，也不保证 T 本身线程安全 |
| `Arc<Mutex<T>>` | 共享所有权 + 互斥修改 | 不保证锁范围合理，不防业务死锁 |
| `Arc<RwLock<T>>` | 多读单写 | 读多不代表一定更快，仍可能写饥饿/竞争 |
| channel | 消息和所有权转移 | 不自动提供容量、关闭和失败协议 |

```rust
let state = Arc::new(tokio::sync::RwLock::new(State::default()));
let worker_state = Arc::clone(&state);

tokio::spawn(async move {
    let snapshot = {
        let guard = worker_state.read().await;
        guard.snapshot()
    }; // 先释放 guard

    send_snapshot(snapshot).await
});
```

不要跨 `.await` 持有锁，除非协议确实要求且已经分析死锁和尾延迟。短小、不会跨 await 的临界区可使用标准同步锁；需要异步等待锁时使用运行时提供的 async 锁。

## spawn、Send 和 'static

- `'static` 不等于对象永远存在，而是 Future 不借用生命周期更短的数据。
- `move` 把捕获值移入任务，不会自动深复制；引用被 move 进去仍然是引用。
- `Arc<T>` 要跨线程安全使用，T 通常还需满足 `Send + Sync`。
- `Rc<T>`/`RefCell<T>` 适合单线程所有权模型，不能直接跨线程 spawn。
- 不要为了消除 `'static` 错误把所有依赖机械包装成 Arc；先判断任务是否应当独立存在。

## 取消与阻塞

- Future 被 drop 可能取消后续执行，但已经发生的外部副作用不会自动回滚。
- `select!` 中被取消的分支必须满足 cancellation safety，尤其是分帧协议和部分读写。
- 阻塞文件/数据库 SDK 或 CPU 计算不能直接占住 async executor；使用 blocking pool、进程或独立服务。
- 每个 spawn 都要有 JoinHandle、任务组或明确的监控/关闭策略。
- 队列和并发必须有界，不能用无限 spawn 掩盖下游过载。

## 其他 Rust 特有检查

- 为绕开借用检查器反复 `clone`，通常说明所有权边界尚未想清楚。
- `Pin`/`Unpin` 主要约束自引用和 Future 移动，不需要在普通业务模型中主动滥用。
- trait 静态分派与 `dyn Trait` 动态分派会影响 API、对象安全、编译时间和产物体积。
- feature 组合需要进入 CI；过多 feature 会产生未测试的构建矩阵。
- unsafe/FFI 必须缩小到模块边界，并记录长度、对齐、别名、线程和释放责任。

## PR 必查

- [ ] 这个 Arc 是真实共享所有权，还是为了绕过借用问题？
- [ ] 共享数据是否真的需要修改，能否使用不可变快照或 channel？
- [ ] 锁 guard 是否跨越 `.await`，锁顺序和竞争是否可解释？
- [ ] 每个 spawn 是否有人等待、取消并观察错误？
- [ ] 阻塞 IO/CPU 工作是否从 async executor 隔离？
- [ ] 取消后外部副作用和资源是否处于一致状态？
- [ ] clone、unsafe、panic 和 feature 是否都有明确理由与测试？
