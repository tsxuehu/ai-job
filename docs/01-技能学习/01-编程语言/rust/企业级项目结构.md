# Rust：企业级项目结构

Rust 企业仓库要同时控制 crate 边界、公共 API、feature、async runtime 和编译成本。公共工程原则参见 [企业级后端项目工程结构](../../../03-实战项目/企业级项目工程结构.md)。

## 推荐 workspace

```text
repository/
├── Cargo.toml                     # workspace members/dependencies/lints
├── Cargo.lock
├── rust-toolchain.toml
├── crates/
│   ├── order-domain/
│   │   ├── Cargo.toml
│   │   ├── src/lib.rs
│   │   └── tests/
│   ├── order-application/
│   ├── order-adapter-postgres/
│   ├── order-adapter-http/
│   ├── order-adapter-messaging/
│   └── platform-observability/
├── bins/
│   ├── api/
│   │   ├── Cargo.toml
│   │   └── src/main.rs
│   └── worker/
├── contracts/
├── migrations/
├── tests/
│   ├── integration/
│   └── performance/
├── deploy/
├── ops/
├── docs/
└── xtask/                         # 项目自动化，可选
```

小项目不要立即拆出十几个 crate。先在一个 library crate 内用私有 module 建立边界；只有需要独立编译、复用、发布或强制依赖隔离时才拆 crate。

## crate 依赖方向

```text
order-domain
      ▲
order-application ◄── order-adapter-postgres
      ▲              order-adapter-http
      │
    api/worker（composition root）
```

- domain 使用 struct、enum 和纯规则，不依赖 Tokio、数据库、HTTP 和序列化框架。
- application 定义用例与消费方 trait；是否使用 async trait/Future 取决于端口需求，不绑定具体 executor。
- adapter 实现 trait，负责外部 DTO/record 与领域类型转换。
- binary 选择 Tokio 等 runtime、创建 client/连接池，并使用 `Arc` 等建立真实共享所有权。
- crate 图必须有向无环；不能用 feature 或动态注册掩盖反向依赖。

## module 与公共 API

- 项默认私有，优先 `pub(crate)`，从 `lib.rs` re-export 最小稳定 API。
- 不把内部错误、第三方 client、ORM row 和 runtime handle 泄露给调用方。
- sealed/internal trait、newtype 和构造函数用于保护不变量。
- 每个 public API 说明 panic、错误、取消、Send/Sync 和资源行为。
- `mod.rs` 或同名文件风格在项目内统一，不影响架构原则。

## workspace 依赖与 feature

- 在 workspace 统一常用依赖版本、lint 和 release profile。
- 应用提交 Cargo.lock，CI 使用 `--locked`。
- feature 表达可选能力，不能作为环境配置或互斥业务模式滥用。
- 支持的 feature 组合进入 CI，避免只在某个客户构建时才编译失败。
- 关注 crate 重复版本、proc macro、泛型单态化和链接对编译时间的影响。

## async 应放在哪里

- runtime 初始化、信号、任务组和优雅停机在 bins/bootstrap。
- adapter 负责数据库、HTTP、消息等异步 IO。
- application 负责编排超时、取消和业务流程，但不直接创建全局 runtime。
- CPU/阻塞工作进入 blocking pool、Rayon/进程或独立服务，并设置容量。
- 每个 spawn 有 JoinHandle、任务组或监控策略，不能成为失管后台任务。

## 测试组织

- crate 内单元测试：私有规则与状态转换。
- crate `tests/`：只通过公共 API 做集成测试。
- workspace 集成测试：数据库、HTTP、消息与迁移。
- 文档测试：公共 API 示例持续可编译。
- property/fuzz：解析、状态机和不可信输入。
- unsafe/FFI：独立安全不变量、Miri/sanitizer 和边界测试。

## 常见错误

- 所有项都改成 `pub`，crate 之间随意调用内部细节。
- 为追求“微模块”创建大量只有转发代码的小 crate。
- domain 派生所有 Serde/ORM 类型，使外部协议污染核心。
- feature 组合爆炸，应用行为依赖无法测试的条件编译。
- 在 library 内创建 runtime，或为了满足 `'static` 到处使用 `Arc`。

## 验收

- [ ] crate/module 边界与业务能力一致，公共 API 明显小于内部实现。
- [ ] domain/application 不依赖具体 async runtime 和基础设施实现。
- [ ] workspace 依赖、lint、工具链、feature 和锁文件可复现。
- [ ] binary 是唯一主要组装入口，任务和资源可优雅关闭。
- [ ] 测试覆盖 crate API、adapter、契约、取消与 unsafe 边界。
- [ ] 能说明继续拆 crate 带来的明确收益与编译成本。
