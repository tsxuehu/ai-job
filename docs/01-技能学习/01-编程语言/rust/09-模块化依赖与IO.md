# Rust：模块化、依赖与 IO

Rust 工程以 Cargo 为中心，但需要分清架构模块、发布单元、编译单元和代码命名空间。

## module、crate 不等于业务模块

module 控制 crate 内命名和可见性，crate 是编译边界，workspace 管理多个 package；业务模块则围绕一组不变量和用例形成。小项目优先在一个 library crate 内用私有 module 建立边界，只有需要独立编译、发布、复用或强依赖隔离时才拆 crate。

```text
domain       # struct/enum/规则，不依赖运行时和数据库
application  # 用例与存储 trait
postgres     # 实现存储 trait
http         # 协议 DTO 与 handler
server       # composition root
```

- Rust 项默认私有；使用 `pub(crate)`、私有 module 和窄 re-export，不能为了消除编译错误全部改成 `pub`。
- 端口 trait 通常定义在消费抽象的一侧，adapter 通过 `impl` 提供实现。
- 核心模型不携带 Serde、ORM、HTTP 和 Tokio 类型，边界 DTO 负责转换。
- workspace crate 依赖必须保持有向无环；循环通常意味着职责需要合并、抽象上移或事件解耦。
- 不为每个小概念创建 crate。crate 过细会增加编译、feature、版本和 API 管理成本。

lib crate 保留业务入口，binary 只负责配置、依赖组装、runtime 和进程生命周期，使核心无需启动服务器即可测试。

## package、crate、module、workspace

- package 由 `Cargo.toml` 描述，可包含库和多个二进制 crate。
- crate 是一次编译的单元。
- module 组织 crate 内名称和可见性。
- workspace 管理多个相关 package，并统一部分构建配置。

```text
project/
├── Cargo.toml
├── src/lib.rs
├── src/service.rs
├── src/bin/server.rs
└── tests/api_test.rs
```

核心业务放 library crate，二进制入口负责配置、依赖组装和进程生命周期。使用 `pub(crate)`、私有模块和 re-export 构建最小稳定 API。

## Cargo 与依赖治理

- `Cargo.toml` 声明依赖、feature、目标和 profile。
- 应用提交 `Cargo.lock` 并在 CI 使用锁定版本。
- feature 表达可选能力，避免无法测试的组合爆炸。
- 检查 crate 维护状态、许可证、安全公告、传递依赖和 MSRV。
- 外部库放在适配层后，避免第三方类型扩散进领域模型。

## IO 与协议边界

```rust
let file = std::fs::File::open(path)?;
for line in BufReader::new(file).lines() {
    process(line?)?;
}
```

- 缓冲小块 IO，限制总大小、行长、嵌套深度和响应体。
- 区分字节、UTF-8 文本与业务字符。
- 处理部分写入、磁盘满、权限、超时和取消。
- 网络异步通常依赖 Tokio 等运行时；Serde 只解决转换，不替代协议版本设计。
- 外部 DTO 与领域类型分离，明确未知字段、默认值和版本演进。

## 验收

- 能区分业务模块、Rust module、crate、package 与 workspace。
- 核心 crate/module 不依赖数据库、HTTP 和 async runtime 具体类型。
- 公共 API 通过最小 re-export 暴露，adapter 可由内存实现替换测试。
- 能解释 package、crate、module 与 workspace 的边界。
- 新环境可用锁定依赖完成构建、测试和运行。
- 文件、网络和序列化边界有大小、超时、错误和演进策略。

完整的 workspace、crates、bins、contracts、migrations 和 deploy 组织方式参见 [Rust 企业级项目结构](企业级项目结构.md)。
