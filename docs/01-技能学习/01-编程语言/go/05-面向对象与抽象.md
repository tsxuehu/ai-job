# Go：用订单支付看懂面向对象

> Go 没有 `class` 和类继承。记住五件事就够了：`struct` 放数据，method 放行为，package 做封装，interface 做多态，组合替代继承。

本文只实现一个需求：订单选择一种支付渠道付款，测试时换成假支付实现。

> 快速阅读：先看第 1、2、4、5、8、10 节；需要处理接口陷阱时再看第 6、7 节。

---

## 1. 一张表先看懂

| 面向对象概念 | Go 怎么实现 |
|---|---|
| 对象 | 一个 struct 值或指针 |
| 类 | 没有；使用 `struct + method` |
| 封装 | 小写名字只在当前 package 可见 |
| 抽象 | interface 只规定需要的方法 |
| 多态 | 多个类型都实现同一个 interface |
| 继承 | 没有；使用字段组合和显式委托 |

Go 把传统 class 拆开了：

```text
class 中的数据      → struct
class 中的方法      → receiver method
private/public      → package 的大小写规则
interface/虚方法    → interface
继承代码            → 组合
```

## 2. struct + method：订单拥有数据和行为

```go
type OrderStatus string

const (
    StatusPending OrderStatus = "pending"
    StatusPaid    OrderStatus = "paid"
)

type Order struct {
    id          string
    amountCents int64
    status      OrderStatus
    paymentID   string
}

func NewOrder(id string, amountCents int64) (*Order, error) {
    if amountCents <= 0 {
        return nil, errors.New("订单金额必须大于 0")
    }
    return &Order{
        id:          id,
        amountCents: amountCents,
        status:      StatusPending,
    }, nil
}

func (o *Order) MarkPaid(paymentID string) error {
    if o.status != StatusPending {
        return errors.New("订单不能重复支付")
    }
    o.status = StatusPaid
    o.paymentID = paymentID
    return nil
}

func (o Order) ID() string          { return o.id }
func (o Order) AmountCents() int64  { return o.amountCents }
```

这里分别发生了什么：

- `Order` struct 保存订单数据；
- `MarkPaid` 是订单行为；
- `(o *Order)` 叫 receiver，指针 receiver 可以修改原订单；
- 字段名是小写，其他 package 不能直接修改；
- 外部必须调用 `NewOrder` 创建合法订单；
- 外部必须调用 `MarkPaid` 改状态，因此不能伪造重复支付。

这就是封装。不是写 getter/setter，而是让订单自己守住业务规则。

## 3. interface：结算流程只要求一个 `Pay` 方法

结算流程不应该知道支付宝 SDK 的细节。它只需要“支付”能力：

```go
type PaymentReceipt struct {
    ID string
}

type PaymentGateway interface {
    Pay(
        ctx context.Context,
        orderID string,
        amountCents int64,
    ) (PaymentReceipt, error)
}
```

`PaymentGateway` 只是规定：

```text
谁想充当支付网关，谁就必须提供同样的 Pay 方法。
```

它不保存订单，也不调用任何支付平台。

### 支付宝实现

```go
type AlipayGateway struct{}

func (AlipayGateway) Pay(
    ctx context.Context,
    orderID string,
    amountCents int64,
) (PaymentReceipt, error) {
    // 实际项目在这里调用支付宝 SDK。
    return PaymentReceipt{ID: "alipay-001"}, nil
}
```

### 测试假实现

```go
type FakeGateway struct{}

func (FakeGateway) Pay(
    ctx context.Context,
    orderID string,
    amountCents int64,
) (PaymentReceipt, error) {
    // 不联网、不扣钱。
    return PaymentReceipt{ID: "test-001"}, nil
}
```

Go 不写 `implements PaymentGateway`。只要 `Pay` 的方法名、参数和返回值一致，类型就自动满足接口。

```go
var _ PaymentGateway = AlipayGateway{}
var _ PaymentGateway = FakeGateway{}
```

这两行只让编译器检查接口是否满足，不执行支付。

## 4. 多态：同一行 `Pay`，运行不同代码

结算服务保存一个 `PaymentGateway`：

```go
type CheckoutService struct {
    gateway PaymentGateway
}

func NewCheckoutService(gateway PaymentGateway) *CheckoutService {
    return &CheckoutService{gateway: gateway}
}

func (s *CheckoutService) Checkout(
    ctx context.Context,
    order *Order,
) error {
    receipt, err := s.gateway.Pay(
        ctx, order.ID(), order.AmountCents(),
    )
    if err != nil {
        return err
    }
    return order.MarkPaid(receipt.ID)
}
```

生产环境传支付宝：

```go
service := NewCheckoutService(AlipayGateway{})
```

测试环境传假实现：

```go
service := NewCheckoutService(FakeGateway{})
```

两种情况下，`Checkout` 内部都是同一行：

```go
s.gateway.Pay(...)
```

但实际执行不同：

```text
gateway 中是 AlipayGateway → 调用 AlipayGateway.Pay
gateway 中是 FakeGateway   → 调用 FakeGateway.Pay
```

这就是运行时多态：**调用代码不变，传入的具体对象决定执行哪个方法。**

## 5. 组合：为什么不需要继承

`CheckoutService` 有一个字段：

```go
type CheckoutService struct {
    gateway PaymentGateway
}
```

它表达的是：

```text
CheckoutService has a PaymentGateway
结算服务“使用一个”支付网关
```

这叫组合。

Go 不需要建立下面这种继承树：

```text
BasePaymentGateway
├── AlipayGateway
└── BankCardGateway
```

传统继承承担的职责，在 Go 中被拆开：

| 需求 | Go 的做法 |
|---|---|
| 复用数据 | 把另一个 struct 放进字段 |
| 复用行为 | 调用字段的方法或普通函数 |
| 替换实现 | interface |
| 增加包装逻辑 | 包装对象并显式调用 `next` |

例如给支付增加日志：

```go
type LoggingGateway struct {
    next PaymentGateway
}

func (g LoggingGateway) Pay(
    ctx context.Context,
    orderID string,
    amountCents int64,
) (PaymentReceipt, error) {
    log.Println("开始支付", orderID)
    receipt, err := g.next.Pay(ctx, orderID, amountCents)
    log.Println("支付结束", orderID, err)
    return receipt, err
}
```

`LoggingGateway` 没有继承支付宝。它拥有一个 `next`，把真正支付委托给 `next`。

## 6. embedding 不是继承

Go 允许省略字段名：

```go
type User struct {
    Name string
}

func (u User) Hello() string {
    return "hello " + u.Name
}

type Admin struct {
    User // embedding
}
```

于是可以写：

```go
admin := Admin{User: User{Name: "Edy"}}
fmt.Println(admin.Hello())
```

但真实关系仍然是：

```text
Admin 有一个 User
不是 Admin 是一种 User
```

`admin.User` 仍然存在。Go 只是把 `admin.User.Hello()` 简写成了 `admin.Hello()`。

所以 embedding 是字段和方法提升，不是父类/子类继承。

## 7. interface 必须知道的两个坑

### 7.1 指针 receiver 会影响谁满足接口

如果方法写在指针上：

```go
type AlipayGateway struct{}

func (*AlipayGateway) Pay(
    context.Context, string, int64,
) (PaymentReceipt, error) {
    return PaymentReceipt{ID: "alipay-001"}, nil
}
```

那么：

```go
var gateway PaymentGateway
gateway = &AlipayGateway{} // 正确
// gateway = AlipayGateway{} // 编译失败
```

入门阶段记住这一条即可：

> 接口方法使用指针 receiver 时，把指针 `&Type{}` 赋给接口。

通常需要修改状态、避免复制或包含锁时，使用指针 receiver。

### 7.2 接口里装了 nil 指针，接口本身不等于 nil

```go
var alipay *AlipayGateway = nil
var gateway PaymentGateway = alipay

fmt.Println(alipay == nil)  // true
fmt.Println(gateway == nil) // false
```

可以把接口理解成：

```text
(具体类型, 具体值)
```

此时 gateway 是：

```text
(*AlipayGateway, nil)
```

它有具体类型，所以接口本身不是 nil。调用方法时可能 panic。

最简单的防线：

- 没有实现时直接返回字面量 `nil`；
- 实现的构造函数优先返回具体指针；
- 不要把 nil 具体指针再赋给接口。

## 8. interface、函数和泛型怎么选

| 需求 | 选择 | 例子 |
|---|---|---|
| 运行时替换实现 | interface | 支付宝、银行卡、测试假实现 |
| 只传入一小段行为 | 函数 | 排序规则、回调 |
| 写适用于多种类型的算法或容器 | 泛型 | `Stack[T]`、`Sum[T]` |
| 处理固定业务状态 | 具名常量 + switch | 订单待支付、已支付、已取消 |

泛型不会取代 interface：

- interface 解决“运行时传进来的是哪个实现”；
- 泛型解决“同一段代码适用于哪些类型”。

订单支付需要运行时替换网关，所以使用 interface。

## 9. 项目中怎么写

推荐结构：

```text
internal/order/
├── order.go          # Order 和业务规则
├── checkout.go       # CheckoutService 和 PaymentGateway 接口
├── alipay.go         # 真实支付实现，也可以放单独 adapter package
└── checkout_test.go  # FakeGateway 和测试
```

项目规则：

1. interface 放在使用方附近，例如 `CheckoutService` 旁边；
2. interface 只放调用方真正需要的方法；
3. 没有替换需求时，直接使用具体类型；
4. 在 `main` 或启动代码中创建具体实现并传入 service；
5. interface 不保证线程安全，多个 goroutine 共享时仍要检查具体实现；
6. 不要创建 `IOrderService`、`IRepository` 等大而空泛的接口。

一个接口只有一个方法完全正常。Go 标准库的 `error`、`io.Reader`、`http.Handler` 都是小接口。

## 10. 面试时这样回答

> Go 没有 class 和类继承。它使用 struct 保存数据、method 定义行为、package 大小写规则实现封装。多个类型只要具有相同方法，就会隐式满足 interface；调用方通过 interface value 在运行时替换具体实现，这就是多态。代码复用优先使用字段组合和显式委托，embedding 只是方法提升，不是父子类型继承。

需要能继续解释：

1. 为什么 `AlipayGateway` 不需要写 `implements`？
2. `CheckoutService` 为什么定义小接口，而不是依赖完整 SDK？
3. 为什么 embedding 不是继承？
4. 值和指针什么时候能满足接口？
5. 为什么接口里装了 nil 指针后不等于 nil？
