# Go：自定义类型、面向对象与抽象

Go 没有 `class`、`extends` 和传统类继承，但并不缺少面向对象需要解决的问题。它把这些能力拆成了更小的机制：

- 用具名类型和 `struct` 表达数据；
- 用 method 给类型增加行为；
- 用 package 和导出规则实现封装；
- 用字段组合、embedding 和委托复用能力；
- 用 interface value 实现运行时多态；
- 用泛型和 constraint 实现编译期的参数化多态。

学习 Go 时不要把它强行翻译成“没有语法糖的 Java”。更准确的认识是：Go 保留了封装、抽象和多态，主动放弃了类继承树。

## 快速阅读路线

- 第一次学习：先读第 3～7 节，掌握 interface、动态类型、方法集和 typed nil；
- 写项目之前：再读第 9～14 节，掌握组合、小接口、泛型选择和并发边界；
- 面试复习：使用第 16～18 节做选型复述、误区检查和动手练习。

## 面向对象概念映射

| 面向对象概念 | Go 中的实现 | 关键区别 |
| --- | --- | --- |
| 对象 | 具名类型或 `struct` 的值、指针以及对应 method | 不要求对象来自 class |
| 类 | 没有 class；类型定义和 receiver method 共同承担类似职责 | 数据定义和方法声明可以分开写，但必须在同一个 package |
| 封装 | package 边界；小写名称不导出，大写名称导出 | 没有 `private/protected/public` 关键字 |
| 继承 | 不支持类继承；使用字段组合、embedding 和显式委托 | embedding 是方法提升，不是父子类型关系 |
| 抽象 | 小 interface、函数类型、泛型 constraint | interface 通常由使用方按最小需求定义 |
| 运行时多态 | interface value | 类型按方法集隐式实现接口，不写 `implements` |
| 编译期多态 | 泛型 + constraint | 适合通用算法、容器和类型安全适配器 |
| 封闭类型集合 | 未导出方法的 interface、标签结构或包内约束 | `type switch` 不提供穷举检查 |

## 1. struct、具名类型与 method

### struct 负责数据，method 负责行为

```go
type Order struct {
	ID     string
	Amount int64
}

func (o Order) IsLarge() bool {
	return o.Amount >= 10_000
}

func (o *Order) ApplyDiscount(percent int64) {
	o.Amount -= o.Amount * percent / 100
}
```

`(o Order)` 和 `(o *Order)` 称为 receiver：

- 值 receiver 得到值的副本，适合小型、不可变语义的类型；
- 指针 receiver 可以修改原值，也能避免复制大结构；
- 包含 `sync.Mutex` 等不可复制字段的类型，应使用指针并禁止复制；
- 同一类型通常统一采用一种 receiver 风格，避免方法集难以判断。

### 具名类型不只用于 struct

```go
type UserID int64
type Status string

const (
	StatusPending Status = "pending"
	StatusPaid    Status = "paid"
)

func (s Status) Valid() bool {
	return s == StatusPending || s == StatusPaid
}
```

`type UserID int64` 定义了新类型，不能和 `int64` 随意混用，也不会继承原类型的方法；`type UserID = int64` 才是类型别名。业务代码优先用具名类型表达语义，减少把订单 ID、用户 ID 和普通数字混用的错误。

## 2. 封装依赖 package，而不是 class

```go
type Service struct {
	notifier Notifier // 小写字段，仅当前 package 可直接访问
}

func NewService(notifier Notifier) (*Service, error) {
	if notifier == nil {
		return nil, ErrMissingNotifier
	}
	return &Service{notifier: notifier}, nil
}
```

Go 用名称首字母控制 package 外是否可见：

- `Service`、`NewService` 可以被其他 package 使用；
- `notifier` 只能在当前 package 访问；
- 没有 `protected`，也不鼓励子类修改父类内部状态；
- 构造函数只是名为 `NewXxx` 的普通函数，用来校验参数、注入依赖和建立不变量。

封装的单位是 package，不是单个 struct。不要因为同包代码能够访问未导出字段，就把整个项目都放进一个大 package；那会失去封装边界。

## 3. Go 的“多态”不只有一种

先按问题选择机制，再写语法：

| 需求 | Go 机制 | 绑定时机 | 类型集合 |
| --- | --- | --- | --- |
| 调用方只依赖一种行为，运行时可替换实现 | interface value | 运行时根据动态类型选择 method | 开放，后续类型可隐式实现 |
| 编写适用于多种类型的算法或容器 | 泛型 + constraint | 编译期做类型检查 | 由 constraint 限制 |
| 一次性传入一段行为 | 函数或函数类型 | 普通函数调用 | 不需要对象层次 |
| 处理有限的业务状态或事件 | 标签结构、包内受限 interface + `type switch` | 运行时分支 | 可以限制实现位置，但没有穷举检查 |

传统 OOP 中“子类重写父类方法”的工作，在 Go 里通常变成“多个类型满足同一个小接口”。

## 4. interface：隐式实现接口

下面用通知能力贯穿运行时多态：

```go
type Notifier interface {
	Send(context.Context, Order) error
}

type EmailNotifier struct {
	from string
}

func (n EmailNotifier) Send(ctx context.Context, order Order) error {
	// 调用邮件服务
	return nil
}

type LogNotifier struct{}

func (LogNotifier) Send(ctx context.Context, order Order) error {
	// 只记录日志
	return nil
}
```

`EmailNotifier` 和 `LogNotifier` 没有声明 `implements Notifier`。只要方法名、参数、返回值和 receiver 对应的方法集满足接口，它们就自动实现 `Notifier`。

可以用编译期断言把设计意图写进代码：

```go
var _ Notifier = EmailNotifier{}
var _ Notifier = LogNotifier{}
```

右侧值只用于让编译器检查赋值是否成立，不会产生业务逻辑。

隐式实现带来两个结果：

1. 实现类型不需要依赖接口所在的 package，第三方类型也能被本地接口抽象；
2. 接口应该尽量小，否则任何新增 method 都可能让已有实现和测试替身不再满足接口。

Go 标准库中的 `error`、`io.Reader`、`http.Handler` 都是这种基于行为的抽象。

## 5. interface value：运行时多态怎样发生

```go
type OrderService struct {
	notifier Notifier
}

func (s *OrderService) Create(ctx context.Context, order Order) error {
	// 保存订单……
	return s.notifier.Send(ctx, order)
}

func NewOrderService(notifier Notifier) *OrderService {
	return &OrderService{notifier: notifier}
}
```

装配时可以注入不同实现：

```go
emailService := NewOrderService(EmailNotifier{from: "shop@example.com"})
logService := NewOrderService(LogNotifier{})
```

`OrderService` 只知道静态类型 `Notifier`，不知道具体实现。执行 `Send` 时，由接口值中保存的动态类型决定调用哪个 method，这就是运行时多态。

### 一个接口值包含什么

理解接口时，可以把它看成一对信息：

```text
(动态类型, 动态值)
```

例如：

```go
var n Notifier = EmailNotifier{from: "shop@example.com"}
```

- 变量 `n` 的静态类型是 `Notifier`；
- 它当前保存的动态类型是 `EmailNotifier`；
- 动态值是对应的 `EmailNotifier` 值。

给接口赋一个非指针值，会把该值放入接口；给接口赋一个指针，则多个位置可能通过该指针共享并修改同一个对象。interface 本身不表达所有权、不可变性或线程安全。

### 异构集合

接口还能把不同具体类型放入同一个集合：

```go
notifiers := []Notifier{
	EmailNotifier{from: "shop@example.com"},
	LogNotifier{},
}

for _, notifier := range notifiers {
	if err := notifier.Send(ctx, order); err != nil {
		return err
	}
}
```

这是 interface value 相对普通泛型参数的重要能力：一个 `[]Notifier` 可以在同一切片里保存多种动态类型。

### interface 是否可比较，取决于动态值

interface 可以和 `nil` 安全比较。两个 interface 的动态类型相同时，如果该类型的值不可比较，相互比较就会 panic：

```go
var left any = []int{1, 2}
var right any = []int{1, 2}

fmt.Println(left == nil)   // false
fmt.Println(left == right) // panic：slice 不可比较
```

因此不要把任意值放进 `any` 后直接当作 map key，也不要假设两个 interface 总能使用 `==`。需要比较复杂数据时，应定义明确的业务相等规则。

## 6. 方法集：值类型为什么有时不能赋给接口

“这个类型明明有这个 method，为什么还说它没有实现接口？”通常是因为混淆了方法调用便利规则和方法集。

先忽略后文的 embedding 提升规则。对非 interface 的具名类型 `T`，核心规则是：

| 类型 | 方法集包含 |
| --- | --- |
| `T` | receiver 为 `T` 的 method |
| `*T` | receiver 为 `T` 或 `*T` 的 method |

看一个需要修改状态的实现：

```go
type CountingNotifier struct {
	count int
}

func (n *CountingNotifier) Send(ctx context.Context, order Order) error {
	n.count++
	return nil
}

var _ Notifier = (*CountingNotifier)(nil)
// var _ Notifier = CountingNotifier{} // 编译失败
```

`Send` 的 receiver 是 `*CountingNotifier`，因此：

- `*CountingNotifier` 满足 `Notifier`；
- `CountingNotifier` 不满足 `Notifier`。

但下面的普通调用可能仍然成功：

```go
counter := CountingNotifier{}
_ = counter.Send(ctx, order)
```

因为 `counter` 是可寻址变量，编译器可以把调用理解为 `(&counter).Send(...)`。这只是 method call 的便利规则，不会改变 `CountingNotifier` 的方法集，也不会让值类型突然满足接口。

### receiver 怎么选

| 情况 | 通常选择 |
| --- | --- |
| method 要修改 receiver | 指针 receiver |
| struct 很大，复制成本明显 | 指针 receiver |
| struct 含 `sync.Mutex` 等不可复制状态 | 指针 receiver |
| 小型值对象，method 不修改值 | 值 receiver |
| 需要值和指针都满足某接口 | 该接口相关 method 使用值 receiver |

不要只为“少写一个 `&`”混用 receiver。先确定类型是值语义还是对象/共享状态语义，再统一设计方法集。

## 7. typed nil：接口不为 nil，里面的指针却为 nil

这是 Go 接口最经典的陷阱：

```go
var counter *CountingNotifier = nil
var notifier Notifier = counter

fmt.Println(counter == nil)  // true
fmt.Println(notifier == nil) // false
```

原因是：

```text
counter   = (*CountingNotifier, nil)
notifier  = (*CountingNotifier, nil)
nil 接口  = (无动态类型, 无动态值)
```

`notifier` 已经保存了动态类型 `*CountingNotifier`，所以它不是 nil interface。此时调用 `notifier.Send(...)` 还可能因为 method 解引用 nil receiver 而 panic。

### 常见错误：返回 typed nil

```go
func NewNotifier(enabled bool) Notifier {
	var notifier *CountingNotifier
	if !enabled {
		return notifier // 错误：返回的是非 nil interface
	}
	return &CountingNotifier{}
}
```

更安全的写法：

```go
func NewNotifier(enabled bool) Notifier {
	if !enabled {
		return nil
	}
	return &CountingNotifier{}
}
```

工程上的防线：

- 实现的构造函数优先返回具体类型，如 `*CountingNotifier`；在装配层再赋给接口；
- 返回接口时，失败或“没有值”应直接返回字面量 `nil`；
- 不要认为 `if dependency == nil` 能识别接口内的所有 typed nil；
- 除非 nil receiver 是刻意设计且有清晰语义，否则 method 不要接收或容忍 nil receiver。

`error` 本身也是 interface。返回一个值为 nil 的 `*MyError`，同样会得到非 nil 的 `error`；自定义错误构造和返回路径必须遵守相同规则。

## 8. type assertion 与 type switch

接口隐藏了具体类型。确实需要恢复具体能力时，可以做类型断言：

```go
type Resettable interface {
	Reset()
}

if resetter, ok := notifier.(Resettable); ok {
	resetter.Reset()
}
```

使用 `value, ok := x.(T)`，断言失败时 `ok` 为 `false`；直接写 `value := x.(T)`，失败会 panic，通常只适合能够证明类型一定成立的内部不变量。

需要区分多个动态类型时使用 type switch：

```go
switch n := notifier.(type) {
case EmailNotifier:
	fmt.Println("email from", n.from)
case *CountingNotifier:
	if n == nil {
		fmt.Println("typed nil counting notifier")
	} else {
		fmt.Println("sent", n.count, "times")
	}
case nil:
	fmt.Println("no notifier")
default:
	fmt.Printf("unknown notifier: %T\n", n)
}
```

适合使用断言的场景：

- 基础设施边界需要识别驱动或协议的额外能力；
- 可选能力接口，例如 `io.Closer`、`http.Flusher`；
- 编解码、注册表等天然与运行时类型有关的代码。

如果核心业务大量 switch 具体实现，通常说明抽象泄漏：调用方真正需要的行为没有进入接口，或者本来应该显式建模成业务状态。

type switch 也没有穷举检查。以后新增一种实现，旧 switch 不会因为漏处理而编译失败。

注意，`case nil` 只匹配 nil interface；保存 `(*CountingNotifier)(nil)` 的接口会进入 `case *CountingNotifier`，所以该分支仍需判断 `n == nil`。

## 9. embedding 是方法提升，不是继承

### 匿名嵌入会提升 method

```go
type EmbeddedNotifier struct {
	Notifier
	logger *slog.Logger
}
```

如果没有重名 method，`EmbeddedNotifier` 可以通过提升后的 `Send` 调用其嵌入字段。它看起来有点像继承，但语义不同：

- `EmbeddedNotifier` 内部“有一个”`Notifier` 字段，不是某个实现的子类；
- 它不会自动变成嵌入具体类型可替换的父子关系；
- 外层值可以显式访问 `x.Notifier`，组合关系仍然存在；
- method 或字段名冲突时，需要显式选择；
- 嵌入 nil 指针或 nil interface，调用提升的方法可能 panic；
- embedding 只解决提升和复用，不会自动给调用加审计逻辑。

### 装饰器应显式委托

要在调用前后增加逻辑，通常使用具名字段并明确转发：

```go
type AuditedNotifier struct {
	next   Notifier
	logger *slog.Logger
}

func (n *AuditedNotifier) Send(ctx context.Context, order Order) error {
	n.logger.InfoContext(ctx, "sending notification", "order_id", order.ID)

	err := n.next.Send(ctx, order)
	if err != nil {
		n.logger.ErrorContext(ctx, "notification failed", "error", err)
	}
	return err
}

var _ Notifier = (*AuditedNotifier)(nil)
```

具名字段能让“委托给谁”更明显，适合业务依赖、装饰器和适配器。embedding 更适合确实希望公开和提升内层能力的场景，不要把它当成默认继承语法。

### interface embedding 是组合要求

```go
type ReadWriteCloser interface {
	io.Reader
	io.Writer
	io.Closer
}
```

这表示实现类型的方法集必须同时包含 `Read`、`Write` 和 `Close`，不是说 `ReadWriteCloser` 对象继承了三个父类。

## 10. 小接口与“由使用方定义”

假设业务只需要保存订单：

```go
type OrderSaver interface {
	Save(context.Context, Order) error
}

type OrderService struct {
	saver OrderSaver
}
```

即使数据库实现还有 `Find`、`Delete`、`Migrate` 等 method，`OrderService` 也只依赖 `Save`。这样做的收益是：

- 调用方的真实需求一眼可见；
- 测试替身只实现一个 method；
- 数据库实现可以在不知道 `OrderSaver` 存在的情况下隐式满足它；
- 不相关 method 的变化不会影响调用方。

常用经验是“接收接口，返回具体类型”，但它是设计启发，不是机械规则：

```go
// 基础设施包通常返回自己的具体实现。
func NewPostgresStore(db *sql.DB) *PostgresStore

// 业务包在消费位置定义自己需要的小接口。
type OrderSaver interface {
	Save(context.Context, Order) error
}
```

以下做法需要警惕：

- 在实现包预先定义包含所有 method 的巨大 `IRepository`；
- 只为了 mock 而给每个 struct 创建同名 interface；
- 返回 interface 后，调用方又频繁断言回具体类型；
- 给已公开 interface 增加 method，却忽略所有外部实现都会受影响。

interface 最有价值的地方是隔离行为边界，而不是消除所有具体类型。

## 11. 函数类型也能实现多态

只有一个行为时，不一定要先创建 struct：

```go
type NotifyFunc func(context.Context, Order) error

func (f NotifyFunc) Send(ctx context.Context, order Order) error {
	return f(ctx, order)
}

var _ Notifier = NotifyFunc(nil)
```

现在闭包也能作为 `Notifier`：

```go
notifier := NotifyFunc(func(ctx context.Context, order Order) error {
	fmt.Println("notify", order.ID)
	return nil
})

service := NewOrderService(notifier)
```

这种适配方式适合：

- 单 method 策略；
- 中间件和回调；
- 测试中的轻量替身；
- 把普通函数接入已有接口。

标准库的 `http.HandlerFunc` 就采用了同样思路：函数类型通过一个 method 满足接口。

## 12. 泛型多态：约束一类类型，而不是保存任意实现

### 泛型调用共同的行为

```go
func SendAll[N Notifier](
	ctx context.Context,
	notifiers []N,
	order Order,
) error {
	for _, notifier := range notifiers {
		if err := notifier.Send(ctx, order); err != nil {
			return err
		}
	}
	return nil
}
```

编译器根据 constraint 检查 `N` 是否允许调用 `Send`。当 `N` 实例化为具体类型时，`[]N` 的元素是同一种具体类型；`[]Notifier` 则明确表达“每个元素可以保存不同的动态类型”。类型参数也可以实例化为接口类型，但这时异构能力仍然来自 interface value，而不是泛型本身。

### type set 描述允许的底层类型和操作

```go
type Number interface {
	~int | ~int64 | ~float64
}

func Sum[N Number](values []N) N {
	var total N
	for _, value := range values {
		total += value
	}
	return total
}
```

`~int64` 表示底层类型为 `int64` 的类型也在集合中，因此自定义的 `type Amount int64` 可以作为 `N`。

要区分 interface 的两种角色：

| 角色 | 示例 | 能否声明普通变量 |
| --- | --- | --- |
| 基本接口，描述 method | `interface { Read([]byte) (int, error) }` | 可以作为普通 interface value，也可以作 constraint |
| 含类型项的非基本接口 | `interface { ~int \| ~int64 }` | 只能用于类型约束，不能作为普通变量类型 |

因此不能写：

```go
// var number Number // 编译失败：Number 只能作 constraint
```

### interface 还是泛型

| 问题 | 更适合 interface | 更适合泛型 |
| --- | --- | --- |
| 运行时选择数据库、消息队列、支付渠道 | 是 | 通常不是首选 |
| 一个集合要保存不同具体实现 | 是，使用 `[]Interface` | 不适合普通 `[]T` |
| 编写栈、集合、排序、映射等通用结构/算法 | 能做但常损失类型信息 | 是 |
| 调用方只依赖少量业务行为 | 是 | 仅在确实需要保留类型参数时使用 |
| 需要基于底层类型使用 `+`、`<` 等运算 | 普通接口不能表达 | 是，使用 type set constraint |

不要因为“泛型可能更快”就改写所有 interface，也不要为了避免一个类型参数就把所有值装进 `any`。先根据语义选择，再用 benchmark 和 profile 判断性能。

## 13. 如何表达封闭的多态集合

Go 的 interface 默认是开放的：其他 package 只要有匹配方法就能实现。可以用未导出 method 限制实现位置：

```go
type Event interface {
	isEvent()
}

type OrderCreated struct {
	OrderID string
}

func (OrderCreated) isEvent() {}

type OrderCancelled struct {
	OrderID string
}

func (OrderCancelled) isEvent() {}
```

其他 package 不能直接声明本包的未导出 `isEvent` method，因此正常实现会被限制在当前 package。严格来说，这不是无法绕过的 sealed type：外部 struct 仍可能通过 embedding `Event` 获得提升的方法；编译器也不会强制检查所有实现是否被处理：

```go
func Handle(event Event) error {
	switch event := event.(type) {
	case OrderCreated:
		return handleCreated(event)
	case OrderCancelled:
		return handleCancelled(event)
	default:
		return fmt.Errorf("unsupported event %T", event)
	}
}
```

以后在本包新增事件，编译器不会强制所有 type switch 增加分支。因此必须保留安全的 `default`、增加测试，或者用带 `Kind` 的标签结构显式校验。

## 14. 并发语境下：interface 不等于线程安全

把具体实现赋给 interface，不会自动复制所有底层状态，也不会自动增加锁：

```go
type ConcurrentCountingNotifier struct {
	mu    sync.Mutex
	count int
}

func (n *ConcurrentCountingNotifier) Send(ctx context.Context, order Order) error {
	n.mu.Lock()
	n.count++
	n.mu.Unlock()
	return nil
}
```

在多个 goroutine 中共享 `Notifier` 时，要检查具体实现：

- 是否共享指针、map、slice、连接或缓存；
- method 是否允许并发调用；
- 锁保护的是哪个不变量；
- 是否正确传递 `context.Context` 以支持取消和超时；
- interface 生命周期是否长于它持有的文件、连接或客户端。

即使把一个 struct 值复制进 interface，struct 内部的 map、slice、指针仍可能指向共享数据。线程安全是具体实现及其使用约定，不是 interface 类型系统提供的保证。

## 15. 为什么 Go 不提供类继承

Go 没有取消面向对象概念，而是把继承承担的多种职责拆开：

| 传统继承常承担的职责 | Go 的替代方式 |
| --- | --- |
| 复用字段 | struct 字段或 embedding |
| 复用实现 | 组合对象并显式委托 |
| 子类型替换 | interface |
| 重写并扩展行为 | 包装器/装饰器，在 method 中调用 `next` |
| 约束通用算法 | 泛型 constraint |
| 共享构造流程 | 普通构造函数、辅助函数或 builder |

这样做避免了几个问题：

- 复用实现不再强制建立“is-a”父子关系；
- 不需要维护脆弱、层级很深的基类；
- 类型可以事后满足接口，不必由框架基类预先授权；
- 业务依赖可以缩小为调用方真正需要的几个 method。

代价也要承认：Go 没有基类模板方法、受保护成员、虚方法覆写等现成机制，需要通过组合和显式委托组织代码。显式代码可能稍多，但依赖关系更容易追踪。

## 16. 项目中的选择流程

遇到“这里需要抽象”时，可以按下面顺序判断：

```text
只是传入一段行为？
  └─ 是：普通函数或函数类型

调用方需要在运行时替换实现？
  └─ 是：在消费位置定义小 interface

是在编写与具体业务实现无关的通用算法或容器？
  └─ 是：泛型 + 最小 constraint

类型集合必须封闭？
  └─ 是：包内受限 interface 或标签结构，并处理 default

只是为了复用代码？
  └─ 优先普通字段 + 委托；确实希望提升 method 时再 embedding
```

企业项目中常见的组合是：

```text
HTTP handler（具体 struct）
  → Application service（具体 struct）
    → 调用方定义的小 interface
      → MySQL / Redis / MQ adapter（具体 struct）
```

边界使用 interface 隔离变化，内部流程保留具体类型；没有替换需求的地方，不必为了“面向接口编程”提前创建抽象。

## 17. 常见误区与面试追问

### “Go 没有继承，所以不是面向对象语言”

面向对象的核心问题是数据与行为组织、封装、抽象和多态，不等于必须具有 class inheritance。Go 用 package、method、interface 和组合解决这些问题。

### “embedding 就是 Go 的继承”

不准确。embedding 会提升 method 或字段，但外层类型仍然持有一个内层值，没有建立传统父类/子类关系。需要增强行为时仍应显式实现 method 并委托。

### “有同名 method 就一定实现接口”

还要检查完整签名和方法集。指针 receiver 的 method 不在值类型的方法集中。

### “接口变量判断为非 nil，就一定可以安全调用”

错误。接口可能保存 typed nil 指针；还要从构造和返回路径上避免产生这种状态。

### “interface 是引用类型”

这个说法过于粗糙。interface 是保存动态类型和动态值的值；动态值本身可能是普通值，也可能是指针、map、slice 等带共享语义的值。讨论复制和并发时必须继续看具体动态值。

### “泛型会取代 interface”

不会。泛型解决的是一段代码适用于一组类型，interface value 解决的是运行时保存和替换不同实现。两者可以配合，但不是同一个问题。

### “用 `any` 最灵活”

`any` 是 `interface{}` 的预声明别名，调用方几乎得不到可用行为，往往需要反射或类型断言。能用具体类型、小接口或类型参数表达的约束，不要退化成 `any`。

### “interface 调用一定慢，泛型一定快”

性能取决于逃逸、内联、分配、调用路径和编译器实现，不能只从语法判断。业务边界先选清晰抽象，热点路径再通过 benchmark、`pprof` 和编译器诊断验证。

## 18. 练习：真正掌握 Go 多态

1. 实现 `EmailNotifier`、`SMSNotifier` 和 `NotifyFunc`，让三者都满足 `Notifier`。
2. 编写 `OrderService`，只依赖一个由它自己所在 package 定义的最小接口。
3. 把 `EmailNotifier.Send` 从值 receiver 改为指针 receiver，分别尝试把值和指针赋给 `Notifier`，解释编译结果。
4. 构造一个 `(*CountingNotifier)(nil)` 并赋给接口，打印 `%T`、`%v` 和 `interface == nil` 的结果。
5. 实现 `AuditedNotifier` 装饰器，在不修改原实现的情况下增加耗时和错误日志。
6. 分别用 `[]Notifier` 和 `SendAll[T Notifier]` 批量发送，说明异构集合与同类型参数的差别。
7. 设计一个只允许本 package 实现的 `Event`，再新增事件，观察 type switch 为什么不会触发穷举错误。
8. 为共享计数器实现并发测试，并使用 `go test -race` 检查数据竞争。

## 验收标准

- 能用未导出字段、构造函数和 method 维护不变量；
- 能解释隐式实现，以及为什么接口通常由消费方按最小需求定义；
- 能准确写出 `T` 与 `*T` 的方法集差异；
- 能解释 interface 的静态类型、动态类型和动态值；
- 能复现并修复 typed nil 问题；
- 能说明 embedding 为什么不是继承；
- 能根据场景选择 interface、函数类型、泛型或封闭事件建模；
- 能说明 interface 不承诺所有权、生命周期与并发安全；
- 能用组合、接口和泛型解释 Go 如何实现封装、抽象与多态。
