# Go：项目注意事项

这篇汇总 Go 项目中最容易被“小语言”表面简洁掩盖的语义。Go 代码容易写出来，但 slice 共享、interface nil、goroutine 生命周期和运行时容量必须主动设计。

## 值复制不等于完全独立

```go
first := Task{Tags: []string{"backend"}}
second := first
second.Tags[0] = "go" // first.Tags[0] 也改变
```

struct 赋值会复制字段，但 slice、map、pointer、channel 和 interface 字段复制后仍可能指向共享数据。对外返回内部 slice/map 时明确是否共享，必要时复制。

## slice 与 map

- slice 是地址、长度、容量组成的描述值；append 可能复用原数组，也可能重新分配。
- subslice 可能保留整个大数组，长期保存少量数据时主动 copy。
- nil slice 可读取和 append；nil map 可读取但写入会 panic。
- map 遍历顺序不是契约；需要稳定输出时排序键。
- 普通 map 并发读写不安全，使用锁、单一 goroutine 所有权或适合的并发结构。

## interface 的 nil 陷阱

```go
var pointer *MyError = nil
var err error = pointer
fmt.Println(err == nil) // false：interface 中仍有动态类型
```

interface 只有动态类型和动态值都为空时才等于 nil。返回 error 时不要把带 nil 指针的具体错误装入接口；API 边界要测试这一情况。

## goroutine 必须有生命周期

启动前回答四个问题：谁拥有、如何停止、谁等待、错误如何传播。

- context 作为第一个参数传递取消和截止时间，不存入长期 struct。
- 派生 context 后及时调用 cancel，释放 timer 和关联资源。
- channel 容量表达背压；不能无限创建 goroutine 代替排队。
- 通常由发送流程的拥有者关闭 channel；接收方不要随意关闭。
- ticker、timer、HTTP body、数据库 rows 和后台 worker 都要停止或关闭。

## defer 和资源

defer 在外围函数返回时执行。循环中不断 defer 会让所有资源积累到整个函数结束，单次迭代应提取为独立函数。持久化操作还要检查 flush/close 错误，不能只 defer 后忽略。

## 并发与运行时

- race detector 只能发现测试实际执行路径上的竞争，不是形式证明。
- mutex 保护一组业务不变量；atomic 只适合简单计数/状态转换。
- 不要复制已经使用过的 mutex、WaitGroup 等同步对象。
- goroutine 便宜但不是免费；持续观察数量、队列、block/mutex profile 和下游容量。
- GC 只回收不可达内存，不能清理 goroutine、连接和仍被缓存引用的对象。

## PR 必查

- [ ] struct/slice/map 复制后是否仍共享底层状态？
- [ ] interface 是否可能包含一个 nil 具体指针？
- [ ] 每个 goroutine 是否有停止、等待和错误路径？
- [ ] channel 的所有者、关闭方、容量和 consumer 退出行为是否明确？
- [ ] context 是否贯穿外部调用并设置总体截止时间？
- [ ] defer 是否在循环中积累，资源 close 错误是否需要处理？
- [ ] race、goroutine、heap、mutex/block profile 是否覆盖新增路径？
