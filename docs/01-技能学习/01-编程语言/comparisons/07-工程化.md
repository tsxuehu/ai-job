# 五门语言的工程化对比：把订单功能变成可交付服务

> 目标：通过同一个订单服务，看懂 C++、Go、Java、Node.js/TypeScript、Python 如何组织代码、构建依赖、测试、发布和生产运行。

统一项目包含：

```text
POST /orders              # 创建订单 API
OrderService              # 订单业务
OrderStore                # 存储接口
MySqlOrderStore           # MySQL 实现
orders migration          # 数据库迁移
unit/integration tests    # 自动化验证
API executable            # 可部署程序
logs/metrics/traces       # 生产观测
```

读完后应该能够：

1. 把同一个功能模块翻译成五门语言的惯用代码；
2. 看懂五种仓库、构建单元和依赖边界；
3. 说明源码如何经过测试、构建、发布，最终成为可运行服务；
4. 判断哪些工程目录和工具是当前项目真正需要的。

---

## 1. 工程化解决的是完整交付链

```text
功能代码
→ 模块边界
→ 构建和依赖
→ 配置与数据库迁移
→ 自动化测试
→ CI 生成制品
→ 部署发布
→ 日志、指标、Trace 和告警
→ 优雅停机与故障恢复
```

只有目录没有自动化，不叫工程化；只有 CI 没有代码边界，也无法长期维护。

工程化的最终目标是：

> 任何成员都能用可重复的方式修改、验证、构建、发布和排查这个服务。

## 2. 同一个订单模块，五门语言如何表达

共同关系：

```text
HTTP Handler
    │ CreateOrder(command)
    ▼
OrderService
    │ Save(orderID, total)
    ▼
OrderStore 接口
    ▲
    │ 实现
MySqlOrderStore
```

`OrderService` 只依赖存储能力，不直接创建 MySQL 连接。启动代码负责把具体实现传进去。

### 2.1 C++

```cpp
class OrderStore {
public:
    virtual ~OrderStore() = default;
    virtual void save(OrderId id, Money total) = 0;
};

class OrderService {
public:
    explicit OrderService(OrderStore& store) : store_(store) {}
    OrderId create(const CreateOrderCommand& command);

private:
    OrderStore& store_;
};

MySqlOrderStore store{database};
OrderService service{store};
```

- 抽象基类表达接口；
- 公共头文件表达可用 API；
- 引用表示 service 不拥有 store，启动代码必须保证生命周期；
- CMake target 控制可见头文件和链接依赖。

### 2.2 Go

```go
type orderStore interface {
    Save(context.Context, OrderID, Money) error
}

type Service struct {
    store orderStore
}

func NewService(store orderStore) *Service {
    return &Service{store: store}
}

store := mysql.NewStore(db)
service := order.NewService(store)
```

- interface 由使用它的订单 package 定义；
- MySQL 类型只要方法匹配就自动实现接口；
- 大写名字对包外公开，小写名字仅包内可见；
- `cmd/api` 负责创建并组装对象。

### 2.3 Java

```java
public interface OrderStore {
    void save(OrderId id, Money total);
}

public final class OrderService {
    private final OrderStore store;

    public OrderService(OrderStore store) {
        this.store = store;
    }
}

OrderStore store = new MySqlOrderStore(dataSource);
OrderService service = new OrderService(store);
```

- `interface` 和 `implements` 显式建立类型关系；
- `public`、package-private 和构建模块共同控制边界；
- Spring 可以负责组装，但业务代码不主动查询容器；
- Maven/Gradle module 可以强化稳定的模块依赖。

### 2.4 Node.js / TypeScript

```ts
interface OrderStore {
  save(id: OrderId, total: Money): Promise<void>;
}

class OrderService {
  constructor(private readonly store: OrderStore) {}
}

const store = new MySqlOrderStore(database);
const service = new OrderService(store);
```

- interface 按对象形状检查，编译后通常不存在；
- ES module 的 `export` 决定源码入口；
- `package.json#exports` 和 lint 防止深层导入；
- `main.ts` 或 bootstrap 负责运行时组装。

### 2.5 Python

```python
class OrderStore(Protocol):
    async def save(self, order_id: OrderId, total: Money) -> None: ...

class OrderService:
    def __init__(self, store: OrderStore) -> None:
        self._store = store

store = MySqlOrderStore(database)
service = OrderService(store)
```

- Protocol 帮助静态检查，运行时仍是鸭子类型；
- `__init__.py` 选择 package 的公开入口；
- `_name` 表示内部实现，但主要依靠约定和工具；
- entrypoint/bootstrap 负责组装。

### 2.6 代码形式快速对照

| 语言 | 功能模块 | 公开入口 | 内部实现 | 依赖接口 |
|---|---|---|---|---|
| C++ | CMake target、namespace | 公共 `.h` | 私有 `.cpp`/头文件 | 抽象基类 |
| Go | package | 大写标识符 | 小写标识符、`internal` | interface 隐式实现 |
| Java | package/build module | `public` API | package-private/private | interface 显式实现 |
| Node.js/TS | ES module/workspace package | `export`/`exports` | 不导出、禁止深层 import | 结构接口 |
| Python | package/distribution | `__init__.py`/`__all__` | `_name` 和内部文件 | Protocol/鸭子类型 |

## 3. 同一个订单服务，仓库如何组织

目录没有统一答案。下面展示每门语言最自然的起点。

### 3.1 C++：target 是主要工程边界

```text
repository/
├── CMakeLists.txt
├── CMakePresets.json
├── apps/api/main.cpp
├── libs/order/
│   ├── CMakeLists.txt
│   ├── include/company/order/
│   ├── src/
│   └── tests/
├── adapters/order_mysql/
├── migrations/
└── tests/integration/
```

外部 target 只看到公共头文件；`apps/api` 同时链接订单核心和 MySQL adapter 完成组装。

### 3.2 Go：先使用一个 module，按 package 分边界

```text
repository/
├── go.mod
├── go.sum
├── cmd/api/main.go
├── cmd/worker/main.go
├── internal/
│   ├── order/
│   │   ├── service.go
│   │   └── mysql/
│   └── platform/
├── migrations/
└── tests/
```

业务 package 放 `internal`；项目确实需要独立版本和发布时，才考虑拆多个 `go.mod`。

### 3.3 Java：先 package by feature

```text
repository/
├── gradlew / mvnw
├── build.gradle.kts / pom.xml
└── src/
    ├── main/java/com/company/app/
    │   ├── order/
    │   ├── inventory/
    │   └── bootstrap/
    └── test/java/com/company/app/
```

边界稳定且需要编译级限制时，再拆 `order-domain`、`order-application`、adapter 和 boot module。

### 3.4 Node.js / TypeScript：先单 package

```text
repository/
├── package.json
├── lockfile
├── tsconfig.json
├── src/
│   ├── main.ts
│   └── modules/order/
│       ├── index.ts
│       ├── order-service.ts
│       └── mysql-store.ts
└── tests/
```

出现多个应用、独立构建或发布需求后，再升级成 `apps + packages` workspace。

### 3.5 Python：src layout + package API

```text
repository/
├── pyproject.toml
├── lockfile
├── src/company_app/
│   ├── entrypoints/api.py
│   └── modules/order/
│       ├── __init__.py
│       ├── service.py
│       └── _mysql_store.py
└── tests/
```

`src layout` 能减少从仓库根目录意外导入源码的问题；公开 API 通过 package 入口表达。

## 4. 构建、依赖和制品对比

| 语言 | 构建入口 | 依赖与锁定 | 常见可交付制品 |
|---|---|---|---|
| C++ | CMake Presets、Ninja/构建器 | Conan、vcpkg 或团队方案，固定工具链 | 可执行文件、动态/静态库、容器镜像 |
| Go | `go build/test` | `go.mod`、`go.sum` | 可执行文件、容器镜像 |
| Java | Maven/Gradle Wrapper | POM/Gradle + 版本平台和锁定策略 | JAR、容器镜像 |
| Node.js/TS | package scripts + `tsc`/构建器 | npm/pnpm/yarn lockfile | JavaScript `dist`、依赖、容器镜像 |
| Python | `pyproject.toml` 构建前端 | lockfile + Python 包索引 | wheel、源码包、容器镜像 |

工程要求：

- 新机器只根据仓库文件就能完成构建；
- 编译器/运行时、依赖和生成工具版本可追踪；
- CI 与本地使用相同的主要入口；
- 生产制品由 CI 构建一次，环境间提升同一个不可变制品；
- 不把开发机上偶然存在的全局依赖当成构建条件。

## 5. 配置和密钥

订单服务需要数据库地址、连接池大小和支付超时。

推荐流程：

```text
环境变量/配置文件
→ 启动时一次性读取
→ 校验必填项、类型、范围和单位
→ 生成只读 Config
→ 只把所需片段传给具体模块
```

| 语言 | 配置对象常见形式 |
|---|---|
| C++ | 明确的 `Config` struct，启动阶段解析并校验 |
| Go | 配置 struct，`main` 加载后传入构造函数 |
| Java | 类型化配置对象，boot/config package 绑定 |
| Node.js/TS | 运行时 schema 校验后形成只读对象 |
| Python | 配置模型/schema 校验后显式注入 |

禁止：

- 业务代码到处读取环境变量；
- 配置非法时继续启动；
- 把密码、Token 和私钥提交仓库；
- 使用没有单位的 `timeout: 30`；
- 修改全局可变配置导致请求行为不可预测。

## 6. 数据库迁移和跨系统契约

数据库 schema 和 HTTP/事件格式都属于可发布内容。

```text
contracts/          # OpenAPI、事件 schema、RPC IDL
migrations/         # 数据库变更
generated/          # 确需提交时保存生成产物
```

共同规则：

- 已在共享环境执行的 migration 不随意修改；
- 不兼容字段使用 expand → backfill → contract 演进；
- 应用新旧版本在发布窗口内都能工作；
- OpenAPI、事件和生成代码有固定工具入口；
- 兼容性进入自动化测试；
- 生产 migration 是发布步骤，不由每个应用实例无条件抢跑。

五门语言的语法不同，但数据库兼容问题完全相同。

## 7. 测试和代码质量

### 测试分层

| 测试 | 订单案例 | 是否需要真实基础设施 |
|---|---|---|
| 单元测试 | 金额计算、订单状态、OrderService + FakeStore | 否 |
| adapter 测试 | MySqlOrderStore 的 SQL 和映射 | 是，使用真实数据库语义 |
| 集成测试 | API → Service → MySQL | 是 |
| 契约测试 | OpenAPI、事件兼容 | 视情况 |
| E2E | 创建订单关键用户流程 | 是 |
| 性能测试 | 固定负载下 P95/P99 和容量 | 是 |

### 工具入口

| 语言 | 格式/静态检查 | 测试入口 |
|---|---|---|
| C++ | clang-format、编译器警告、clang-tidy、sanitizer | CTest + 所选测试框架 |
| Go | gofmt、go vet、静态检查、race detector | `go test` |
| Java | 编译检查、格式/lint、架构规则 | Maven/Gradle + JUnit |
| Node.js/TS | TypeScript、ESLint、格式检查 | node:test、Vitest/Jest 等统一一种主路径 |
| Python | Ruff/格式、类型检查 | pytest 等统一入口 |

测试不应全部启动完整框架。核心业务测试应该快、确定，并且不依赖网络和数据库。

## 8. CI/CD 和发布

推荐流水线：

```text
格式与静态检查
→ 单元测试
→ 构建不可变制品
→ 依赖/安全与制品信息
→ adapter、集成、契约和 migration 测试
→ 部署 QA
→ 冒烟测试
→ 灰度/渐进发布
→ 根据错误率、延迟和业务指标完成或回滚
```

每个制品至少能追踪：

- Git commit；
- 编译器或运行时版本；
- 依赖锁定信息；
- 构建选项；
- migration 版本；
- 镜像/二进制/JAR/wheel 的摘要。

回滚不能假设数据库 schema 可以瞬间回退。应用和 migration 必须设计兼容窗口。

## 9. 可观测性、健康检查和优雅停机

每个服务至少提供：

```text
结构化日志：发生了什么，关联 order_id 和 trace_id
指标：请求量、错误率、P95/P99、连接池和队列容量
Trace：一次请求跨数据库、消息和外部支付的路径
liveness：进程是否需要重启
readiness：当前是否能安全接收流量
runbook：告警后怎样判断、止损和恢复
```

关闭顺序：

```text
收到 SIGTERM/停止信号
→ readiness 变为不可接流量
→ 停止接收新请求和新任务
→ 取消后台任务
→ 在期限内等待正在执行的工作
→ 刷新日志/Trace
→ 关闭连接池和网络资源
→ 退出进程
```

语言落点：

| 语言 | 生命周期管理重点 |
|---|---|
| C++ | signal、线程/协程停止、RAII 析构顺序和对象生命周期 |
| Go | 根 context、signal、goroutine wait、连接池关闭 |
| Java | Spring/JVM 生命周期、Executor、虚拟线程任务和连接池 |
| Node.js/TS | SIGTERM、AbortController、server/Stream/Worker/handle |
| Python | signal、asyncio TaskGroup、取消传播、client/pool context |

“进程退出了”不等于“优雅停机完成了”。必须验证任务没有丢、连接没有泄漏、超时后能强制结束。

## 10. 项目从小到大怎么演进

| 阶段 | 推荐做法 |
|---|---|
| 练习/原型 | 一个入口、按业务分目录、基础测试 |
| 生产单体 | 模块边界、迁移、配置、观测和 CI/CD |
| 模块化单体 | 构建规则强化依赖，API/Worker 可分进程 |
| 独立服务 | 业务、数据、部署、容量和团队责任都已稳定 |

各语言强化边界的动作：

- C++：拆清晰的 CMake target；
- Go：先拆 package，独立发布时才拆 module；
- Java：从 package by feature 演进到多构建模块；
- Node.js/TS：从单 package 演进到 workspace；
- Python：从单 distribution 内多 package 演进到少量独立 distribution。

不要因为目录变多就拆微服务。网络、数据一致性、部署和排障成本会同时增加。

## 11. 常见错误

- 全局 `controllers/services/repositories/models`，一个订单需求跑遍整个仓库；
- 目录分开了，所有模块仍能深层 import 内部文件；
- `common/utils` 成为所有业务的垃圾场；
- 业务代码主动创建数据库、HTTP client 或读取全局配置；
- 每个小目录都拆成构建模块或 package；
- 只写单元测试，不验证真实 SQL、迁移和协议；
- CI 在不同环境重新构建，产物不可追踪；
- 发布成功只看 Pod 存活，不看错误率、延迟和业务指标；
- 后台任务没有取消、等待和关闭路径；
- 把语言框架的默认行为当成明确的工程约定。

## 12. 工程化验收清单

### 代码与依赖

- [ ] 订单模块有明确职责、公开入口和内部实现；
- [ ] 业务代码不依赖具体数据库、Web 框架和全局容器；
- [ ] 构建或 lint 能发现禁止的依赖和深层导入；

### 构建与测试

- [ ] 新环境能够根据锁文件和固定入口完成构建；
- [ ] 单元、adapter、集成、契约和性能测试职责清楚；
- [ ] CI 只发布通过验证的不可变制品；

### 数据与发布

- [ ] 配置启动时完整校验，密钥不进入仓库；
- [ ] migration 和契约有兼容、测试和发布策略；
- [ ] 制品可追踪到源码、工具链、依赖和构建选项；

### 生产运行

- [ ] 日志、指标、Trace、健康检查和告警能够定位订单失败；
- [ ] API、Worker 和后台任务都支持超时、取消和优雅停机；
- [ ] 发布能够根据技术和业务指标继续、暂停或回滚。

## 13. 面试时怎么回答

> 我会先用模块化单体实现订单服务：按订单业务聚合代码，公开最小 API，通过 OrderStore 隔离数据库，启动入口负责组装。然后用语言自己的构建边界约束依赖，例如 CMake target、Go package/internal、Java build module、Node exports/workspace 或 Python package API。工程上再补齐可复现依赖、分层测试、配置校验、数据库迁移、CI 不可变制品、渐进发布、可观测性和优雅停机。只有业务、数据和部署边界稳定且收益明确时，才拆独立服务。

这个回答同时覆盖代码、构建、测试、交付和生产运行，而不只是背目录树。
