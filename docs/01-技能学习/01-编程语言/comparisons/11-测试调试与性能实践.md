# 五门语言的测试、调试与性能实践：证明订单规则正确

> 目标：用同一个“非法金额必须失败”的规则，对比测试代码、故障定位和性能验证入口。

## 1. 工具快速对照

| 语言 | 测试入口 | 并发/内存检查 | 性能入口 |
|---|---|---|---|
| C++ | Catch2/GoogleTest/项目框架 | ASan、UBSan、TSan | release benchmark、perf/平台 profiler |
| Go | `go test` | `-race`、fuzz | benchmark、pprof、trace |
| Java | JUnit | JVM 工具、并发测试 | JMH、JFR、async-profiler |
| Node.js/TS | node:test/Vitest/Jest | handle 检查、heap snapshot | CPU profile、event-loop 指标 |
| Python | unittest/pytest | Task/线程检查、tracemalloc | pytest-benchmark、cProfile/采样 profiler |

测试框架名称不是重点。每门语言都要覆盖：正常、边界、错误、取消、资源清理和真实基础设施语义。

## 2. 同一个规则测试

### C++

```cpp
TEST_CASE("rejects non-positive amount") {
    const auto result = Order::create(OrderId{1}, Money{0});
    REQUIRE(result.error() == OrderError::invalid_amount);
}
```

### Go

```go
func TestNewOrderRejectsInvalidAmount(t *testing.T) {
	_, err := NewOrder("o-1", 0)
	if !errors.Is(err, ErrInvalidAmount) {
		t.Fatalf("got %v", err)
	}
}
```

### Java

```java
@Test
void rejectsNonPositiveAmount() {
    assertThrows(InvalidAmountException.class,
        () -> Order.create(new OrderId("o-1"), Money.ZERO));
}
```

### Node.js / TypeScript

```ts
test("rejects non-positive amount", () => {
  assert.throws(
    () => Order.create("o-1", 0),
    InvalidAmountError,
  );
});
```

### Python

```python
def test_rejects_non_positive_amount() -> None:
    with pytest.raises(InvalidAmountError):
        Order.create("o-1", 0)
```

测试应断言稳定语义，而不是完整错误文本、内部私有字段或框架调用次数。

## 3. 测试分层

| 层次 | 验证什么 | 是否使用真实外部依赖 |
|---|---|---|
| 单元 | 值对象、状态机、纯函数、application 用例 | 否 |
| adapter/组件 | SQL、JSON、HTTP、Stream、错误映射 | 通常使用真实协议或轻量容器 |
| 契约 | OpenAPI、事件、RPC 与调用方兼容 | 使用 schema/消费者契约 |
| 集成 | API → 业务 → 数据库/队列 | 是 |
| E2E | 少量关键用户流程和部署配置 | 是 |

Mock 只隔离稳定边界，不要用几百个 mock 复刻 ORM、网络库或框架内部行为。

## 4. 调试顺序

```text
稳定复现
→ 保存输入、版本和配置
→ 看错误链与调用栈
→ 看线程/goroutine/Task 和资源状态
→ 用 profiler 或内存工具找证据
→ 做最小修改
→ 增加回归测试
```

- 崩溃/异常：先看最早有业务意义的栈帧和 cause 链。
- 卡住：看锁、线程、goroutine、Task、连接池和队列。
- 内存增长：区分语言堆、native/Buffer、缓存和业务资源。
- 变慢：同时看 P95/P99、CPU、IO、锁、GC 和下游等待。

## 5. 性能测试必须说明什么

- 语言、运行时、构建模式和依赖版本。
- 机器、数据规模、并发和预热方式。
- 吞吐、P50/P95/P99、错误率与资源占用。
- 正确性检查，避免优化后结果已经错误。
- 变更前后使用相同环境，且一次只改变一个因素。

不要用 Debug C++、未预热 JVM、热更新 Node 或带调试器的 Python 得出语言性能排名。

## 6. 面试怎么问

**单元测试为什么不能证明 SQL 正确？** Mock 不具备真实数据库的事务、锁、索引、类型转换和方言语义，adapter 必须有真实集成测试。

**覆盖率高为什么仍可能质量差？** 覆盖率只说明代码被执行，不能证明断言有效、边界完整、并发安全或错误路径正确。

**性能优化第一步是什么？** 固定负载并建立基线，然后用 profile 找最大瓶颈；不能先凭感觉重写。
