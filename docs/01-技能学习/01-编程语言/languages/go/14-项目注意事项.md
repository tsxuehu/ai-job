# Go：项目注意事项

这篇汇总 Go 项目中最容易被“小语言”表面简洁掩盖的语义。Go 代码容易写出来，但 slice 共享、interface nil、goroutine 生命周期和运行时容量必须主动设计。

## 1. 值复制不等于完全独立

```go
first := Task{Tags: []string{"backend"}}
second := first
second.Tags[0] = "go" // first.Tags[0] 也改变
```

struct 赋值会复制字段，但 slice、map、pointer、channel 和 interface 字段复制后仍可能指向共享数据。对外返回内部 slice/map 时明确是否共享，必要时复制。

## 2. slice 与 map

- slice 是地址、长度、容量组成的描述值；append 可能复用原数组，也可能重新分配。
- subslice 可能保留整个大数组，长期保存少量数据时主动 copy。
- nil slice 可读取和 append；nil map 可读取但写入会 panic。
- map 遍历顺序不是契约；需要稳定输出时排序键。
- 普通 map 并发读写不安全，使用锁、单一 goroutine 所有权或适合的并发结构。

## 3. interface 的 nil 陷阱

```go
var pointer *MyError = nil
var err error = pointer
fmt.Println(err == nil) // false：interface 中仍有动态类型
```

interface 只有动态类型和动态值都为空时才等于 nil。返回 error 时不要把带 nil 指针的具体错误装入接口；API 边界要测试这一情况。

## 4. goroutine 必须有生命周期

启动前回答四个问题：谁拥有、如何停止、谁等待、错误如何传播。

- context 作为第一个参数传递取消和截止时间，不存入长期 struct。
- 派生 context 后及时调用 cancel，释放 timer 和关联资源。
- channel 容量表达背压；不能无限创建 goroutine 代替排队。
- 通常由发送流程的拥有者关闭 channel；接收方不要随意关闭。
- ticker、timer、HTTP body、数据库 rows 和后台 worker 都要停止或关闭。

## 5. defer 和资源

defer 在外围函数返回时执行。循环中不断 defer 会让所有资源积累到整个函数结束，单次迭代应提取为独立函数。持久化操作还要检查 flush/close 错误，不能只 defer 后忽略。

## 6. 并发与运行时

- race detector 只能发现测试实际执行路径上的竞争，不是形式证明。
- mutex 保护一组业务不变量；atomic 只适合简单计数/状态转换。
- 不要复制已经使用过的 mutex、WaitGroup 等同步对象。
- goroutine 便宜但不是免费；持续观察数量、队列、block/mutex profile 和下游容量。
- GC 只回收不可达内存，不能清理 goroutine、连接和仍被缓存引用的对象。

## 7. 反射、代码生成与 cgo

- `reflect` 会绕过部分静态类型帮助，集中在序列化、框架或 adapter 边界，并测试无效类型和值。
- `go generate` 不是 `go build` 自动步骤；生成工具、命令、输入和产物必须可复现。
- build tag 会让不同平台编译不同源码，CI 至少验证生产目标平台。
- cgo 引入 C 所有权、线程、ABI、交叉编译和阻塞边界；普通业务核心不直接传播 C 类型。

## 8. 安全专项

- HTTP client 校验协议、主机、端口和重定向，防止用户 URL 变成 SSRF。
- 文件和压缩包路径清理后仍要验证位于允许根目录，不能只调用 `filepath.Clean`。
- 使用参数化 SQL；执行外部命令时传参数数组，不拼接 shell 命令。
- 请求体、JSON 数组、压缩数据、goroutine 和队列都有总量上限。
- 固定 module 和工具依赖，审查新增依赖、生成代码与二进制来源。

## 9. PR 必查

- [ ] struct/slice/map 复制后是否仍共享底层状态？
- [ ] interface 是否可能包含一个 nil 具体指针？
- [ ] 每个 goroutine 是否有停止、等待和错误路径？
- [ ] channel 的所有者、关闭方、容量和 consumer 退出行为是否明确？
- [ ] context 是否贯穿外部调用并设置总体截止时间？
- [ ] defer 是否在循环中积累，资源 close 错误是否需要处理？
- [ ] race、goroutine、heap、mutex/block profile 是否覆盖新增路径？
- [ ] URL、路径、命令参数和输入总量是否受 allowlist 与上限约束？

## 10. 用生产故障反推规则

### 10.1 只缓存 1 KB，进程却多保留了几百 MB

```go
func header(data []byte) []byte {
    return data[:1024]
}
```

返回的小 slice 仍引用原来的大数组，GC 不能回收大数组。长期保存前复制需要的数据：

```go
result := append([]byte(nil), data[:1024]...)
```

不要看到 RSS 高就断言“GC 泄漏”；先用 heap profile 找到被谁保留。

### 10.2 流量翻倍后，下游先崩溃

```go
for _, order := range orders {
    go process(order)
}
```

输入量直接变成 goroutine 和下游并发量，没有背压。改成固定 worker、semaphore 或有界队列，并为排队、拒绝、超时定义指标。goroutine 便宜不代表下游容量无限。

### 10.3 HTTP 延迟逐渐升高，连接复用率下降

成功请求只解码了部分响应，又没有正确关闭 Body。连接无法按预期复用，最终大量时间消耗在建连和等待上。取得 `resp` 后立即安排 `resp.Body.Close()`，并按协议读取、限制或丢弃剩余内容。

### 10.4 具体错误指针是 nil，`err == nil` 却是 false

根因通常是 interface 中装入了 nil 具体指针。先分别打印具体类型和值：

```go
fmt.Printf("type=%T value=%v nil=%v\n", err, err, err == nil)
```

修复位置通常在返回边界：没有错误就直接 `return nil`，不要返回一个类型为 `*MyError`、值为 nil 的变量。

### 10.5 发布期间进程已退出，任务只执行了一半

只监听信号并调用 `cancel()` 不够。入口必须停止接收新任务、取消根 context、等待 worker 返回，并在总关闭期限内按顺序关闭连接。测试要验证“收到取消”与“已经退出”是两个不同事件。

## 11. 专家级动手题

1. 写一个故意保留大数组的缓存，用 heap profile 找到保留路径，再复制小片段验证改善；
2. 给订单批处理加入有界并发，压测不同 worker 数，解释吞吐、延迟和下游连接池的关系；
3. 构造带 nil 指针的 `error`，用 interface 的动态类型/动态值解释比较结果；
4. 写一个关闭不完整的 worker，再用 goroutine profile 和停机测试找到阻塞点；
5. 为用户提供的 URL、压缩包和 SQL 查询分别列出输入、资源和时间上限；
6. 审查一次真实 PR：每个 goroutine、channel、timer、Body、Rows 和 Tx 都标出拥有者与结束路径。

## 12. 掌握标准

- [ ] 看到 slice、map、pointer 或 interface 复制时，能判断实际数据是否共享；
- [ ] 每个 goroutine 都能回答谁启动、谁停止、谁等待、错误给谁；
- [ ] 每个外部输入和下游调用都有大小、并发、时间和资源上限；
- [ ] 能用 race、heap、goroutine、mutex/block profile 证明判断；
- [ ] 能把一次生产故障沉淀为测试、指标、代码规则或发布检查，而不只修当前症状。
