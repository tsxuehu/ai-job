# Go：从订单请求看内存与资源生命周期

Go 的 GC 只管理普通内存，不会替你完成 HTTP body、文件、数据库事务、goroutine 和 ticker 的业务生命周期。本章把“对象是否可达”和“资源是否正确关闭”分开讲。

## 1. 先区分内存和业务资源

| 对象/资源 | 谁管理普通内存 | 谁完成业务关闭 |
| --- | --- | --- |
| `Order`、slice、map | Go GC | 通常不需要显式释放内存 |
| 文件 | Go GC 管包装对象 | 代码调用 `Close` |
| HTTP response body | Go GC 管包装对象 | 代码关闭并按需要读完 body |
| `sql.Rows`、事务 | Go GC 管包装对象 | 代码 Close/Commit/Rollback |
| goroutine | runtime 管调度结构 | goroutine 自己 return，创建者取消并等待 |
| timer/ticker | runtime 管内部对象 | 不再使用时停止或取消关联 context |

GC 的问题是“对象还能不能从根引用到达”；资源管理的问题是“协议和业务是否已经完成”。两者不是一回事。

## 2. 一个请求中的生命周期

```go
func LoadInventory(ctx context.Context, client *http.Client, url string) error {
	req, err := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
	if err != nil {
		return err
	}

	resp, err := client.Do(req)
	if err != nil {
		return err
	}
	defer resp.Body.Close()

	_, err = io.Copy(io.Discard, io.LimitReader(resp.Body, 1<<20))
	return err
}
```

生命周期是：

```text
创建 request
→ client 发起 IO
→ 获得 response/body
→ 函数取得关闭责任
→ 读取受限内容
→ defer 关闭 body
→ 函数返回
```

忘记关闭不是普通 Go 对象“没 free”，而是连接复用、文件描述符和下游资源可能不能及时恢复。

## 3. 栈、堆与逃逸

源码不直接指定栈或堆：

```go
func localAmount() int64 {
	amount := int64(100)
	p := &amount
	return *p
}
```

虽然取得了地址，指针没有离开函数，编译器可能把值放在栈/寄存器或消除对象。

```go
func newOrder() *Order {
	order := Order{ID: "order-1"}
	return &order
}
```

返回后仍需要使用该值，它通常会逃逸到堆。Go 保证指针有效，编译器决定实现位置：

```bash
go build -gcflags="-m=2" ./...
```

不要把“指针更快”当规则。指针可能减少大对象复制，也可能导致逃逸、额外间接访问、共享状态和 GC 压力。

## 4. GC 看的是可达性

可以从全局变量、当前 goroutine 栈、运行时结构等继续找到的对象仍然可达，不能回收：

```go
var cache = map[string][]byte{}

func remember(id string, payload []byte) {
	cache[id] = payload
}
```

只要 cache 不删除条目，payload 就仍然可达。这是逻辑泄漏，不是 GC 算法失灵。

常见保留路径：

- 无上限 map/cache；
- goroutine 栈仍引用大对象；
- closure 捕获请求对象；
- subslice 保留整个大数组；
- listener、timer 和回调仍被注册；
- interface 字段继续持有动态值。

heap profile 的关键不是“哪个类型最大”，而是“谁仍然引用它”。

## 5. struct 复制后可能仍然共享

```go
type Order struct {
	ID   string
	Tags []string
}

first := Order{ID: "order-1", Tags: []string{"backend"}}
second := first
second.Tags[0] = "go"

fmt.Println(first.Tags[0]) // go
```

外层 Order 被复制，slice 描述值也被复制，但两者仍指向同一个数组。map、pointer、channel、function 和 interface 字段也可能继续共享内部状态。

API 返回内部 slice/map 前必须决定：

- 明确共享并由调用方遵守只读约定；
- 返回克隆；
- 暴露更窄的查询方法；
- 转移所有权并让原对象不再使用。

## 6. `defer` 管理函数级资源

成功获取资源后立即注册清理：

```go
file, err := os.Open(path)
if err != nil {
	return err
}
defer file.Close()
```

但 defer 在当前函数返回时执行。大循环中反复 defer 会积累资源：

```go
func processOne(path string) error {
	file, err := os.Open(path)
	if err != nil {
		return err
	}
	defer file.Close()
	return decode(file)
}
```

把一次迭代提取成函数，让资源及时关闭。

写文件、flush、事务提交等结束阶段可能失败，不能总是忽略：

```go
func write(path string, data []byte) (err error) {
	file, err := os.Create(path)
	if err != nil {
		return err
	}
	defer func() { err = errors.Join(err, file.Close()) }()

	_, err = file.Write(data)
	return err
}
```

## 7. goroutine 也是资源

```go
go watchOrders(ctx)
```

它至少占用栈、调度状态，并可能持有对象、timer、连接或锁。创建者必须回答：

```text
创建多少？
谁发取消？
阻塞在哪里？
谁等待结束？
错误和 panic 去哪里？
停机时能否返回？
```

goroutine 泄漏常常同时表现为 goroutine 数、heap、连接数和延迟上涨。

## 8. 内存优化的正确顺序

```text
定义服务目标
→ 稳定复现
→ 看 alloc/op、heap、GC 和尾延迟
→ 找到分配/保留路径
→ 修改算法或生命周期
→ 重新验证正确性和指标
```

常见优先级：减少无用工作和大对象存活时间，避免重复序列化/转换，批量或流式处理，再考虑复用缓冲。`sync.Pool` 只用于 profile 证明的高频临时对象，且必须清理敏感残留。

## 9. 与其他语言对照

| 语言经验 | Go 中要注意 |
| --- | --- |
| Java/Python GC | 同样只回收不可达内存，不关闭业务资源 |
| C++ RAII | Go 没有析构函数，资源责任通常用 defer/Close 表达 |
| Node.js listener/timer 泄漏 | Go goroutine/timer/cache 也会形成逻辑泄漏 |
| C++ 栈对象取地址危险 | Go 可安全返回局部变量指针，编译器处理逃逸 |
| Java 所有对象引用语义 | Go struct 是值，外层复制与内部共享要分别判断 |

## 10. 动手验证

1. 编译两个取地址示例，使用 `-gcflags="-m=2"` 对比逃逸报告。
2. 用 subslice 保留大数组，再复制小片段，对比 heap profile。
3. 启动无法退出的 goroutine 并持有大 slice，观察 goroutine/heap 增长。
4. 在循环中 defer 打开文件，再提取小函数比较资源释放时间。
5. 对包含 slice 和 map 字段的 struct 做复制，画出共享关系。

## 11. 掌握标准

- 能区分 GC 管理的普通内存和必须主动结束的业务资源。
- 能根据可达性解释缓存、goroutine、closure 和 subslice 泄漏。
- 能使用逃逸报告、benchmark 和 heap/goroutine profile，而不是猜栈堆。
- 能设计 defer、Close、Commit/Rollback 和 goroutine 的完整生命周期。
- 能识别外层值复制后仍共享内部状态的情况。
