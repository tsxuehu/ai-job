# Go：测试、调试与性能实践

> 目标：不只会写 `*_test.go`，还要能用证据回答三个问题：功能是否正确、并发是否安全、性能瓶颈在哪里。

统一场景：测试一个订单结算服务。它校验订单、调用支付接口，并保存支付结果。

## 1. 先按风险选择测试

| 风险 | 首选手段 | 要证明什么 |
| --- | --- | --- |
| 金额、状态转换 | 单元测试 | 输入与业务结果正确 |
| 支付接口调用 | fake + 单元测试 | 参数、错误传播、状态变更正确 |
| SQL、事务、HTTP 协议 | 集成测试 | 与真实基础设施的行为一致 |
| 多 goroutine 共享状态 | `go test -race` | 执行到的路径没有数据竞争 |
| 解析任意外部输入 | fuzz | 不 panic、不死循环、不失控分配 |
| 延迟、吞吐、分配 | benchmark + profile | 瓶颈由数据证明 |
| 超时、停机、泄漏 | 生命周期测试 | goroutine 和资源能按时退出 |

测试数量不是目标。每个测试都应对应一个可能造成业务损失或生产故障的风险。

## 2. 表驱动单元测试

Go 通常把“同一规则的多组输入”写成表：

```go
func TestNewOrder(t *testing.T) {
    tests := []struct {
        name        string
        amountCents int64
        wantErr     error
    }{
        {name: "valid", amountCents: 100},
        {name: "zero", amountCents: 0, wantErr: ErrInvalidAmount},
        {name: "negative", amountCents: -1, wantErr: ErrInvalidAmount},
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            _, err := NewOrder("order-1", tt.amountCents)
            if !errors.Is(err, tt.wantErr) {
                t.Fatalf("NewOrder() error = %v, want %v", err, tt.wantErr)
            }
        })
    }
}
```

这里有三层结构：

1. `tests` 是测试数据；
2. `t.Run` 为每一行创建有名字的子测试；
3. 断言只比较调用者真正依赖的行为。

错误存在包装链时使用 `errors.Is` 或 `errors.As`，不要比较完整错误文本。错误文本适合人读，不是稳定协议。

## 3. 用小接口隔离外部依赖

生产代码只声明自己需要的能力：

```go
type PaymentGateway interface {
    Pay(ctx context.Context, orderID string, amountCents int64) (PaymentReceipt, error)
}
```

测试提供一个最小 fake：

```go
type paymentGatewayFunc func(
    context.Context,
    string,
    int64,
) (PaymentReceipt, error)

func (f paymentGatewayFunc) Pay(
    ctx context.Context,
    orderID string,
    amountCents int64,
) (PaymentReceipt, error) {
    return f(ctx, orderID, amountCents)
}
```

测试成功路径：

```go
func TestCheckoutMarksOrderPaid(t *testing.T) {
    order, err := NewOrder("order-1", 100)
    if err != nil {
        t.Fatal(err)
    }

    gateway := paymentGatewayFunc(func(
        ctx context.Context,
        orderID string,
        amountCents int64,
    ) (PaymentReceipt, error) {
        if orderID != "order-1" || amountCents != 100 {
            t.Fatalf("unexpected payment: id=%q amount=%d", orderID, amountCents)
        }
        return PaymentReceipt{ID: "payment-1"}, nil
    })

    if err := Checkout(context.Background(), order, gateway); err != nil {
        t.Fatal(err)
    }
    if order.Status() != StatusPaid {
        t.Fatalf("status = %q, want %q", order.Status(), StatusPaid)
    }
}
```

这不是为了模拟整个支付 SDK，而是只控制本次用例的输入和输出。SQL、事务隔离、序列化格式等实现行为不能靠 fake 证明，必须使用真实依赖做集成测试。

## 4. package 内测还是黑盒测试

```text
order/order_test.go          package order
order/order_public_test.go   package order_test
```

- `package order`：能访问未导出标识符，适合验证复杂内部算法；
- `package order_test`：只能使用公开 API，能发现 API 难用、耦合或遗漏；
- 一个项目可以同时使用两种，但默认优先测试公开行为。

不要为了测试把所有字段和函数都改为导出。那会扩大生产 API，只为测试制造永久成本。

## 5. 集成测试验证真实边界

数据库集成测试至少验证：

- schema、SQL 和 `Scan` 类型是否匹配；
- 唯一约束、外键和事务回滚是否生效；
- context 取消后驱动是否真的停止；
- 连接是否归还连接池。

HTTP 集成测试可用 `httptest.Server` 启动真实 HTTP 协议端点：

```go
func TestInventoryClient(t *testing.T) {
    server := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        if r.URL.Path != "/inventory/order-1" {
            http.NotFound(w, r)
            return
        }
        w.Header().Set("Content-Type", "application/json")
        _, _ = io.WriteString(w, `{"available":true}`)
    }))
    t.Cleanup(server.Close)

    client := NewInventoryClient(server.Client(), server.URL)
    available, err := client.Available(context.Background(), "order-1")
    if err != nil || !available {
        t.Fatalf("Available() = %v, %v", available, err)
    }
}
```

`t.Cleanup` 在测试结束时执行清理，即使测试中途 `Fatal` 也不会漏掉。

## 6. 测试取消、阻塞和资源退出

并发代码最重要的测试不是“启动成功”，而是“能够停止”：

```go
func TestWorkerStopsAfterCancel(t *testing.T) {
    ctx, cancel := context.WithCancel(context.Background())
    done := make(chan error, 1)

    go func() {
        done <- RunWorker(ctx)
    }()

    cancel()
    select {
    case err := <-done:
        if !errors.Is(err, context.Canceled) {
            t.Fatalf("RunWorker() error = %v", err)
        }
    case <-time.After(time.Second):
        t.Fatal("worker did not stop after cancellation")
    }
}
```

为什么 `done` 的容量是 1？如果测试先超时返回，worker 随后发送结果仍能完成，不会再永久阻塞在发送动作上。

还应覆盖：队列已满、消费者退出、下游超时、进程关闭期限、文件/Body/Rows 关闭和事务回滚。

## 7. race detector 找数据竞争

```bash
go test -race ./...
```

它会在程序运行时记录内存访问和同步关系，发现“同一内存被并发访问且至少一方写入”的路径。代价是测试更慢、占用更多内存，因此通常在 CI 单独执行。

它只能检查测试实际走到的路径。`-race` 没报错不等于程序被证明没有竞争；仍要设计能让并发操作真正重叠的测试。

## 8. fuzz 探索未知输入

```go
func FuzzParseOrder(f *testing.F) {
    f.Add([]byte(`{"id":"order-1","amountCents":100}`))

    f.Fuzz(func(t *testing.T, input []byte) {
        order, err := ParseOrder(input)
        if err != nil {
            return
        }
        if order.AmountCents() <= 0 {
            t.Fatalf("accepted invalid amount: %d", order.AmountCents())
        }
    })
}
```

先加入代表性 seed，fuzzer 再自动变异输入。目标可以是：不 panic、满足不变量、编码后能解码，或优化版与参考实现结果相同。

发现失败后，Go 会保存能复现的输入。先把它保留为回归用例，再修实现，不能只删除失败样本。

## 9. benchmark 测量时间和分配

```go
func BenchmarkParseOrder(b *testing.B) {
    input := []byte(`{"id":"order-1","amountCents":100}`)
    b.ReportAllocs()

    for b.Loop() {
        _, _ = ParseOrder(input)
    }
}
```

```bash
go test -run='^$' -bench=BenchmarkParseOrder -benchmem ./...
```

- benchmark 只说明指定机器、版本、输入和并发度下的结果；
- `ns/op` 是每次操作耗时，`B/op` 和 `allocs/op` 是每次分配；
- 用同一环境多次采样并做统计比较，不根据单次波动下结论；
- 先确认它代表真实请求，再优化数字。

## 10. pprof、trace 和调试器各回答什么

| 工具 | 适合回答的问题 |
| --- | --- |
| 日志、指标、请求 trace | 哪个请求失败，故障发生在哪个边界 |
| `go test -run` | 最小用例能否稳定复现 |
| Delve 调试器 | 某一时刻变量、调用栈和 goroutine 状态是什么 |
| CPU profile | CPU 时间主要消耗在哪些调用路径 |
| heap/allocs profile | 哪些路径分配或保留了大量内存 |
| goroutine profile | goroutine 阻塞在哪里、是否持续泄漏 |
| block/mutex profile | channel/锁等待集中在哪里 |
| runtime trace | 调度、网络、GC、阻塞如何随时间发生 |

推荐排查顺序：先从故障证据缩小范围，写出稳定复现，再选能回答具体问题的 profile。不要一遇到性能问题就同时打开所有工具。

## 11. 一组可执行的质量命令

```bash
gofmt -w .
go vet ./...
go test ./...
go test -race ./...
go test -fuzz=FuzzParseOrder -fuzztime=10s ./...
go test -run='^$' -bench=. -benchmem ./...
```

CI 至少执行 format 检查、`vet`、单元/集成测试和生产构建。race、fuzz、benchmark 可按成本放进独立流水线，但必须有固定入口和负责人。

## 12. 常见错误及结果

| 错误 | 结果 | 改法 |
| --- | --- | --- |
| 只测成功路径 | 边界错误上线后才出现 | 每条规则覆盖正常、边界和失败 |
| 断言完整错误文本 | 改文案导致无意义失败 | 使用 `errors.Is/As` |
| mock 所有东西 | 测试只证明 mock 配置正确 | 领域用 fake，协议和数据库做集成测试 |
| 用 `time.Sleep` 等并发 | 测试慢且偶发失败 | 使用 channel、context 和明确事件同步 |
| benchmark 中包含随机 IO | 数据不可比较 | 固定输入并分离环境噪声 |
| 没 profile 就改内存 | 复杂度增加，热点未改善 | 先 benchmark/profile，再改变实现 |

## 13. 与其他语言对照

| 已熟悉的语言 | 可类比 | Go 中要改变的习惯 |
| --- | --- | --- |
| Java | JUnit 参数化测试、JMH、async-profiler | Go 测试直接属于 package；接口 fake 常可手写；race detector 是常用工程入口 |
| Node.js | Jest table tests、fake timer、clinic | goroutine 可能真正并行；阻塞、共享内存和 data race 都要验证 |
| Python | pytest parameterize、fixture、Hypothesis | `testing` 标准库约定更统一；fuzz、benchmark 和 race 使用 Go 工具链 |
| C++ | GoogleTest、sanitizer、benchmark | Go 仍需关注竞争与生命周期，但内存安全故障面不同，profile 应针对 GC/调度/分配 |

## 14. 动手验证

1. 给 `NewOrder` 添加订单 ID 校验，并补正常、空串和空白串测试；
2. 让 fake 支付接口返回包装错误，证明 `Checkout` 保留错误链；
3. 故意让两个 goroutine 写同一个 map，运行 `go test -race`，再用锁修复；
4. 为 JSON 解析器加入 fuzz，观察 Go 保存的失败输入；
5. 对“直接解码”和“复用缓冲区”各写 benchmark，用 profile 判断是否值得优化；
6. 编写停机测试，证明取消根 context 后所有 worker 在期限内退出。

## 15. 掌握标准

- [ ] 能按业务风险选择单元、集成、race、fuzz 或 benchmark；
- [ ] 测试验证公开行为，不依赖完整错误文本和无意义内部细节；
- [ ] 超时、取消、关闭、回滚和 goroutine 退出都有证据；
- [ ] 能稳定复现故障，并选择合适的 profile 解释瓶颈；
- [ ] 性能结论包含环境、输入、基准数据和优化前后对比。
