# Go：用订单 Worker 掌握并发与异步

goroutine 很轻，但不是免费资源；channel 很方便，但不是所有共享状态的答案。本章实现一个有界订单 Worker，并用它解释创建数量、阻塞、取消、错误、panic、背压和优雅停机。

## 1. 先看危险写法

```go
for order := range orders {
	go handle(order)
}
```

这段代码没有回答：

- 输入一百万条时会创建多少 goroutine？
- `handle` 阻塞后谁取消？
- 错误和 panic 去哪里？
- 服务停机时谁等待？
- 数据库连接池只有 20 条连接时，额外并发有什么价值？

“能并发”不等于“并发有边界”。

## 2. 一个有生命周期的 Worker Pool

```go
func RunWorkers(
	ctx context.Context,
	orders <-chan Order,
	workerCount int,
) error {
	group, ctx := errgroup.WithContext(ctx)

	for i := 0; i < workerCount; i++ {
		group.Go(func() error {
			for {
				select {
				case <-ctx.Done():
					return ctx.Err()

				case order, ok := <-orders:
					if !ok {
						return nil
					}
					if err := handle(ctx, order); err != nil {
						return err
					}
				}
			}
		})
	}

	return group.Wait()
}
```

现在生命周期明确：

```text
创建数量      workerCount
工作来源      orders channel
正常结束      channel 关闭并消费完成
取消          ctx.Done()
错误          返回给 errgroup，取消同组任务
等待          group.Wait()
```

`errgroup` 收集返回 error，但不会自动把 panic 转换为 error。

## 3. goroutine 到底是什么

```go
go handle(ctx, order)
```

每执行一次 `go` 语句，就启动一个新的 goroutine。它由 Go runtime 调度，不等于立即创建一个 OS 线程。

```text
goroutine 可运行
→ 调度器安排到某个 OS 线程
→ 执行 Go 代码
→ 遇到 channel/timer/网络等待时可能被挂起
→ OS 线程继续运行其他 goroutine
```

阻塞系统调用或 cgo 可能占住 OS 线程；runtime 会尽量让其他线程继续执行可运行 goroutine。

## 4. channel 表达通信和同步

无缓冲 channel：

```go
orders := make(chan Order)
```

发送和接收需要同时准备好，常用于交接所有权或同步时刻。

有缓冲 channel：

```go
orders := make(chan Order, 100)
```

允许最多 100 条待处理数据。容量不是随意参数，它表达系统允许积压多少工作：

```text
生产速度 > 消费速度
→ 缓冲逐渐填满
→ 发送方阻塞或执行明确的拒绝/降级
```

这就是背压。把容量调得非常大只会把过载变成更晚发生的高内存和高延迟。

## 5. 谁关闭 channel

通常由确定“以后不会再发送”的一方关闭：

```go
close(orders)
```

关闭表示协议事件“不会再有新值”，不是释放内存，也不是通知接收方停止处理已有缓冲值。

```go
order, ok := <-orders
if !ok {
	return nil
}
```

规则：

- 不向已关闭 channel 发送，否则 panic；
- 重复关闭会 panic；
- 接收方通常不关闭生产者拥有的 channel；
- 不需要关闭每个 channel，只有接收方依赖关闭信号时才关闭；
- nil channel 的发送和接收会永久阻塞。

## 6. `select` 处理多个可能事件

```go
select {
case order, ok := <-orders:
	if !ok {
		return nil
	}
	return handle(ctx, order)

case <-ctx.Done():
	return ctx.Err()
}
```

如果多个 case 同时可进行，runtime 选择其中一个；不能依赖固定优先顺序。将 channel 变量设为 nil 可禁用对应 case，但错误使用会让任务永远等待。

`default` 会让 select 不阻塞，放在循环中可能形成 CPU 忙等：

```go
for {
	select {
	case order := <-orders:
		handle(ctx, order)
	default:
		// 没有等待，循环可能打满 CPU。
	}
}
```

## 7. context 是协作式取消

```go
ctx, cancel := context.WithTimeout(parent, 2*time.Second)
defer cancel()
```

取消只关闭 `ctx.Done()` 并让 `ctx.Err()` 返回原因，不会强制杀死 goroutine。被调用代码必须传递并检查 context：

```go
func handle(ctx context.Context, order Order) error {
	return repository.Save(ctx, order)
}
```

约定：

- context 通常是第一个参数；
- 不保存进长期 struct；
- 不用 context value 传普通业务参数；
- 派生后及时 cancel；
- 一个请求的总体 deadline 应继续传到 HTTP、数据库和消息操作。

## 8. channel、Mutex 还是 atomic

| 问题 | 常见选择 |
| --- | --- |
| 传递任务、结果或所有权 | channel |
| 保护 map 和一组关联字段的不变量 | `sync.Mutex` |
| 等待多个任务结束 | `WaitGroup`/`errgroup` |
| 只执行一次初始化 | `sync.Once` |
| 简单计数或标志 | atomic，前提是状态转换足够简单 |

```go
type OrderBook struct {
	mu   sync.Mutex
	byID map[string]*Order
}

func (b *OrderBook) Add(order *Order) error {
	b.mu.Lock()
	defer b.mu.Unlock()

	if _, exists := b.byID[order.ID()]; exists {
		return ErrDuplicateOrder
	}
	b.byID[order.ID()] = order
	return nil
}
```

锁保护的是“检查并写入”这个完整不变量，不只是某一行 map 访问。

## 9. data race 和 happens-before

两个 goroutine 无同步地访问同一内存，且至少一个写入，就可能产生 data race。结果不只是“偶尔读到旧值”；编译器、CPU 和运行时都不保证错误程序的直觉顺序。

channel 通信、锁的解锁/随后加锁、atomic 操作等建立特定同步关系。普通变量赋值和 `time.Sleep` 不建立可靠可见性。

```bash
go test -race ./...
```

race detector 只能发现测试实际执行到的竞争路径，不是形式证明。

## 10. error 和 panic 如何跨 goroutine

goroutine 的返回值不会自动交给创建者。下面的代码可以编译，但返回的 `error` 会被直接丢弃：

```go
go func() error { return err }() // 可以编译，但调用结果没人接收
```

使用 channel、errgroup 或受保护的共享状态传递结果。

panic 只会在当前 goroutine 展开 defer；父 goroutine 的 recover 接不住。未恢复 panic 最终使整个进程崩溃。只有能够隔离任务失败的边界才考虑在同一 goroutine 中 recover，并记录堆栈。

## 11. 优雅停机

```text
收到 SIGTERM
→ readiness 变为不可用
→ 停止接收请求和拉取新任务
→ 取消根 context
→ 等待在途任务
→ 关闭连接池和遥测
→ 超过总期限后退出
```

如果任务忽略 context、卡在不支持取消的调用或没有被等待，停机就不能保证完成。`os.Exit` 会直接结束进程，defer 不会执行。

## 12. 常见故障及证据

| 现象 | 常见原因 | 证据 |
| --- | --- | --- |
| goroutine 持续上涨 | channel/锁/IO 永久阻塞 | goroutine profile |
| CPU 高 | select default 忙等、计算热点 | CPU profile、trace |
| P99 高但 CPU 不高 | 锁、连接池、channel、下游等待 | trace、block/mutex profile |
| 内存上涨 | goroutine 持有对象、无界队列 | heap + goroutine profile |
| 停机超时 | 任务不响应 context/无人 wait | goroutine dump、关闭日志 |
| 偶发错误 | data race | `go test -race` |

## 13. 与其他语言对照

| 旧模型 | Go 中的区别 |
| --- | --- |
| Java thread/virtual thread | goroutine 由 Go runtime 调度，生命周期仍需显式管理 |
| Node.js Promise/event loop | goroutine 可并行执行 Go 代码，阻塞点和共享内存更重要 |
| Python asyncio Task | goroutine 不需要 async/await 着色，但取消同样是协作式 |
| C++ thread/future | goroutine 更轻，资源所有权和等待协议仍不能省略 |

## 14. 动手验证

1. 写无界 `go handle()` 和固定 worker pool，比较 goroutine、heap 和 P99。
2. 分别让 worker 阻塞在 nil channel、Mutex、HTTP 和数据库池，使用 profile 定位。
3. 写一个忽略 context 的任务，验证服务为何停不下来。
4. 制造 map 并发读写，运行 race detector。
5. 在子 goroutine panic，验证父 goroutine recover 无效。
6. 用容量 1 和 1000 的 channel 压测，比较吞吐、排队和内存。

## 15. 掌握标准

- 每个 goroutine 都有数量上限、所有者、停止、等待和错误路径。
- 能说明 channel 缓冲如何形成排队和背压。
- 能按状态所有权选择 channel、Mutex、errgroup 或 atomic。
- 能解释取消是协作式的、panic 的 goroutine 边界和 data race 风险。
- 能用 race、goroutine、block/mutex profile 和 trace 定位并发故障。
- 能实现有总体期限的优雅停机。
