# Go：运行时与性能

Go 代码通常编译为本地机器码，但 goroutine 调度、栈增长、网络轮询、内存分配和垃圾回收都由运行时参与。

## 运行时模型

- goroutine 由调度器复用到操作系统线程，栈按需增长和收缩。
- 网络轮询器帮助调度大量网络 IO；阻塞系统调用和 cgo 会影响线程行为。
- GC 根据堆和分配速率工作，高分配会消耗 CPU 并影响尾延迟。
- 编译器会判断一个值是否需要在函数结束后继续存在，再决定如何分配内存。
- 内存模型定义 goroutine 之间何时能观察写入；无同步 data race 是错误程序。

## 逃逸分析：先看值要活多久

Go 代码不直接指定“这个值放栈上”或“放堆上”。编译器会进行逃逸分析：

- 值只在当前函数内使用，通常可以放在栈上，函数结束时一起回收。
- 值被返回或被外部长期引用，它就“逃出”了当前函数，通常需要放在堆上，以后由 GC 回收。

使用指针不等于一定分配到堆。下面虽然使用了 `&amount`，但指针没有离开函数：

```go
func localAmount() int {
	amount := 100
	p := &amount
	return *p
}
```

下面返回了 `amount` 的地址。`newAmount` 结束后，调用者仍然要使用它，因此这个值通常会逃逸：

```go
func newAmount() *int {
	amount := 100
	return &amount
}
```

```text
只在函数内使用 → 通常不逃逸 → 可以在栈上
函数结束后仍被引用 → 逃逸 → 通常需要在堆上
```

具体结果由编译器和优化情况决定，可以查看编译器报告：

```bash
go build -gcflags="-m=2" .
```

`escapes to heap` 表示编译器判断该值逃逸到堆。不要为了“看起来省分配”就拒绝指针；先写清楚所有权和共享关系，再用 benchmark 和 pprof 确认它是否真的构成瓶颈。

## 常见性能因素

- 算法复杂度、序列化、字符串/字节转换与分配。
- 锁竞争、channel 阻塞、goroutine 激增和排队。
- HTTP 连接池、数据库池、系统调用和下游延迟。
- GC 周期、堆保留、大型 slice 和缓存增长。

## benchmark、pprof 与 trace

```go
func BenchmarkParse(b *testing.B) {
	b.ReportAllocs()
	for i := 0; i < b.N; i++ {
		_, _ = Parse(sample)
	}
}
```

pprof 分析 CPU、heap、goroutine、mutex 和 block；trace 观察调度、网络、GC 和时序。先建立服务级吞吐与 P95/P99 基线，再定位热点、单点修改并重新验证。

## 易错点

- 因为 goroutine 便宜就无限创建。
- 为减少一次分配引入 `sync.Pool`，却增加共享和残留状态。
- 只看平均延迟，不看排队和尾延迟。
- 未分析就把所有参数改成指针，反而引发逃逸和间接访问。

## 验收

- 能解释调度器、网络轮询、GC、逃逸和内存模型的边界。
- 能用 benchmark、pprof 和 trace 区分 CPU、分配、锁与调度问题。
- 性能结论包含环境、负载、尾延迟、资源和正确性验证。
