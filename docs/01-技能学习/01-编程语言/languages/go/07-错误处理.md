# Go：用订单结算理解错误处理

Go 把失败表示成普通 `error` 值。专家级错误处理不是到处写 `if err != nil`，而是设计稳定错误类别、保留原因链、明确转换和记录边界，并让取消、重试和部分成功具有一致语义。

## 1. 从结算失败开始

```go
func Checkout(ctx context.Context, order *Order, gateway PaymentGateway) error {
	receipt, err := gateway.Pay(ctx, order.ID(), order.AmountCents())
	if err != nil {
		return fmt.Errorf("pay order %s: %w", order.ID(), err)
	}

	if err := order.MarkPaid(receipt.ID); err != nil {
		return fmt.Errorf("mark order %s paid: %w", order.ID(), err)
	}
	return nil
}
```

调用链可能是：

```text
HTTP handler
→ Checkout
→ AlipayGateway.Pay
→ HTTP client
```

每层只补充自己知道的操作上下文，最外层决定日志和协议响应。

## 2. `error` 是一个接口值

标准定义可以简化理解为：

```go
type error interface {
	Error() string
}
```

任何提供 `Error() string` 的类型都可以作为错误。函数返回 `(T, error)`，让结果和失败一起进入普通控制流：

```go
order, err := store.Get(ctx, id)
if err != nil {
	return nil, err
}
```

这与 Java exception、Python exception 不同：error 不会自动跨栈传播；你必须显式返回、处理或有意忽略。

## 3. 三种错误表达方式

### 3.1 简单错误

```go
var ErrInvalidAmount = errors.New("invalid order amount")
```

适合没有额外字段、需要稳定判断的类别。

### 3.2 sentinel error

```go
var (
	ErrOrderNotFound = errors.New("order not found")
	ErrAlreadyPaid   = errors.New("order already paid")
)
```

调用方使用 `errors.Is`，不要比较错误文本：

```go
if errors.Is(err, ErrOrderNotFound) {
	// 映射为 404
}
```

### 3.3 自定义错误类型

```go
type PaymentRejectedError struct {
	Code string
}

func (e *PaymentRejectedError) Error() string {
	return "payment rejected: " + e.Code
}
```

调用方通过 `errors.As` 取得结构化信息：

```go
var rejected *PaymentRejectedError
if errors.As(err, &rejected) {
	log.Printf("payment code=%s", rejected.Code)
}
```

不要把令牌、银行卡号、完整 SQL 等敏感信息放入错误文本。

## 4. 包装错误：`%w` 保留原因链

```go
order, err := store.Get(ctx, id)
if err != nil {
	return nil, fmt.Errorf("load order %s: %w", id, err)
}
```

`%w` 让上层既看到“加载哪个订单失败”，又能继续判断根因：

```go
errors.Is(err, sql.ErrNoRows)
errors.As(err, &networkError)
```

使用 `%v` 只会把文本拼进去，原因链会在这一层中断。是否包装某个底层错误也是 API 契约：一旦上层依赖它，就要考虑兼容性。

## 5. 在边界统一转换和记录

核心业务返回领域错误，HTTP 层负责协议映射：

```go
func writeError(w http.ResponseWriter, err error) {
	switch {
	case errors.Is(err, ErrOrderNotFound):
		http.Error(w, "order not found", http.StatusNotFound)
	case errors.Is(err, ErrAlreadyPaid):
		http.Error(w, "order conflict", http.StatusConflict)
	case errors.Is(err, context.DeadlineExceeded):
		http.Error(w, "request timed out", http.StatusGatewayTimeout)
	default:
		http.Error(w, "internal error", http.StatusInternalServerError)
	}
}
```

通常只在请求、消息消费或任务边界记录一次完整错误链和 trace ID。每一层都打印会制造重复日志，却不增加信息。

## 6. `defer`、关闭错误和多错误

只写：

```go
defer file.Close()
```

可能丢失写入最终 flush/close 时的错误。重要持久化操作应显式合并：

```go
func WriteReport(path string, data []byte) (err error) {
	file, err := os.Create(path)
	if err != nil {
		return err
	}
	defer func() {
		err = errors.Join(err, file.Close())
	}()

	_, err = file.Write(data)
	return err
}
```

读取型资源的 close 错误通常不影响结果，但仍应依据 API 契约判断，不能形成机械规则。

## 7. panic 不是普通失败

适合返回 error：

- 用户输入错误；
- 订单不存在；
- 下游超时；
- 数据库冲突；
- 支付被拒绝。

可能 panic：

- 初始化时关键不变量被破坏；
- 程序进入不可能状态；
- 库 API 明确约定调用错误会 panic。

`recover` 只在发生 panic 的同一 goroutine 的 defer 中有效：

```go
defer func() {
	if value := recover(); value != nil {
		log.Printf("panic=%v\n%s", value, debug.Stack())
	}
}()
```

父 goroutine 不能 recover 子 goroutine 的 panic。恢复边界通常位于 HTTP 请求或独立任务入口；恢复后也不能假设共享状态一定安全。

## 8. 取消、超时和重试

`context.Canceled` 与 `context.DeadlineExceeded` 是可判断错误。不要包装后再比较 `==`，使用 `errors.Is`。

重试必须同时满足：

- 错误类别确实可重试；
- 操作幂等，或者具有幂等键；
- 有退避和次数上限；
- 总体不超过 context deadline；
- 不把过载继续放大到下游。

支付拒绝、参数错误等永久失败不能因为“网络代码统一重试”而重复执行。

## 9. 常见错误及结果

| 错误写法 | 运行结果 |
| --- | --- |
| `_ = do()` | 失败消失，状态可能不完整 |
| `fmt.Errorf("... %v", err)` | 原因链中断，`Is/As` 失效 |
| 每层都 log | 同一故障产生多条噪声日志 |
| 比较 `err.Error()` | 文本变化破坏程序逻辑 |
| 所有错误都重试 | 放大流量或重复副作用 |
| 用 panic 处理业务失败 | 请求错误升级为进程风险 |
| 父 goroutine defer recover | 接不住子 goroutine panic |

## 10. 与其他语言对照

| Java/Python/C++ 习惯 | Go 中的做法 |
| --- | --- |
| throw 自动展开调用栈 | 显式返回 error |
| catch by type | `errors.As` |
| catch cause chain | `%w` + `errors.Is/As` |
| finally/RAII | `defer`，但仍要处理 close 错误 |
| unchecked exception 穿透线程 | goroutine panic 未恢复会使进程崩溃 |

## 11. 动手验证

1. 建立三层错误链，分别用 `%w` 和 `%v` 包装，观察 `errors.Is`。
2. 写自定义支付拒绝错误，通过 `errors.As` 提取 code。
3. 在子 goroutine 中 panic，验证父 goroutine 无法 recover。
4. 为 HTTP 边界建立表驱动测试，验证领域错误与状态码映射。
5. 模拟“支付成功、标记订单失败”，说明为什么还需要幂等和补偿设计。

## 12. 掌握标准

- 能设计简单错误、sentinel 和结构化错误的使用边界。
- 包装错误时既增加操作上下文又保留原因链。
- 日志、HTTP/RPC 映射和重试决策集中在明确边界。
- 能处理 context 错误、close 错误和部分成功。
- 能说明 panic/recover 的 goroutine 作用域和系统风险。
