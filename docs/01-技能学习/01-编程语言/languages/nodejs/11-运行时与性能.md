# Node.js / TypeScript：运行时与性能

Node.js 性能受 V8 编译与 GC、事件循环延迟、libuv、系统调用、连接池和下游服务共同影响。

## 1. 运行时组成

- V8 解析 JavaScript、解释执行并对热点代码 JIT 优化。
- 对象形状稳定、类型反馈一致的代码更容易优化；动态行为可能触发去优化。
- libuv 提供事件循环和部分线程池任务，操作系统提供网络事件与进程资源。
- TypeScript 编译后不参与运行时，不会让代码自动更快或校验输入。

## 2. 关键指标

- 请求吞吐、P50/P95/P99 与错误率。
- event loop delay/utilization，长同步任务和 microtask 饥饿。
- CPU profile、heap/RSS/Buffer、GC 时间和分配。
- 活跃 socket、连接池、队列、Stream 缓冲和 worker 使用率。

## 3. 分析方法

固定 Node 版本、构建、负载和数据，先建立服务级基线。CPU profile 找热点函数，火焰图看调用路径，heap snapshot 看保留链，GC/内存指标看增长，诊断报告记录崩溃状态。

先把事件循环 P99 延迟变成可观测指标：

```ts
import { monitorEventLoopDelay } from "node:perf_hooks";

const delay = monitorEventLoopDelay({ resolution: 20 });
delay.enable();

const timer = setInterval(() => {
  console.log({ eventLoopP99Ms: delay.percentile(99) / 1e6 });
  delay.reset();
}, 10_000);
timer.unref();
```

若 P99 延迟异常，再用 `node --cpu-prof dist/server.js` 找长时间占用 JavaScript 线程的代码；内存增长则同时看 V8 heap、Buffer 和进程 RSS。

常见瓶颈是同步 JSON/正则/加密、超大对象复制、无界 Promise、日志、序列化和下游连接池，而不是“事件循环本身慢”。

## 4. 易错点

- 只看 CPU，不看事件循环延迟和下游排队。
- 在开发热更新环境采样并代表生产构建。
- 盲目增加 libuv 线程池或 Node 进程数，压垮数据库。
- 用更大内存上限掩盖对象保留和无界缓存。

## 5. 从订单接口定位慢在哪里

```text
请求总延迟
  = 等待事件循环
  + JavaScript/JSON/校验 CPU
  + 等待连接池
  + 数据库与外部 HTTP
  + 排队、重试和响应写出
```

先用 trace 或分段指标判断时间落在哪一段。event-loop delay 高且 CPU 高，再看 CPU profile；heap/RSS 持续增长，再看对象保留链、Buffer 和 native 资源；连接池排队高，则优化 JavaScript 通常无效。

## 6. V8 优化是实现细节

稳定对象形状和避免无意义的大量分配通常有益，但不要根据“听说 hidden class 更快”重写清晰的领域代码。V8 会升级，优化与去优化条件会变。只有 profile 指向某个热点，并有可重复 benchmark 时，才做针对性修改。

## 7. JavaScript 反射：对象检查、Reflect 和 Proxy

JavaScript 对象本来就是运行时存在的动态结构，因此很多“反射”就是普通对象操作。TypeScript 的 `type` 和 `interface` 编译后通常被擦除，不能在运行时枚举。

```text
TypeScript interface ──编译后──→ 不存在
JavaScript class      ──运行时──→ 构造函数 + prototype
JavaScript object     ──运行时──→ 自有属性 + 原型链
```

下面观察一个订单对象：

```ts
class Order {
  constructor(
    readonly id: string,
    public status: "pending" | "paid" = "pending",
  ) {}

  markPaid(): void {
    this.status = "paid";
  }
}

const order = new Order("order-1");

console.log(typeof order);                       // object
console.log(order instanceof Order);             // true
console.log(Object.keys(order));                  // id、status
console.log(Object.getPrototypeOf(order));       // Order.prototype
console.log(Reflect.get(order, "status"));       // pending
Reflect.set(order, "status", "paid");

const method = Reflect.get(order, "markPaid");
if (typeof method === "function") {
  Reflect.apply(method, order, []);
}
```

`Object.keys(order)` 只返回可枚举的自有属性；`markPaid` 在原型上，所以不会出现在结果中。属性还可能是 getter/setter，读取它可能执行代码，而不只是取一块内存。

`Reflect.get/set/apply/construct` 把读取属性、写属性、调用函数和调用构造器统一成函数形式，方便框架组合。它不会恢复 TypeScript 类型，也不会替输入做业务校验。

`Proxy` 可以拦截对象操作：

```ts
function withLogging<T extends object>(target: T): T {
  return new Proxy(target, {
    get(current, property, receiver) {
      const value = Reflect.get(current, property, receiver);
      if (typeof value !== "function") return value;

      return (...args: unknown[]) => {
        console.log("call", String(property));
        return Reflect.apply(value, current, args);
      };
    },
  });
}

const tracedOrder = withLogging(new Order("order-2"));
tracedOrder.markPaid();
```

调用链是：

```text
tracedOrder.markPaid
→ Proxy 的 get trap
→ 取得原方法并包装
→ 包装函数记录日志
→ Reflect.apply 调用原方法
```

这与 Java 动态代理用途相似，但建立在 JavaScript 属性协议上。Proxy、getter 和大量动态属性会隐藏控制流，也可能让 V8 更难优化；业务核心优先使用普通函数、显式包装器和稳定对象结构。

装饰器可以在类或成员定义阶段执行逻辑，框架也可以额外保存 metadata，但它们不会让已经擦除的 TypeScript interface 自动出现在运行时。依赖注入若需要定位 `PaymentGateway`，必须使用 class、`Symbol`、字符串 token 或显式注册表；外部数据仍要经过 schema 校验。

## 8. 从服务指标到局部 benchmark

1. 固定生产构建、Node 版本、数据和下游容量。
2. 用服务压测复现 P99、吞吐或内存问题。
3. 用 trace、CPU/heap profile 缩小到具体路径。
4. 抽出纯 CPU 热点，用 `node:perf_hooks` 或可靠工具做局部 benchmark。
5. 改动后回到服务压测，验证正确性与尾延迟。

局部 benchmark 不能证明数据库查询或整条订单链路更快。

## 9. 与其他语言对照

| 运行时 | 优化重点 |
|---|---|
| C++ | AOT 编译、内存布局、分配、系统调用 |
| Java | JVM JIT、GC、线程/虚拟线程、连接池 |
| Python | 解释器开销、算法、C 扩展、进程/asyncio |
| Node.js | V8 JIT/GC、event loop、Buffer/native、异步队列 |

## 10. 动手验证

1. 给订单接口加入 event-loop delay、连接池等待和下游耗时指标。
2. 制造 CPU 循环与慢数据库两种故障，比较 profile 和指标形状。
3. 制造 Buffer 增长，观察 heapUsed 与 RSS 为什么不同步。
4. 用 `Object.keys`、原型和 `Reflect.get` 检查 Order，说明实例字段与原型方法的区别。
5. 用 Proxy 包装 Order，再从调用栈确认方法经过哪几层。

## 11. 掌握标准

- 能解释 V8、事件循环、libuv、GC 与系统 IO 的职责。
- 能区分 TypeScript 编译期类型和 JavaScript 运行时对象，并解释 Reflect、Proxy 与装饰器的作用边界。
- 能先按请求阶段定位，再选择 CPU profile、heap snapshot 或下游指标。
- 不把 TypeScript 类型、V8 传闻或局部 benchmark 当作服务性能结论。
- 性能结论包含真实负载、尾延迟、资源上限和正确性验证。
