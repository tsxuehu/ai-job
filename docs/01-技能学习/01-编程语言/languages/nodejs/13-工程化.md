# Node.js / TypeScript：工程化

Node.js/TypeScript 企业仓库要同时约束 workspace package、JavaScript 运行时 import、TypeScript 类型边界、外部输入校验和异步资源生命周期。公共原则参见 [企业级后端项目工程结构](../../../../03-实战项目/企业级项目工程结构.md)。

## 推荐 workspace

```text
repository/
├── package.json
├── lockfile
├── tsconfig.base.json
├── apps/
│   ├── api/
│   │   ├── src/bootstrap.ts
│   │   └── src/main.ts
│   └── worker/
├── packages/
│   ├── order-domain/
│   ├── order-application/
│   ├── order-adapter-postgres/
│   ├── order-adapter-http/
│   ├── contracts/
│   └── platform-observability/
├── migrations/
├── tests/
│   ├── integration/
│   ├── contract/
│   └── performance/
├── deploy/
├── ops/
├── docs/
└── tools/
```

小型项目先在单 package 内使用 `src/modules/order/...`。只有需要独立构建、缓存、版本、发布或强边界时才拆 workspace package，避免 package 爆炸。

## 运行时依赖方向

```text
order-domain
      ▲
order-application ◄── postgres-adapter
      ▲              external-api-adapter
      │
http-adapter
      ▲
apps/api bootstrap（显式组装）
```

- TypeScript `import type` 和 interface 会在编译后消失，不能当作运行时注入机制。
- app/bootstrap 通过构造参数、工厂、token 或具体对象完成组装。
- domain/application 不导入 Web 框架、ORM、具体 SDK 和进程全局状态。
- adapter 做 schema 校验、DTO 转换、错误映射、超时和资源管理。
- package exports 只暴露公共入口，lint/构建规则禁止深层 import。

## package 设计

- 每个 package 有明确 `name`、exports、types、构建产物与环境要求。
- ESM/CommonJS 策略在仓库统一，package.json、tsconfig、测试和运行器一致。
- 谨慎使用全量 barrel `index.ts`，避免循环依赖和意外初始化顺序。
- 公共类型与运行时 schema 尽量同源或建立一致性测试。
- 不创建 types/common/utils 巨包；类型属于产生该语义的业务模块。

## 依赖安装与构建

- 运行时需要的包放 `dependencies`，只参与开发和构建的工具放 `devDependencies`；
  插件要求宿主提供的包才使用 `peerDependencies`。
- 提交 lockfile，CI 使用冻结锁文件的安装方式，并固定 Node.js 与包管理器版本。
- 构建必须实际执行类型检查、测试和产物启动验证，不能只依赖编辑器提示。
- 评估传递依赖、安装脚本、许可证和安全更新，不让业务代码深度绑定第三方 SDK。

## apps 入口

apps 负责：配置校验、日志/Trace、连接池、HTTP server/consumer、AbortController、信号和优雅停机。应用入口不包含订单状态判断等业务规则。

关闭流程：停止接收 → abort 根 signal → 等待受管理 Promise/worker → 关闭 server/Stream/连接池 → 刷新观测。顶层 uncaught exception/rejection 记录后进入受控退出，而不是吞掉继续运行。

## 配置和外部数据

- 环境变量先经运行时 schema 解析成只读 Config，再注入所需片段。
- HTTP/消息/数据库数据不能通过 `as Type` 伪装成已验证对象。
- contracts package 保存 OpenAPI、事件 schema 和生成入口，不让生成 DTO 成为 domain。
- 数据库 migration 与 adapter 同版本演进，但不在应用启动时无条件自动执行生产迁移。

## 测试组织

- domain/application：不启动 server 和数据库的快速单元测试。
- adapter：schema、SQL、HTTP/Stream、AbortSignal 与错误映射测试。
- contract：API/事件 schema 与消费者兼容。
- integration/E2E：真实数据库、进程关闭、断连和任务恢复。
- performance：event loop、CPU、heap/RSS、连接池和 P95/P99。
- 测试结束检查未关闭 handle、timer、listener、worker 和 Promise。

## 常见错误

- apps/api 成为所有业务代码的堆放处，路由直接写 SQL。
- package 之间深层相对导入，exports 形同虚设。
- 通过全局 DI container/单例隐藏依赖和生命周期。
- domain 使用框架 Request/Response、ORM entity 和动态 JSON。
- 每个小目录都发布 package，构建链和版本管理远大于业务价值。

## 验收

- [ ] workspace package 与业务/稳定技术能力对应，依赖图有向无环。
- [ ] 类型依赖和运行时依赖都可见，bootstrap 负责显式组装。
- [ ] 外部数据运行时校验，schema、DTO 和 domain 分离。
- [ ] ESM、锁文件、tsconfig、生成代码和产物可复现。
- [ ] Promise、worker、Stream、连接和取消都有所有者与关闭路径。
- [ ] 单元、契约、集成和性能测试覆盖真实异步风险。
