# Node.js / TypeScript：IO 与网络

> 目标：使用 Buffer、Stream、HTTP、JSON 和数据库时，正确处理编码、背压、超时、取消、输入限制和资源关闭。

统一场景：读取订单文件，调用库存 HTTP 服务，再把订单写入数据库。

## 1. string、Buffer 与编码

```ts
const bytes = Buffer.from(text, "utf8");
const textAgain = bytes.toString("utf8");
```

- string 表示文本，Buffer 表示字节；
- 文本与字节转换显式指定编码；
- 不用 string 保存任意二进制协议；
- Buffer 可能占用 V8 堆外内存，排查内存时同时看 RSS；
- 网络 chunk 不等于完整消息。

## 2. Stream 与背压

```ts
await pipeline(
  createReadStream(inputPath),
  transformOrders(),
  createWriteStream(outputPath)
);
```

优先使用 `pipeline`/`finished` 统一传播错误并等待关闭。

如果手动写入：

```ts
if (!writable.write(chunk)) {
  await once(writable, "drain");
}
```

返回 `false` 表示下游缓冲已满，必须等待背压。忽略背压会让进程内存不断增长。

## 3. HTTP 与取消

```ts
const controller = new AbortController();
const timer = setTimeout(() => controller.abort(), 2000);

try {
  const response = await fetch(url, { signal: controller.signal });
  if (!response.ok) throw new HttpStatusError(response.status);
  // 限制并解析 response body。
} finally {
  clearTimeout(timer);
}
```

- 复用连接和 client/agent；
- 设置连接、请求和总体业务 deadline；
- AbortSignal 必须传到真实 IO；
- 限制请求体、响应体和并发量；
- 只对幂等操作和明确临时错误重试；
- CPU 密集处理会阻塞事件循环，应转移到 Worker/native/独立服务。

## 4. JSON 与运行时校验

TypeScript 类型在运行时不存在：

```ts
const value: unknown = await response.json();
const request = createOrderSchema.parse(value);
```

外部 JSON 必须通过运行时 schema 或显式检查。校验字段、长度、金额精度、时间格式、未知字段和版本，再转换成领域类型。

不要使用：

```ts
const request = value as CreateOrderRequest;
```

类型断言不会检查真实数据。

## 5. 数据库

```ts
const client = await pool.connect();
try {
  await client.query("BEGIN");
  await client.query(sql, [orderId, total]);
  await client.query("COMMIT");
} catch (error) {
  await client.query("ROLLBACK");
  throw error;
} finally {
  client.release();
}
```

- 使用参数化 SQL；
- pool 是应用级资源，client/transaction 是操作级资源；
- 配置池容量、获取超时、查询 deadline；
- 失败路径必须回滚并 release；
- 大结果集使用 cursor/stream 并处理背压。

## 6. 常见错误

- 把 Buffer、string 和 JSON 对象混为一谈；
- 假设一个 chunk 等于一条消息；
- 忽略 `write()` 返回值；
- Promise 失败无人 await/return；
- TypeScript 类型代替运行时数据校验；
- timer、Stream、socket、listener 或数据库 client 未关闭。

## 7. 一次订单请求经过哪些 IO

```text
HTTP 字节
  → 限制大小、解码 JSON
  → 运行时校验，得到 CreateOrderRequest
  → 查询数据库 / 调库存 HTTP 服务
  → Order 转换为响应 DTO
  → 编码 JSON，写入响应 Stream
```

每一条箭头都是边界：字节不等于文本，文本不等于合法 JSON，合法 JSON 不等于合法订单；`Order` 也不应该直接作为网络响应。理解这些转换，比记住某个框架的路由写法更重要。

## 8. 异步 IO 为什么仍会压垮服务

“不阻塞 JavaScript 线程”不等于“没有成本”。每个请求仍占用 socket、Buffer、Promise、连接池槽位和下游容量。

```ts
const pending = orderIds.map((id) => fetchInventory(id));
await Promise.all(pending); // orderIds 无上限时，会瞬间发出所有请求
```

入口要限制请求大小和并发；数据库池限制同时查询数；对外 HTTP 使用并发上限、deadline 和取消；Stream 用背压让上游跟随下游速度。

## 9. 与其他语言对照

| 语言 | 常见 IO 形式 | 最容易忽略的点 |
|---|---|---|
| C++ | 同步 API、回调、协程或框架事件循环 | 资源所有权和 buffer 生命周期 |
| Java | 阻塞 IO、线程池、虚拟线程、异步 API | 线程/连接池容量和超时传播 |
| Python | 同步 IO 或 `asyncio` | 不能在 event loop 中调用阻塞函数 |
| Node.js | Promise、Stream、事件循环 | Promise 不等于取消，chunk 不等于消息 |

## 10. 动手验证

1. 用慢 Writable 分别测试“等待 drain”和“忽略返回值”，观察 RSS。
2. 服务端延迟响应，客户端超时后确认 socket 和服务端工作是否真的停止。
3. 给库存服务设置并发上限，比较无限 `Promise.all` 下的尾延迟和错误率。
