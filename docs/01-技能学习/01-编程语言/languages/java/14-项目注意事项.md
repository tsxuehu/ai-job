# Java：项目注意事项

目标：识别 Java 后端特有的 JVM、对象语义、框架代理与线程模型边界，并能从实际调用链解释生产行为。

## 1. 对象引用与相等

- 参数永远按值传递；传对象时复制引用值，方法不能重新绑定调用方变量。
- `==` 对对象比较引用身份，值语义使用 `equals`。
- 作为 HashMap key 的对象必须保持 `equals/hashCode` 一致，参与哈希的字段不能在放入后变化。
- `final` 只禁止引用重新赋值，不让对象自动不可变。
- 包装类型可能为 null，并有装箱、拆箱和缓存行为；业务比较不要依赖对象身份。

## 2. Spring 代理边界

事务、缓存、重试、异步等能力经常由代理/AOP 实现，只有经过代理的调用才会生效。

```java
@Transactional
public void outer() {
    this.inner(); // 自调用通常不会再次经过代理
}
```

- 同类自调用可能绕过 `@Transactional`、`@Async`、`@Cacheable` 等代理拦截。
- private/final 方法、代理类型与可见性会影响拦截方式。
- 事务不能跨线程自动传播；提交异步任务后，原事务上下文通常已不再属于新线程。
- catch 异常后不重新抛出可能让事务错误提交；回滚规则需明确。

## 3. JMM、线程池和虚拟线程

- volatile 提供可见性和顺序约束，不让 `count++` 自动原子化。
- ThreadLocal 在线程池中会跨请求复用，必须 finally remove；虚拟线程下也不要把它当无限存储。
- 平台线程池要设置线程数、队列容量、拒绝策略和关闭流程。
- 虚拟线程适合大量阻塞式 IO，不会增加数据库连接数或下游容量；仍需 semaphore/连接池限制。
- CompletableFuture 明确 Executor，不能把阻塞任务随意扔进公共 ForkJoinPool。

## 4. JVM 与资源

GC 只管理普通对象内存，不关闭文件、HTTP 响应、JDBC ResultSet/Statement/Connection、ExecutorService 和 native 资源。使用 try-with-resources，并关注 suppressed exception。

常见内存保留来源包括静态集合、无界缓存、监听器、ThreadLocal、线程池队列和类加载器。排障时结合线程转储、堆转储、JFR 和 GC 日志，而不是先调大堆。

## 5. ORM 与序列化

- ORM 不能消除事务隔离、锁、N+1、懒加载和批量写入问题。
- entity 不直接作为外部 DTO，避免字段、懒加载和持久化语义泄漏。
- JSON 反序列化后的 null、默认值和未知字段要明确校验。
- record 适合数据载体，但内部引用对象仍可能可变。

## 6. 反射、注解与类加载

- 注解只是元数据；真正行为来自编译器、annotation processor、反射、代理或框架扩展点。
- 反射访问要处理缺失成员、访问控制、泛型擦除和 native image/AOT 配置，不能把字符串成员名散落在业务代码。
- 动态代理只拦截经过代理对象的调用；代理类型、final/private 方法和自调用都会影响行为。
- 类型身份包含类加载器；插件和热加载必须设计 API、隔离、关闭与卸载边界。

## 7. 安全专项

- 不接受任意 Java 原生反序列化对象；外部 DTO 使用明确 schema 和允许类型。
- 表达式语言、模板、反射类名和脚本入口不能直接接收用户字符串。
- XML/压缩/文件上传配置实体、递归、展开比例、路径和总量限制。
- SQL 使用参数绑定；日志和错误响应不泄露令牌、SQL 参数和内部堆栈。
- 固定 JDK、插件和依赖平台，检查传递依赖与构建制品来源。

- [ ] 事务边界、异常回滚和异步线程切换是否一致？
- [ ] 线程池/虚拟线程是否仍受连接池和下游容量限制？
- [ ] ThreadLocal、静态缓存和队列是否会长期保留对象？
- [ ] JDBC/HTTP/Executor 等资源是否确定关闭？

- [ ] 反序列化、表达式、反射、上传和依赖是否存在不可信输入边界？

## 9. 用故障反推规则

### 9.1 标了 `@Transactional` 却没有事务

调用没有经过 Spring 代理，常见于同类自调用、private/final 方法或对象并非容器创建。先确认实际对象 class 和调用路径，不要继续堆注解。

### 9.2 堆不断增长但 GC 正常工作

静态 cache、ThreadLocal、listener、队列或 classloader 仍持有对象。heap dump 沿 GC root 找所有者；调大堆只会推迟故障。

### 9.3 换虚拟线程后数据库仍超时

虚拟线程降低等待线程成本，不增加数据库连接和下游容量。使用 semaphore/连接池限制并发，并观察 acquisition wait、SQL 和锁。

### 9.4 CompletableFuture 偶发不返回

stage 使用了公共池并执行阻塞操作，或 cancel 没传到底层。记录每个 stage 的 executor、超时、异常和实际中断/取消支持。

## 10. 专家级动手题

1. 用代理对象 class/调用栈证明一次注解为何生效或失效；
2. 构造 ThreadLocal 泄漏并用 heap dump 找到 root；
3. 比较平台线程与虚拟线程，但固定连接池和 CPU；
4. 设计 JPA entity、DTO、领域对象三层映射与事务测试；
5. 从 JFR/thread dump/GC log 三种证据诊断同一服务。
