# Java：错误处理

Java 用异常传播非正常结果。设计重点不是“都 catch 住”，而是区分可恢复业务失败、系统失败和程序缺陷，并建立边界。

## 1. 异常体系

- checked exception 必须声明或捕获，适合调用方有明确恢复动作的失败。
- unchecked exception 继承 `RuntimeException`，常用于参数、不变量和无法合理恢复的失败。
- `Error` 通常表示 JVM 或环境严重问题，业务代码不应常规捕获。
- 自定义异常保留原因 `cause` 和结构化上下文。

```java
try {
    return repository.load(id);
} catch (SQLException e) {
    throw new StorageException("load task " + id, e);
}
```

## 2. 异常边界

领域层不依赖 HTTP 状态码；Web 边界统一将领域异常映射为外部错误。线程池、异步 stage、消息消费和定时任务都要观察异常，不能让失败静默丢失。

只在能够处理、转换或增加有效上下文的位置 catch。记录通常放在请求/任务最外层，避免每层重复日志。外部响应不泄露堆栈、SQL 和敏感信息。

## 3. finally 与受抑制异常

`finally` 无论正常或异常都会执行，但不要从 finally 返回或抛出新异常覆盖原失败。资源优先使用 try-with-resources；关闭异常会作为 suppressed exception 保留。

## 4. 易错点

- `catch (Exception)` 后忽略或只打印。
- 用异常执行普通条件分支。
- 异步异常封装在 `CompletionException` 中却未解开原因链。
- 事务边界捕获异常后不重新抛出，导致错误提交。

## 5. 订单结算如何保留原因链

```java
public void checkout(Order order) {
    try {
        var receipt = gateway.pay(order.id(), order.amountCents());
        order.markPaid(receipt.id());
    } catch (GatewayTimeoutException cause) {
        throw new CheckoutException("pay order " + order.id(), cause);
    }
}
```

每层只增加自己知道的操作上下文，最外层请求/任务边界记录一次并映射协议。不要用 `throw new CheckoutException(cause.getMessage())` 丢失 cause 和堆栈。

## 6. checked 还是 unchecked 不是机械选择

先问调用方能否在当前抽象层采取恢复动作。若所有调用者只能上抛，checked exception 会制造样板；若调用者必须选择替代流程，类型化的 checked 失败可能有价值。业务可预期结果也可以用 sealed result 表达，避免用异常承载普通分支。

## 7. 资源和异步异常

try-with-resources 负责确定关闭并保留 suppressed exception。CompletableFuture 的异常通常包在 `CompletionException` 中；线程池提交的任务若无人 `get/join` 或没有统一 handler，失败可能没有进入业务可观测边界。

## 8. 与其他语言对照

| 语言经验 | Java 中的差异 |
| --- | --- |
| C++/Python exception | Java 区分 checked/unchecked，并由 try-with-resources 保留关闭异常 |
| Go error | Java 异常会自动跨栈传播，但边界、分类和 cause 仍需显式设计 |
| Node Promise | 两者异步失败都可能被包装；必须等待并建立最外层错误边界 |

## 9. 动手验证

1. 在支付、状态更新和数据库保存处注入失败，验证最终状态；
2. 构造 primary 与 close 同时失败，检查 suppressed exception；
3. 比较 checked exception、RuntimeException 和 sealed result 的调用体验；
4. 让 CompletableFuture 失败但不 join，再建立统一观察路径；
5. 验证事务方法捕获异常后是否影响回滚规则。

## 10. 掌握标准

- 能设计 checked/unchecked、领域/基础设施异常边界。
- 能保留 cause 链并集中映射、记录错误。
- 能说明异常对事务、线程池和 CompletableFuture 的传播影响。
