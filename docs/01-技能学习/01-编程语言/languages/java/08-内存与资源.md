# Java：内存与资源

JVM 的 GC 管理普通对象内存，不会自动关闭文件、连接、事务、线程和其他业务资源。

## 1. JVM 内存概念

- heap 保存普通对象，由 GC 管理。
- 每个线程有调用栈，栈帧保存局部状态和调用信息。
- Metaspace 保存类元数据；直接内存和 native 内存不属于普通堆。
- 对象是否回收取决于从 GC Roots 的可达性，不取决于局部变量何时离开源码作用域。

## 2. GC 与泄漏

GC 回收不可达对象；仍被静态集合、缓存、监听器、ThreadLocal、队列或类加载器引用的对象不会被回收。需要通过堆转储和引用链区分“容量确实需要”与“意外保留”。

不要用 `System.gc()` 代替容量治理。优化前同时观察分配速率、存活集、停顿、吞吐和尾延迟。

## 3. try-with-resources

```java
try (var input = Files.newBufferedReader(path)) {
    return parse(input);
}
```

实现 `AutoCloseable` 的文件、流、JDBC 资源等应放入 try-with-resources。关闭顺序与声明相反；关闭错误会保留为 suppressed exception。

连接池归还连接不等于 GC；数据库 ResultSet、Statement、事务和 HTTP 响应体按契约关闭。ExecutorService、定时器和虚拟线程任务也需要停止与等待策略。

## 4. 订单请求中的对象与资源不是一回事

```text
Order/DTO/List 对象
→ 不再从 GC Roots 可达后，由 GC 决定回收内存

HTTP body/JDBC Connection/ResultSet
→ 完成协议后必须立即 close

Executor/后台任务
→ 必须停止提交、取消/中断、等待结束
```

对象被 GC 回收得很快，也不能补救未归还的数据库连接；资源已经 close，也不代表持有它的包装对象马上离开堆。两条生命周期必须分别设计。

## 5. 引用链决定逻辑泄漏

```java
static final Map<String, Order> CACHE = new HashMap<>();
```

只要静态字段、线程、ThreadLocal、listener 或队列仍能到达 Order，GC 就不能回收。heap dump 要沿 dominator/GC root 引用链找到所有者，不只看“哪种对象数量多”。

## 6. 与其他语言对照

| 语言经验 | Java 中的差异 |
| --- | --- |
| C++ RAII | Java 没有普通对象的确定析构；业务资源用 try-with-resources |
| Go/Python GC | 都按可达性回收；Java 还需观察 Metaspace、direct/native memory 和类加载器 |
| Node.js | listener/timer/cache 同样会保留对象；Java 还常见 ThreadLocal/线程池队列 |

## 7. 动手验证

1. 在 ThreadLocal 中遗留大对象，用 heap dump 查 GC root；
2. 构造无界 cache/queue，区分分配速率与存活集；
3. 让 body 与 close 同时抛异常，查看 suppressed exception；
4. 比较 heap、direct buffer、线程栈和 Metaspace 指标；
5. 关闭 Executor 后等待所有订单任务结束。

## 8. 掌握标准

- 能解释 heap、线程栈、Metaspace、直接内存和可达性。
- 能用 try-with-resources 正确管理 IO/JDBC 资源。
- 能识别静态集合、缓存、ThreadLocal、线程和类加载器泄漏。
