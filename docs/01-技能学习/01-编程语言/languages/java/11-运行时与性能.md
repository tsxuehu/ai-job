# Java：运行时与性能

Java 性能来自 JVM、JIT、GC、类加载、线程和操作系统共同作用；不能用源码行数猜测运行成本。

## 1. JVM 执行过程

```text
源码 → javac 字节码 → 类加载/验证/链接/初始化
→ 解释执行与 JIT 编译 → 本地机器码
```

类加载器定义类型身份；同名类由不同加载器加载也不是同一类型。初始化静态字段或代码块时要避免隐藏 IO、循环依赖和死锁。

JIT 根据运行热点优化、内联和逃逸分析，假设失效时可能去优化。基准需要预热，不能用一次调用衡量稳定性能。

## 2. GC 与性能指标

选择 GC 前先定义堆规模、吞吐、暂停和尾延迟目标。观察分配速率、存活集、晋升、停顿、CPU 和 native 内存，不根据一条 GC 日志调参数。

常见瓶颈包括算法、装箱、对象分配、序列化、锁竞争、连接池、日志和下游 IO。对象池和缓存可能增加存活集与复杂度。

## 3. 分析工具

- JFR/JMC：低开销事件、CPU、分配、锁和 IO 分析。
- 线程转储：死锁、阻塞、线程池饱和。
- 堆转储：对象占用、GC Roots 和保留链。
- GC 日志/native memory tracking：回收与堆外容量。
- JMH：可靠微基准，处理预热和无用代码消除。

## 4. 从订单热路径推导 JVM 行为

```java
orders.computeIfAbsent(id, this::loadOrder);
gateway.pay(order.id(), order.amountCents());
```

继续追问：lambda 是否分配/捕获？HashMap 是否扩容？接口调用是否内联？amount 是否装箱？线程是否等待连接池？对象是否短命并快速回收？答案可能随 JDK、热点和调用形态改变，因此用 JFR/JMH/GC 数据验证。

## 5. 类加载和动态特性也是成本

反射、代理、annotation processing、动态生成 class 和多个 classloader 会影响启动、Metaspace、类型身份和 native image。生产故障不只看 Java heap；线程、direct memory、code cache 和 native allocation 也可能成为上限。

## 6. 反射：从 Class 元数据找到成员并调用

Java 编译后的 class 文件保留类名、字段、方法、构造器和运行时注解等元数据。类被加载后，JVM 用一个 `Class<?>` 对象表示这些类型信息。

```text
Order.class / order.getClass()
→ Class<Order>
→ 查找 Constructor、Field、Method、Annotation
→ 读取字段、创建对象或调用方法
```

下面不依赖 Spring，直接观察 Java 反射：

```java
import java.lang.reflect.Constructor;
import java.lang.reflect.Field;
import java.lang.reflect.Method;

final class Order {
    private final String id;
    private String status;

    public Order(String id) {
        this.id = id;
        this.status = "pending";
    }

    public void markPaid() {
        status = "paid";
    }
}

public class ReflectionDemo {
    public static void main(String[] args) throws ReflectiveOperationException {
        Class<Order> type = Order.class;

        Constructor<Order> constructor = type.getConstructor(String.class);
        Order order = constructor.newInstance("order-1");

        Method method = type.getMethod("markPaid");
        method.invoke(order);

        for (Field field : type.getDeclaredFields()) {
            System.out.println(field.getName() + ": " + field.getType().getName());
        }
    }
}
```

普通调用 `order.markPaid()` 在编译期检查方法是否存在；`getMethod("markPaid")` 把方法名变成字符串，找不到成员、参数不匹配或目标对象错误时才在运行时失败。`invoke` 抛出的业务异常还会被包装，需要读取其 cause。

`getField/getMethod` 主要查找可访问的 public 成员；`getDeclaredField/getDeclaredMethod` 查看当前类声明的成员。private 不等于可以被框架随意突破：模块边界、访问控制、运行参数和部署方式都可能限制深反射。领域代码优先调用公开方法，不通过反射直接篡改 private 字段和对象不变量。

注解只是附着在程序元素上的元数据：

```java
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;
import java.lang.annotation.ElementType;

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.TYPE)
@interface OrderHandler {}

@OrderHandler
final class CreateOrderHandler {}

final class HandlerRegistry {
    static boolean isOrderHandler(Class<?> candidate) {
        return candidate.isAnnotationPresent(OrderHandler.class);
    }
}
```

`@OrderHandler` 不会自己注册对象。必须有启动代码或框架扫描 class，再读取注解并创建、保存实例。Spring 的组件扫描、ORM 映射和 JSON 序列化是在反射之上实现的工程能力，不是注解自动执行。

动态代理则是在运行时创建一个实现接口的代理对象，把方法调用交给 `InvocationHandler`。事务、权限、指标等横切逻辑常用代理实现，所以只有“经过代理对象”的调用才能被拦截；同类自调用绕过代理时，注解可能看起来存在却没有行为。

反射会减少编译期检查，也可能影响启动、优化、AOT/native image 和错误定位。框架边界可以使用，核心业务优先使用接口、普通方法、显式注册或编译期代码生成。

## 7. 先看服务，再做微基准

```text
服务指标/trace 找到高成本路径
→ JFR/async-profiler 找 CPU、分配、锁或 IO
→ 必要时 JMH 隔离微小实现
→ 回到服务负载验证 P99 和资源
```

JMH 数字不能证明整个服务更快；对象减少也可能换成锁竞争或更大存活集。

## 8. 与其他语言对照

| 语言经验 | JVM 中的差异 |
| --- | --- |
| C++/Go AOT | JVM 根据运行热点 JIT，存在预热、去优化和 code cache |
| Node V8 | 都有 JIT/GC，但对象模型、线程模型和诊断工具不同 |
| Python | CPython 常先受解释器/对象模型成本影响，JVM 热点能被 JIT 深度优化 |

## 9. 动手验证

1. 用 JFR 观察订单解析的 CPU、分配和锁事件；
2. 比较装箱 stream 与基本类型 stream；
3. 保存 thread dump 定位连接池等待而非 CPU 问题；
4. 用 heap dump 沿引用链找到 cache/ThreadLocal 保留；
5. 写 JMH 并设置预热，最后回到服务压测验证。
6. 用反射创建 Order、调用 `markPaid`，再故意写错方法名观察失败阶段。

## 10. 掌握标准

- 能解释类加载、解释器、JIT、去优化和 GC 的基本关系。
- 能从 `Class<?>` 解释字段、方法、注解和动态代理如何被运行时发现及调用。
- 能选择线程转储、堆转储、JFR、GC 日志定位不同问题。
- 性能结论包含预热、负载、P95/P99、资源和正确性回归。
