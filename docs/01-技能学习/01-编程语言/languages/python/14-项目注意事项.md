# Python：项目注意事项

目标：识别 Python 项目中的动态对象、可变性、异步阻塞、依赖环境和运行时边界，并把类型提示与真实运行时行为分清。

## 1. 名称绑定与可变对象

```python
def add_tag(tags: list[str] = []) -> list[str]:  # 错误：只创建一次
    tags.append("backend")
    return tags
```

默认参数在函数定义时求值一次，可变默认值使用 `None` 后在函数体创建。赋值只绑定同一对象，浅复制只复制外层；嵌套 list/dict 仍可能共享。

- `is` 判断身份，普通值比较使用 `==`。
- class 属性被所有实例共享，实例可变状态通常放在 `__init__`。
- 闭包捕获名称，循环创建 lambda 存在晚绑定问题。
- dataclass 的可变默认字段使用 `default_factory`。

## 2. 类型提示不做运行时校验

HTTP、JSON、环境变量、数据库和模型输出必须经过 schema/模型校验。`Any` 会向调用链扩散并关闭检查；`cast` 只通知类型检查器，不验证对象。动态插件/反射边界要保留明确的运行时协议检查。

`type`、`vars`、`getattr`、descriptor、装饰器和 `inspect` 的运行路径参见 [运行时与性能：内省与反射](11-运行时与性能.md#7-内省与反射对象在运行时保留丰富信息)。

## 3. async 中不能混入阻塞工作

```python
async def handle() -> Result:
    # 阻塞 SDK 应隔离到线程；CPU 计算使用进程/外部服务
    return await asyncio.to_thread(blocking_client.call)
```

- coroutine 必须 await 或创建受管理 Task；只调用 async 函数不会执行完成。
- 优先 TaskGroup，让子任务异常和取消有结构化边界。
- 不要吞掉 `CancelledError`；清理后通常继续传播取消。
- 同步数据库/HTTP SDK、文件 IO 和 CPU 循环会阻塞事件循环。
- semaphore/有界队列限制模型、HTTP、数据库并发。

## 4. GIL 不是线程安全保证

CPython GIL 通常限制多个线程同时执行 Python 字节码，但复合业务状态仍可能交错，native 扩展也可能释放 GIL。线程适合阻塞 IO，CPU 密集 Python 代码使用进程或 native/外部计算；进程间传输要考虑序列化和数据复制。

## 5. import、环境和资源

- import 会执行模块顶层代码；避免顶层连接数据库、网络调用和启动后台线程。
- 固定 Python、虚拟环境和完整依赖锁，不能用“我机器能 import”作为部署依据。
- 文件、HTTP client、数据库 session、线程/进程池使用 with/async with。
- 缓存、任务集合、模块全局、闭包和 native 库都可能长期占用内存。

## 6. 描述符、动态属性与插件

- `property`、descriptor 和 `__getattr__` 会改变普通属性访问的实际执行路径，避免隐藏网络或数据库 IO。
- decorator 保留 `__wrapped__` 和签名，事务、重试与缓存等关键行为要能从入口看见。
- import 会缓存模块并执行顶层代码；循环导入通常说明边界或初始化职责不清。
- 动态插件通过 Protocol/ABC、入口点和运行时校验建立边界，不让任意模块名直接来自用户输入。

## 7. 安全专项

- 不反序列化不可信 `pickle`；YAML 使用安全加载方式，JSON 仍需 schema 校验。
- 不把外部字符串交给 `eval`、`exec`、动态 import 或 `shell=True`。
- URL、重定向和代理目标使用 allowlist，防止 SSRF；文件路径验证不能逃出允许根目录。
- 上传、压缩包、模型输入和集合大小有总量、递归、时间与并发上限。
- 固定直接和传递依赖，生产从已验证 wheel/镜像安装，不依赖本地 editable path。

## 8. PR 必查

- [ ] 是否存在可变默认参数、共享 class 属性或错误浅复制？
- [ ] 外部数据是否运行时校验，Any/cast 是否掩盖边界？
- [ ] async 路径是否调用同步阻塞 SDK 或 CPU 密集代码？
- [ ] coroutine/Task 是否有人等待、取消并观察异常？
- [ ] CancelledError、超时和上下文管理器能否正确清理资源？
- [ ] import 是否产生隐藏副作用，依赖环境是否可复现？
- [ ] CPU、tracemalloc、RSS 和事件循环指标是否支持诊断？
- [ ] 是否避开不可信 pickle/eval/shell/import，并限制 URL、路径和输入总量？

## 9. 用故障反推规则

### 9.1 第二个请求带着第一个请求的数据

常见根因是可变默认参数、class 属性或共享 fixture/cache。先画名称到对象的绑定，确认对象在哪次定义时创建，而不是只在调用处加 copy。

### 9.2 async 服务 CPU 不高却所有请求卡住

事件循环线程进入同步 SDK、文件 IO、`time.sleep` 或阻塞锁。开启 asyncio debug/event-loop delay，定位阻塞调用并换异步库或隔离线程。

### 9.3 tracemalloc 稳定但 RSS 上涨

检查 native extension、mmap、allocator 保留、子进程和大 buffer。tracemalloc 只覆盖 Python 跟踪分配，不能据此否定进程内存问题。

### 9.4 类型检查通过，线上 JSON 仍报属性错误

标注/cast 没有校验数据。外部 object 先经过 runtime schema，再构造领域类型；测试非法/缺失/超大输入。

## 10. 专家级动手题

1. 为可变默认、闭包晚绑定和浅复制分别写失败测试；
2. 在 async 热路径注入阻塞并用 loop 证据定位；
3. TaskGroup 多失败和取消中验证所有上下文资源关闭；
4. 构建 wheel 在干净 venv 验证 import/资源；
5. 同时使用 CPU profile、tracemalloc、RSS 和下游 trace 诊断服务。

## 11. 掌握标准

- [ ] 能从名称、对象、可变性和协议推导运行结果；
- [ ] 类型标注、runtime schema 和测试各守不同边界；
- [ ] async Task 都有 owner、取消、等待和错误路径；
- [ ] 能区分 Python heap、native/RSS、IO 和事件循环阻塞；
- [ ] import、environment、wheel、依赖和资源生命周期可复现。
