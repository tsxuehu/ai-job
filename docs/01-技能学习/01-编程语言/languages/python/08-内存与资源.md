# Python：内存与资源

Python 实现通常结合引用计数和循环垃圾回收管理对象，但资源释放不能只依赖对象最终何时被回收。

## 1. 对象生命周期

- 名称和容器持有对象引用；对象无引用后通常可回收。
- 循环引用由 GC 辅助处理，但回收时机不是业务契约。
- `__del__` 有循环、异常和解释器退出问题，不作为主要资源管理方式。
- 模块全局、缓存、闭包、线程和长期任务会让对象持续可达。

不同 Python 实现的回收时机可能不同，因此“在 CPython 上立即关闭”不能作为可移植设计。

## 2. 上下文管理器

```python
with path.open(encoding="utf-8") as stream:
    return parse(stream)
```

`with` 通过 `__enter__/__exit__` 管理文件、锁、事务和临时状态；异步资源使用 `async with`。多个动态资源使用 `contextlib.ExitStack`/`AsyncExitStack`。

生成器、HTTP 响应、数据库 session/cursor、线程/进程池和异步 client 都要按契约关闭。异常和取消路径也必须执行清理。

## 3. 可变性与内存保留

小切片通常创建新 list，但内层对象仍共享；缓存需要容量和淘汰策略。队列、任务集合和结果列表无界增长是常见逻辑泄漏。

使用 tracemalloc 比较分配快照，memory profiler/系统指标观察进程和 native 扩展内存；Python heap 不等于 RSS。

## 4. 订单请求中的对象和资源

```text
Order/list/dict
→ 没有强引用后由实现决定回收

文件/HTTP response/DB transaction
→ with/async with 确定结束

Task/thread/process pool
→ 取消或停止、等待、观察错误
```

CPython 引用计数经常让对象“立即”销毁，但可靠代码不能把这种实现现象当文件/事务关闭合同。资源必须由上下文管理器或显式 owner 管理。

## 5. 引用图决定对象为何留下

```python
cache: dict[str, Order] = {}
listeners: list[Callable[[], None]] = []
```

模块全局、闭包、cache、Task、traceback 和容器都可能保留对象。tracemalloc 只能看到 Python allocator 跟踪的分配；RSS 增长也可能来自 native 库、mmap 或进程模型。

## 6. 与其他语言对照

| 语言经验 | Python 中的差异 |
| --- | --- |
| C++ RAII | Python with 提供代码块级确定清理，但普通对象析构时机不是跨实现合同 |
| Java/Go GC | 都按可达性回收；CPython 还常见引用计数的即时现象和循环 GC |
| Node.js | listener、closure、cache 同样形成逻辑泄漏；Python 还需关注 traceback/Task/native extension |

## 7. 动手验证

1. 创建循环引用并观察 GC，不依赖 `__del__` 做业务清理；
2. 让 traceback/Task 保留大对象，用 tracemalloc 查分配；
3. 用 ExitStack 管理动态数量资源并注入中途失败；
4. 对比 Python heap 与 RSS/native 数值；
5. 为 async client/pool 编写启动和关闭测试。

## 8. 掌握标准

- 能解释引用、循环 GC、可达性和回收时机边界。
- 能用 with/async with/ExitStack 管理同步与异步资源。
- 能定位缓存、任务、闭包、队列和 native 内存保留问题。
