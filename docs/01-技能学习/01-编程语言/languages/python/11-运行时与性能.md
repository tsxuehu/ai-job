# Python：运行时与性能

“Python 运行时”需要注明实现。后端最常见的是 CPython，其字节码执行、对象模型、引用计数、GC 和 GIL 共同影响性能。

## 1. 执行模型

- 源码编译为字节码，由解释器执行；导入缓存已加载模块。
- 几乎所有值都是对象，动态属性、协议调用和分配有成本。
- 普通 CPython 构建的 GIL 通常限制同一进程内多个线程同时执行 Python 字节码，但阻塞 IO 和部分 native 代码可释放它。
- Python 3.14 已正式支持 free-threaded 构建；使用前要单独验证扩展兼容性、线程安全和真实性能，不能把普通构建的结论直接套用。
- native 扩展可能持有堆外内存，也可能崩溃或阻塞运行时。
- 其他 Python 实现的 GC、JIT 和 GIL 行为可能不同，结论注明环境。

## 2. 常见热点

- 算法复杂度、Python 层大循环、重复序列化和对象创建。
- 同步阻塞进入事件循环、数据库 N+1、连接池和下游等待。
- 大量日志、无界缓存/队列、DataFrame/模型等 native 内存。
- 线程锁、进程序列化和任务粒度过小。

## 3. 分析方法

先记录吞吐、P95/P99、CPU、RSS、Python 分配、事件循环延迟和依赖时间。使用 cProfile/采样 profiler 找 CPU 路径，tracemalloc 看 Python 分配，asyncio 调试/指标看阻塞，系统工具看 native 与 IO。

下面先同时测量一次订单索引的耗时和 Python 分配峰值：

```python
import time
import tracemalloc

orders = [{"id": "o-1", "amount": 100}, {"id": "o-2", "amount": 200}]
tracemalloc.start()
started = time.perf_counter()
index = {order["id"]: order for order in orders}
elapsed_ms = (time.perf_counter() - started) * 1000
current, peak = tracemalloc.get_traced_memory()

print({"elapsed_ms": elapsed_ms, "peak_bytes": peak})
tracemalloc.stop()
```

这只用于发现可疑点，不是一次运行就下结论。CPU 热点可再用 `python -m cProfile -o profile.out app.py`；RSS 增长但 tracemalloc 稳定时，应继续检查 native 库、内存映射和进程模型。

优化顺序通常是算法和 IO → 批量化/缓存边界 → 成熟库/native → 进程或架构隔离。不要只因为“Python 慢”就重写服务。

## 4. 从订单热路径推导成本

```python
index = {order.id: order for order in orders}
receipt = await gateway.pay(order.id, order.amount_cents)
```

继续追问：创建了多少 dict entry/对象？`order.id` 是普通属性还是 property/descriptor？hash/eq 调用了什么？await 前是否有同步序列化？连接池等多久？运行时成本来自数据模型协议、对象分配、解释器、native 库和 IO 的组合。

## 5. 先优化层次，不先换语言

```text
算法/查询/N+1/重复 IO
→ 批量化和减少 Python 层循环
→ 使用成熟 C/native 实现的数据操作
→ 进程/服务隔离 CPU 工作
→ 证据仍不足时再评估重写热点
```

整体服务耗时如果主要在数据库，重写 Python 循环没有意义；若 profile 显示纯 Python CPU 热点，也应先检查算法和数据移动。

## 6. free-threaded 构建要单独评估

它不是“升级版本后所有线程自动更快”。扩展兼容、锁竞争、对象分配和工作负载都会影响结果。文档和 benchmark 必须注明 Python 实现、版本、是否启用 GIL、扩展版本和机器。

## 7. 与其他语言对照

| 语言经验 | Python 中的差异 |
| --- | --- |
| Java/V8 | 常见 CPython 没有同类热点 JIT 假设，动态对象操作成本模型不同 |
| Go/C++ | Python 解释器/对象层开销更显著，但大量工作可在 native 库完成 |
| Node.js | 都需监控事件循环阻塞；CPython 还需区分 GIL、进程和 native extension |

## 8. 动手验证

1. 用 `dis` 看属性访问/循环字节码，再用 profiler 找真实热点；
2. 比较 Python 循环、批量库和算法改进；
3. tracemalloc 稳定但 RSS 上涨时排查 native/mmap；
4. 在 async 服务注入同步 CPU/IO，观察 event-loop delay；
5. 保存解释器构建、数据集、并发、P99、CPU/RSS 和正确性。

## 9. 掌握标准

- 能解释 CPython 字节码、对象、GC、GIL 和 native 扩展边界。
- 能用 CPU、内存和事件循环工具定位不同瓶颈。
- 性能结论包含解释器版本、负载、尾延迟、资源和正确性验证。
