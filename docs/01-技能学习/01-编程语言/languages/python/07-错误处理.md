# Python：错误处理

Python 异常是正常的失败传播机制。可靠代码应捕获具体异常、保留原因链，并在请求或任务边界统一转换和记录。

## 1. raise 与异常链

```python
try:
    return repository.load(task_id)
except DatabaseError as exc:
    raise StorageError(f"load task {task_id}") from exc
```

- 只捕获能够恢复、转换或增加有效上下文的异常。
- `raise ... from exc` 显式保留 cause，裸 `raise` 重新抛当前异常。
- 自定义异常形成简洁领域层次，稳定字段用于程序判断。
- 不使用裸 `except:` 吞掉 KeyboardInterrupt/SystemExit 等控制信号。

## 2. try/except/else/finally

- `else` 只在 try 未抛异常时执行，可缩小受捕获代码范围。
- `finally` 总执行，用于无法由上下文管理器表达的清理。
- finally 中 return 会覆盖正常返回或异常，应避免。
- 多个并发任务同时失败时，理解 ExceptionGroup 和 `except*` 的边界。

## 3. 错误边界

领域异常在 HTTP/任务边界映射为外部状态，记录 traceback 和请求上下文但隐藏敏感信息。重试只针对明确瞬时错误，设置退避、次数和总体 deadline。

异步任务的异常保存在 Task 中，必须 await、任务组收集或显式回调观察；“创建后不管”会让错误与资源生命周期失控。

## 4. 订单结算如何保留异常链

```python
def checkout(order: Order, gateway: PaymentGateway) -> None:
    try:
        receipt = gateway.pay(order.id, order.amount_cents)
    except GatewayTimeout as exc:
        raise CheckoutError(f"pay order {order.id}") from exc
    order.mark_paid(receipt.id)
```

支付成功后才改变订单状态。`from exc` 保留根因；最外层 HTTP/任务入口记录一次完整 traceback 并映射稳定协议，内部层不要重复打印。

## 5. ExceptionGroup 对应并发的多个失败

TaskGroup 等结构化并发中，多个子任务可能在同一轮失败，Python 用 ExceptionGroup 保留全部异常。`except*` 按类型处理组内部分异常；不能只取第一个而丢失其他任务证据。

## 6. EAFP 仍需控制捕获范围

“先做、失败再捕获”不等于包住大段代码。try 只覆盖预期会产生该异常的操作，成功逻辑放在 else；否则同类型编程错误可能被误当业务分支。

## 7. 与其他语言对照

| 语言经验 | Python 中的差异 |
| --- | --- |
| Java | 没有 checked exception 声明；ExceptionGroup 可同时保留多个并发失败 |
| C++ | 都会栈展开；Python 清理通常用 context manager，析构时机不作资源合同 |
| Go | error 显式返回；Python exception 自动传播但仍需设计 cause 和边界 |
| Node | Promise 聚合失败与 ExceptionGroup 类似，具体聚合/取消规则不同 |

## 8. 动手验证

1. 比较 `raise`, `raise exc`, `raise NewError from exc` 的 traceback；
2. 缩小 try 范围，避免捕获同类型编程错误；
3. 在 TaskGroup 中让两个任务失败，使用 except* 检查全部原因；
4. 在 context manager 的 body 和 `__exit__` 同时失败，观察异常上下文；
5. 验证重试只覆盖幂等、瞬时失败且受总 deadline 限制。

## 9. 掌握标准

- 能捕获具体异常并用 cause 链保留来源。
- 能正确使用 else/finally，避免吞异常和重复日志。
- 能设计同步、异步和协议边界的错误转换与重试策略。
