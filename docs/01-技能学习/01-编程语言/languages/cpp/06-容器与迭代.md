# C++：容器与迭代

容器选择首先取决于访问模式、顺序语义和失效规则，其次才是理论复杂度。

## 1. 常用容器

| 容器 | 适合场景 | 主要代价或风险 |
| --- | --- | --- |
| `vector` | 默认动态序列、连续内存 | 扩容使指针、引用和迭代器失效 |
| `array` | 编译期固定长度序列 | 长度不能运行时变化 |
| `deque` | 两端插入、分段存储 | 不保证整体连续 |
| `list` | 节点稳定、频繁中间接合 | 额外分配且缓存局部性差 |
| `unordered_map` | 按键平均常数查找 | rehash、哈希质量、无稳定顺序 |
| `map` | 有序键、范围查询 | 节点开销和对数复杂度 |
| `set` / `unordered_set` | 去重、成员判断 | 与对应 map 相同的顺序和布局权衡 |

`vector` 通常是序列的默认选择。不要只因为中间插入理论上是常数复杂度就选择 `list`，真实性能还受分配和缓存影响。

## 2. 迭代器、算法与 ranges

```cpp
auto active = tasks
    | std::views::filter([](const Task& task) { return task.active(); });

for (const auto& task : active) {
    process(task);
}
```

- 标准算法表达“做什么”，通常比手写下标循环更易审查。
- `begin/end` 定义半开区间 `[first, last)`。
- ranges 视图通常惰性计算并借用底层数据，视图不能比数据活得更久。
- 修改容器前必须查清插入、删除和扩容的迭代器失效规则。

## 3. 复杂度与容量

区分 `size` 和 `capacity`；已知规模时可对 `vector` 或哈希表预留容量。预留是基于负载证据的优化，不应为了猜测的上限长期占用大量内存。

## 4. 易错点

- 遍历时删除元素，却错误递增已失效迭代器。
- `unordered_map` rehash 后继续使用旧迭代器。
- ranges 视图引用了临时容器。
- 用 `operator[]` 查询 map，意外插入默认值。

## 5. 一个订单索引的选择

```cpp
class OrderBook {
public:
    bool add(Order order) {
        auto id = order.id();
        return orders_.emplace(std::move(id), std::move(order)).second;
    }

    const Order* find(std::string_view id) const;

private:
    std::unordered_map<std::string, Order> orders_;
};
```

这里选择 hash map 是因为主要操作是按 ID 查询，且不承诺排序。`find` 返回观察指针时，必须说明：只要 map 被修改并触发 rehash，或 OrderBook 被销毁，调用方保存的地址就可能失效。更安全的 API 可以返回副本、在回调内借用或通过上层锁限定使用区间。

## 6. 失效规则比容器名称更重要

```text
vector 扩容        → 所有元素地址/引用/迭代器可能失效
vector 中间插入删除 → 插入点之后通常失效
unordered_map rehash → 迭代器失效；元素引用规则需查具体操作
erase              → 被删除元素相关引用必然失效
```

代码评审看到“先保存地址，再修改容器”时，必须立即检查规则。理论复杂度不能回答对象地址是否仍有效。

## 7. 与其他语言对照

| 语言经验 | C++ 中的差异 |
| --- | --- |
| Java/Python/Node.js 集合 | C++ 容器常直接存值，对象搬移和迭代器失效更显式 |
| Go slice | 都可能因扩容更换底层存储；C++ 还需遵守迭代器类别和失效合同 |
| Java Stream/Python generator | C++ ranges view 通常惰性借用源数据，不拥有源生命周期 |
