# C++：测试、调试与性能实践

目标：用测试和工具证明代码正确，定位崩溃、未定义行为与性能瓶颈。仓库结构、依赖和交付流程参见 [13-工程化](13-工程化.md)。

## 1. 单元测试要验证行为

下面使用 Catch2 表达订单规则；GoogleTest 写法不同，测试边界相同。

```cpp
TEST_CASE("order rejects non-positive amount") {
    const auto result = Order::create(OrderId{1}, Money{0});

    REQUIRE_FALSE(result.has_value());
    REQUIRE(result.error() == OrderError::invalid_amount);
}
```

断言稳定错误类型和可观察结果，不断言私有字段、完整日志文本或函数被调用了几次。值对象、状态机和算法测试不应启动数据库和网络。

## 2. 必测的 C++ 风险

- 复制、移动和析构后对象仍满足契约。
- 异常、早返回和取消路径没有资源泄漏。
- parser/协议面对空输入、超长输入和随机字节不会越界。
- 多线程测试反复运行，覆盖启动、停止、超时和竞争。
- 数据库和网络 adapter 使用真实协议验证部分读写与错误映射。

```cpp
TEST_CASE("worker stops before dependency is destroyed") {
    FakeQueue queue;
    Worker worker{queue};
    worker.start();
    worker.request_stop();
    REQUIRE(worker.wait_for(100ms));
}
```

## 3. 编译器和 sanitizer 是测试的一部分

```bash
cmake --preset debug
cmake --build --preset debug
ctest --preset debug --output-on-failure

cmake --preset asan
cmake --build --preset asan
ctest --preset asan --output-on-failure
```

ASan 查越界和 use-after-free，UBSan 查部分未定义行为，TSan 查实际执行路径上的数据竞争。不同 sanitizer 通常分开运行；没有报告不等于程序已被证明正确。

## 4. 调试顺序

1. 保存输入、commit、编译器、构建参数和依赖版本。
2. 使用 GDB/LLDB 读取崩溃栈、线程和 core dump。
3. 用 sanitizer 缩小内存、UB 或竞争问题。
4. 加最小回归测试，再修改实现。

Release 产物保留可匹配的调试符号；不要只在 Debug 构建复现性能问题。

## 5. 性能验证

```cpp
TEST_CASE("benchmark parsing") {
    const std::string payload = sample_order_json();
    BENCHMARK("parse order") { return parse_order(payload); };
}
```

基准使用优化构建，固定输入和机器，报告吞吐、P95/P99、分配、锁和系统调用。先用 profiler 找热点，再改算法、数据布局、复制或分配。

## 6. 从风险选择工具

| 风险 | 首选证据 |
| --- | --- |
| 订单状态规则 | 单元/属性测试 |
| SQL/HTTP/序列化 | 真实 adapter 集成测试 |
| 越界、悬垂、double free | ASan |
| 非法转换、溢出等 UB | UBSan |
| data race | TSan + 能产生重叠的并发测试 |
| 任意协议输入 | fuzz + sanitizer |
| CPU、cache、分配 | release benchmark + profiler |
| ABI/构建差异 | 多工具链构建与二进制兼容检查 |

测试框架只能断言业务结果；sanitizer 和编译器发现语言级风险；profiler 解释成本。它们不能互相替代。

## 7. Fuzz 和属性测试

parser 的目标不是只通过几个样例，而是对任意字节不越界、不死循环、不失控分配；合法输入还应满足 round-trip 或业务不变量。失败 corpus 应保存为回归测试。

```bash
./order_parser_fuzz -max_total_time=30 corpus/
```

## 8. 与其他语言对照

| 语言经验 | C++ 测试重点 |
| --- | --- |
| Java/Go/Python/Node | 除业务断言外，C++ 必须把 UB、内存和 ABI 工具纳入常规证据 |
| Java JMH/Go benchmark | C++ benchmark 必须使用优化构建并防止结果被优化器消除 |
| GC 语言资源测试 | C++ 还要验证 copy/move/destructor 和异常展开后的对象契约 |

## 9. 动手验证

1. 为 Order 构造、copy/move 和状态转换写测试；
2. 为 parser 建 fuzz target 并同时启用 ASan/UBSan；
3. 故意制造 race，让 TSan 报告后用同步修复；
4. 保存 core dump，用 LLDB/GDB 还原一次崩溃；
5. 对一个 profile 证明的热点做 benchmark 前后对比。

## 10. 掌握标准

- [ ] 关键规则有正常、边界和错误测试。
- [ ] ASan、UBSan、TSan 和严格警告进入独立 CI 任务。
- [ ] 能从 core dump、调用栈和 sanitizer 报告定位问题。
- [ ] 性能结论来自优化构建和可复现负载。
