# C++：错误处理

错误模型要先区分：调用方能够预期并处理的失败、当前层无法恢复的失败，以及违反程序不变量的缺陷。

## 1. 三类表达方式

| 方式 | 适合表达 | 注意事项 |
| --- | --- | --- |
| 返回结果/错误码 | 预期业务失败，调用方必须分支 | 需要携带类型和上下文 |
| `std::optional<T>` | 只有“有或没有”两种语义 | 无法说明失败原因 |
| 异常 | 当前层不能处理、需要跨层传播 | 建立异常边界，禁止析构抛出 |
| 断言 | 理论上不可能被破坏的不变量 | 不用于普通输入校验 |

C++23 提供 `std::expected<T, E>`；旧标准可使用团队统一的结果类型。

```cpp
std::expected<Config, ParseError> parse_config(std::string_view text);
```

## 2. 异常安全保证

- 基本保证：失败后对象仍有效，资源不泄漏。
- 强保证：失败后可观察状态与调用前相同。
- 不抛出保证：操作承诺不抛异常，析构函数通常必须满足。

“先构造新状态，再交换或提交”是实现强保证的常用手法。RAII 负责释放资源，但不自动恢复已经修改一半的业务状态。

## 3. 错误边界与上下文

- 在 HTTP、任务、线程和进程边界统一捕获未知异常，转换为稳定的外部响应。
- 每层只补充自己知道的上下文，避免重复记录同一个错误。
- 错误信息不得泄露密码、令牌和敏感数据。
- 重试必须基于错误类别，并带退避、次数和整体截止时间。

## 4. 易错点

- 捕获所有异常后静默忽略。
- 使用异常执行普通分支，或返回错误码却从不检查。
- 析构期间抛出第二个异常导致进程终止。
- 只记录文本，不保留可机器判断的错误类型。

## 5. 订单结算的错误边界

若“支付拒绝”是调用方必须分支处理的业务结果，可以返回类型化结果；连接失败等无法在当前层处理的问题可以异常传播。无论选哪种，全项目必须有一致约定。

```cpp
enum class PayError { rejected, unavailable, timed_out };

std::expected<Receipt, PayError> pay(const Order& order); // C++23
```

```cpp
void checkout(Order& order, PaymentGateway& gateway) {
    auto receipt = gateway.pay(order); // 可能抛系统异常
    order.mark_paid(receipt.id);        // 成功后才提交状态
}
```

顺序很关键：先完成可能失败的支付，再改变订单。若还涉及数据库，需要事务或补偿保证跨资源一致性，RAII 只能保证资源清理，不能自动实现业务原子性。

## 6. 异常展开时 RAII 做什么

异常离开作用域时，已经完整构造的局部对象逆序析构。因此锁、文件、事务 guard 和内存应由对象持有，不能散落 `try/catch` 手工清理。析构必须避免抛出；否则在另一个异常展开期间可能调用 `std::terminate`。

## 7. 与其他语言对照

| 语言经验 | C++ 中的差异 |
| --- | --- |
| Java/Python exception | 都能跨栈传播；C++ 还必须明确异常安全保证和析构行为 |
| Go error | 显式结果接近 `expected`；C++ 项目也可为预期失败采用结果类型 |
| Node Promise rejection | C++ 异步任务中的异常必须通过 future/task 边界取得，否则可能丢失或终止 |

## 8. 动手验证

1. 在支付、状态变更和保存三个位置注入失败，检查订单最终状态；
2. 给资源 guard 打印构造/析构，观察异常展开顺序；
3. 实现 basic guarantee 和 strong guarantee 两个更新函数；
4. 让析构函数抛异常，观察 terminate，并改为显式 close/commit；
5. 在 HTTP/线程入口捕获未知异常，映射稳定响应并记录一次。

## 9. 掌握标准

- 能为业务失败、系统失败和程序缺陷选择不同表达方式。
- 能说明函数提供哪一级异常安全保证。
- 能设计不丢上下文、可观测且不泄露敏感信息的错误边界。
