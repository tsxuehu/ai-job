# C++：运行时与性能

C++ 通常提前编译为机器码，没有语言级垃圾回收；但标准库、异常、RTTI、分配器、线程库和操作系统共同构成实际运行环境。

## 1. 执行模型与成本

- 自动对象按作用域逆序析构，动态对象由所有权对象决定释放时机。
- 虚函数通常动态分派；模板通常编译期实例化和单态化。
- 异常的常规路径成本取决于实现，但抛出和展开栈不是免费的。
- “零开销抽象”表示不用的能力不付费，不表示所有抽象都没有成本。
- 编译器优化可能改变指令布局，但不能修复未定义行为。

## 2. 主要性能因素

1. 算法复杂度和数据规模。
2. 数据布局、缓存局部性与内存带宽。
3. 动态分配、复制、虚调用和分支预测。
4. 锁竞争、线程调度、系统调用和网络等待。
5. 序列化、日志和跨进程边界。

连续容器常因缓存局部性优于节点容器；批量处理可减少调用和同步开销。SIMD、对象池、arena 和无锁结构只应在热点明确后使用。

## 3. 性能分析方法

```text
定义负载和指标 → 建立基线 → profiler 定位热点
→ 单变量修改 → 正确性回归 → 重新测量
```

同时记录吞吐、P50/P95/P99、CPU、内存、分配和队列等待。基准测试要防止编译器消除无用计算，并固定编译模式、机器和数据集。

## 4. 易错点

- 用 Debug 构建结果评价 Release 性能。
- 看到一次耗时就下结论，忽略预热、噪声和尾延迟。
- 为避免一次复制引入共享所有权，反而增加分配和同步。
- 优化单函数，却让整体 IO、锁竞争或数据布局更差。

## 5. 从订单热路径推导成本

```cpp
orders.emplace_back(id, amount);
gateway.pay(orders.back());
```

继续追问：vector 是否扩容并移动旧元素？string 是否分配？Order 是否满足 noexcept move？gateway 是虚调用还是已被去虚化？pay 内是否系统调用/锁等待？只有把源码连接到实际工作，profile 才能解释。

## 6. 优化器与未定义行为

as-if rule 允许编译器进行任何不改变有定义程序可观察行为的优化。若代码已触发 UB，编译器不必保留开发者直觉结果。性能实验必须先通过正确性、严格警告和 sanitizer 基线。

查看汇编可以解释局部优化，但不能替代服务级 CPU、cache miss、allocation、lock 和 IO profile。

## 7. RTTI：C++ 只有有限的运行时类型识别

先区分三个概念：

```text
虚函数多态：已经知道要调用 pay，只在运行时选择哪个实现
RTTI：询问一个基类引用实际指向什么派生类型
完整反射：按名字枚举字段和方法，并在运行时读写或调用
```

C++ 支持前两项，但标准 C++ 没有 Java、Go、Python 那种通用字段/方法反射。普通对象通常不会为了反射保留字段名和完整成员列表。

下面的基类至少有一个虚函数，因此是多态类型：

```cpp
#include <iostream>
#include <typeinfo>

struct PaymentGateway {
    virtual ~PaymentGateway() = default;
    virtual void pay() = 0;
};

struct AlipayGateway final : PaymentGateway {
    void pay() override { std::cout << "alipay\n"; }
    void verify_signature() const {}
};

void inspect(PaymentGateway& gateway) {
    std::cout << typeid(gateway).name() << '\n';

    if (auto* alipay = dynamic_cast<AlipayGateway*>(&gateway)) {
        alipay->verify_signature();
    }
}
```

执行过程可以简化为：

```text
PaymentGateway&
→ 对象携带的多态类型信息
→ typeid 得到实际类型
→ dynamic_cast 检查能否安全转换
→ 成功后才能使用 AlipayGateway 专有行为
```

需要注意：

- `gateway.pay()` 是普通虚函数多态，不是反射；调用方已经在源码中写明方法。
- `dynamic_cast<T*>(p)` 失败返回 `nullptr`；引用转换失败抛出 `std::bad_cast`。
- `typeid(...).name()` 的字符串由实现决定，不能作为稳定协议或持久化格式。
- 常见实现把动态类型信息关联到虚函数表，但标准只规定可观察行为，不保证具体内存布局。
- 禁用 RTTI 的构建选项会影响 `dynamic_cast` 和对多态对象使用 `typeid`，必须由整个项目统一决定。

如果项目需要序列化、命令路由或插件注册，常见做法是显式注册表、visitor、模板、代码生成或第三方元数据系统。模板和 Concept 属于编译期元编程，不等于运行时反射。业务分支能用虚函数、`std::variant` 或显式映射表达时，不要堆叠 `typeid` 判断。

## 8. 与其他语言对照

| 语言经验 | C++ 中的差异 |
| --- | --- |
| Java/V8 | C++ 通常 AOT 优化，没有相同的运行时 JIT 预热模型 |
| Go | 都生成本地代码；C++ 没有语言级 GC/调度器但有更多布局和 UB 控制 |
| Python | C++ 热点常在本地指令/缓存层，Python 热点常先受解释器和对象开销影响 |

## 9. 动手验证

1. 比较 vector 与 list 顺序处理订单的 cache/profile；
2. 为 vector reserve 前后测分配和耗时；
3. 比较按值、unique_ptr、shared_ptr 存储的布局和成本；
4. 用 perf/Instruments/profile 定位虚调用、锁或系统调用热点；
5. 保存编译器、flags、数据集和统计结果，验证优化前后正确性。
6. 分别用虚函数和 `dynamic_cast` 处理网关，说明哪个是在选择行为、哪个是在识别类型。

## 10. 掌握标准

- 能解释对象析构、虚函数、模板、异常和分配的主要成本。
- 能区分虚函数多态、RTTI 和完整反射，并知道标准 C++ 能提供什么。
- 能用 profiler 和基准数据定位瓶颈，而不是凭直觉改代码。
- 每个性能结论都包含环境、负载、统计数据和正确性验证。
