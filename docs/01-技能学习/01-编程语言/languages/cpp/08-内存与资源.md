# C++：内存与资源

C++ 的关键能力是确定性资源管理。内存只是资源的一种，文件、锁、连接、线程和临时状态都需要所有权。

## 1. RAII

RAII 在构造时取得资源，在析构时释放资源；离开作用域、早返回或抛异常时都执行清理。

```cpp
void write_file(const std::filesystem::path& path) {
    std::ofstream output(path);
    if (!output) throw std::runtime_error("open failed");
    output << "data";
} // output 在这里自动关闭
```

## 2. 所有权工具

| 工具 | 语义 | 使用建议 |
| --- | --- | --- |
| 局部/成员对象 | 作用域或宿主对象独占 | 默认选择 |
| `unique_ptr<T>` | 动态对象独占 | 动态生命周期或运行时多态 |
| `shared_ptr<T>` | 引用计数共享 | 确实存在共同生命周期 |
| `weak_ptr<T>` | 不拥有的共享观察者 | 打破引用环、检查是否存活 |
| 裸指针/引用 | 通常不拥有 | 短期观察且生命周期明确 |

不要用 `shared_ptr` 掩盖架构上不清楚的所有权；它带来原子计数、对象布局和生命周期推理成本。

## 3. 栈、堆与对象生命周期

“栈对象”通常随作用域销毁，“堆对象”由拥有它的 RAII 对象决定何时释放。业务代码优先使用容器、值对象和智能指针，不直接配对 `new/delete`。

第三方 C 资源应立即包装成只移动的 RAII 类型。资源类遵循 Rule of Zero；确需手写析构时再检查 Rule of Five。

## 4. 未定义行为与工具

常见问题包括越界、use-after-free、double free、未初始化读取、悬垂视图和 data race。它们可能在某次运行“看起来正常”，不能依赖复现概率判断正确性。

使用 AddressSanitizer、UndefinedBehaviorSanitizer 和泄漏检查验证；不能仅靠代码审查猜测。

## 5. 订单服务的所有权图

```text
ApiProcess
├── unique_ptr<HttpServer>
├── unique_ptr<DatabasePool>
└── unique_ptr<CheckoutService>
      └── PaymentGateway& / 明确受控的共享句柄

单次请求
├── Request/Order 值
├── transaction guard
└── 临时 buffer
```

长寿命组件由进程入口拥有，短寿命资源由请求栈上的 RAII 对象拥有，借用不得超过所有者。先画图再选智能指针；不是先用 shared_ptr 再猜谁负责结束。

## 6. Rule of Zero 让成员替你管理资源

```cpp
class OrderBatch {
    std::vector<Order> orders_;
    std::string source_;
};
```

这些标准成员已经正确实现复制、移动和析构，OrderBatch 通常不应手写五个特殊成员。只有直接包装 C handle 等资源时才写专用 RAII 类型，并让它不可复制、可移动、析构不抛异常。

## 7. 与其他语言对照

| 语言经验 | C++ 中的差异 |
| --- | --- |
| Java/Python/Go GC | C++ 作用域能确定析构时刻；所有权类型是设计的一部分 |
| Go defer | defer 是函数级清理；C++ RAII 与对象作用域/成员层级组合 |
| Node listener/handle | 两者都会因隐藏引用延长生命周期；C++ 还可能出现悬垂和 double free |

## 8. 动手验证

1. 用 unique_ptr、shared_ptr、weak_ptr 画同一对象图并选择最窄语义；
2. 创建 shared_ptr 引用环，再用 weak_ptr 打破；
3. 包装一个 C FILE/handle 为只移动 RAII 类型；
4. 在多个异常点注入失败，打印析构顺序；
5. 用 ASan/LSan 验证 use-after-free、double free 和泄漏。

## 9. 掌握标准

- 能画出对象、文件、连接和线程的所有权图。
- 异常和提前返回时，资源仍能正确释放。
- 能使用 RAII 和智能指针修复泄漏、悬垂与共享引用环。
