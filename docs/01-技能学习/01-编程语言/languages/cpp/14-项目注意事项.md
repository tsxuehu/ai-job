# C++：项目注意事项

目标：识别 C++ 项目中特有的所有权、生命周期、未定义行为、ABI 和运行时成本风险，并把它们落实为评审与诊断规则。

## 1. C++ 项目的核心心智模型

```text
对象由谁拥有
→ 哪些位置只是借用
→ 借用能持续多久
→ 资源如何确定释放
→ 代码以什么编译/链接配置进入最终程序
```

## 2. 项目中最需要注意的事项

| 事项 | 为什么特殊 | 项目做法 |
| --- | --- | --- |
| 所有权不写在统一类型系统里 | 裸指针、引用可能拥有，也可能只观察 | 字段和签名约定：值/`unique_ptr` 拥有，引用/裸指针默认不拥有 |
| 视图可能悬垂 | `string_view`、`span`、迭代器不延长底层寿命 | 不返回局部对象视图，不让视图进入比数据更长的异步任务 |
| 容器扩容使引用失效 | `vector` 扩容会移动存储 | 修改容器前检查 invalidation 规则，不能保留旧地址 |
| 未定义行为不保证复现 | 越界、data race 等可能在优化后表现完全不同 | CI 分别运行 ASan、UBSan、TSan，并开启严格警告 |
| RAII 与异常安全 | 资源能自动释放，但业务状态可能修改一半 | 资源全部 RAII；状态更新采用先构造、后提交 |
| 多态析构 | 通过基类指针删除派生对象需要虚析构 | 多态基类声明 `virtual ~Base() = default` |
| ABI 与编译配置 | 编译器、标准库、宏和选项会改变二进制边界 | 固定工具链、运行库和关键编译选项；跨边界保持窄接口 |
| ODR 与静态初始化 | 多份定义或跨文件初始化顺序会产生隐蔽故障 | 减少全局对象，理解 inline/模板定义位置 |

## 3. 异步任务中的生命周期

```cpp
auto service = std::make_shared<Service>();

executor.submit([service, request = std::move(request)] {
    service->handle(request);
});
```

- 按引用捕获局部变量后异步执行，任务开始时对象可能已经销毁。
- 捕获 `this` 不拥有当前对象；必要时由明确拥有者等待任务结束，或捕获受控的共享所有权。
- 不要把所有对象都改成 `shared_ptr`。默认仍应是值和 `unique_ptr`，共享所有权只用于真实的共同生命周期。
- 关闭顺序通常是：停止接收 → 通知任务 → 等待线程 → 再销毁任务依赖。

## 4. 构建也是语言语义的一部分

C++ 项目必须记录：语言标准、编译器、标准库、Debug/Release 选项、异常/RTTI 策略、依赖版本、目标架构和 sanitizer 构建方式。头文件、宏和编译选项不一致可能让相同源码产生不兼容类型或 ABI。

RTTI 能力边界和 `typeid/dynamic_cast` 用法参见 [运行时与性能：RTTI](11-运行时与性能.md#7-rttic-只有有限的运行时类型识别)。

## 5. 安全专项

- 所有外部长度、索引、整数转换和分配大小先校验，避免溢出后产生越界。
- 不把不可信文本直接拼进 SQL、shell、路径和格式字符串；使用参数化 API 和明确 allowlist。
- parser、压缩包、图片和协议输入设置总量、递归深度、超时并运行 fuzz/sanitizer。
- 第三方 C/C++ 库通过窄 RAII wrapper 隔离所有权、错误、线程和 ABI。
- 生产构建启用适用的平台加固选项，依赖和编译产物保持可追溯。

## 6. PR 必查

- [ ] 新增指针、引用和视图的所有者与有效期是否明确？
- [ ] 异步回调是否捕获了可能提前销毁的对象？
- [ ] 容器修改后是否继续使用旧迭代器、引用或地址？
- [ ] 异常和早返回是否仍保持资源与业务状态正确？
- [ ] 多态基类是否能被安全析构，复制/移动行为是否合理？
- [ ] 新依赖和编译选项是否影响 ABI、产物和部署环境？
- [ ] 内存、未定义行为和并发检测是否覆盖新增路径？
- [ ] 不可信长度、路径、格式字符串和整数转换是否经过边界校验？

## 7. 用故障反推规则

### 7.1 Release 偶发错误，Debug 正常

首先怀疑未定义行为、竞争、未初始化读取和生命周期，而不是给 Release 增加 sleep。保存生产 flags 和输入，运行匹配优化级别的 sanitizer/调试符号构建。

### 7.2 vector 增加元素后旧对象地址崩溃

扩容搬迁了存储，旧指针/引用失效。修复不是盲目 reserve 一个“足够大”数字，而是重新设计借用区间、使用稳定句柄或在修改后重新查找。

### 7.3 服务停机时偶发 use-after-free

依赖先析构，后台任务仍捕获 this/引用。入口必须停止生产、请求停止、等待全部任务，再按依赖逆序销毁。

### 7.4 内存不降但没有裸 new

可能是 shared_ptr 环、容器容量、缓存或仍运行任务保留对象。用 heap/引用图定位所有者，不能因为使用智能指针就断言没有逻辑泄漏。

## 8. 专家级动手题

1. 为订单服务画完整所有权和借用图；
2. 制造 vector 失效、string_view 悬垂和 shared_ptr 环，分别用工具定位；
3. 建立 ASan/UBSan/TSan 三条独立 CI 配置；
4. 审查一个动态库 API 的 allocator、异常、RTTI、所有权和 ABI；
5. 让 worker 在停机中访问已销毁依赖，再重构关闭顺序并加回归测试。

## 9. 掌握标准

- [ ] 每个资源只有明确所有者，每个借用都有有效期；
- [ ] 能从 copy/move/destructor、容器失效和异常展开推导结果；
- [ ] UB、内存和 data race 都有工具化检查；
- [ ] target、头文件、宏、编译选项和 ABI 可追踪；
- [ ] 能把生产故障沉淀成测试、sanitizer、静态规则或工程边界。
