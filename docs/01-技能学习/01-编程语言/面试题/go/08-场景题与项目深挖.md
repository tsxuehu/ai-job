# Go 面试题：场景题与项目深挖

## 1. 设计一个有界 worker pool，需要考虑什么？

**答案：**

- 固定或可控的 worker 数量，不为每个输入无界启动 goroutine。
- 有界队列和满载策略：等待、拒绝、降级或丢弃。
- context 取消与 deadline 传播。
- 任务 panic 边界、错误收集和局部失败策略。
- 输入 channel 由谁关闭，worker 何时退出，谁等待全部结束。
- 队列深度、等待时间、处理时间、失败率和活跃 worker 指标。

资深面试会追问：下游只有 20 条数据库连接时，为什么开 1000 个 worker 不会更快？

## 2. 线上 goroutine 数从 500 增长到 50 万，怎么排查？

**答案：**

1. 确认增长时间、版本、流量和下游故障的关联。
2. 及时限流、摘除问题实例或回滚，先防止内存和连接耗尽。
3. 采集 goroutine profile，按重复栈聚合，找最大的阻塞类别。
4. 检查 channel send/receive、锁、下游 IO、重试循环、timer 和 context 取消路径。
5. 用取消、超时和优雅停机测试复现，修复后增加回归测试和告警。

只用 `runtime.NumGoroutine()` 不能找到根因，关键是栈分类、任务所有者和缺失的退出路径。

## 3. API P99 突然升高，但 CPU 不高，怎么分析？

**答案：**

先拆分请求时间，查看数据库和 HTTP 连接池等待、下游延迟、队列深度、锁竞争、goroutine 阻塞和 GC 事件。CPU 不高常说明任务在等待，不代表服务没有瓶颈。

使用 trace 和 block/mutex profile 分析串行化和阻塞，用分布式追踪确认时间花在哪个下游。同时检查是否有超时后重试风暴放大排队。

## 4. 支付接口如何防止重复扣款？

**答案：**

客户端为一次业务操作提供稳定幂等键，服务端通过唯一约束或幂等表原子记录请求状态和结果。相同键与相同请求重复到达时返回已有结果；相同键却参数不同时拒绝。

支付有明确状态机，不从未知结果直接盲目再扣款。调用第三方支付时向下传递稳定业务号，并通过主动查询、回调验签和对账任务处理超时后的未知状态。

## 5. 服务发布时仍有队列任务，如何停机？

**答案：**

先停止获取新任务，再等待已经开始的任务完成或在 deadline 内安全中断。消息确认只能在业务结果已持久化后执行；未完成任务不确认，让它之后重新投递。

任务必须幂等，因为进程可能在任何时候被强制终止。停机期间记录处理中任务、剩余队列和超时数，不把“优雅停机”假设为绝对成功。

## 6. 面试官追问“你做过的最难 Go 项目”，怎么回答？

**答案：**

用数据和取舍回答，不只列技术名词：

```text
业务和规模：吞吐、P99、数据量、实例数
→ 你负责的边界
→ 问题的证据和根因
→ 为什么选择当前方案
→ 放弃了什么，付出了什么代价
→ 上线后的数据变化
→ 如果重做会改什么
```

“用了 Redis、Kafka、Kubernetes”不能证明资深。能说明故障模式、容量、指标、回滚、数据一致性和方案代价，才能体现完整工程判断。
