# Go 面试题：工程化与测试

## 1. Go package 应该怎么划分？

**答案：**

按稳定责任和业务能力划分，使 package 内高内聚，对外 API 小且清晰，导入图无环。不要盲目把 Java 的 controller/service/repository 平铺成全局技术层，使一个业务修改横跨大量无关 package。

资深回答应说明依赖方向：核心业务不直接依赖 HTTP、数据库驱动和第三方 SDK，而是由边界适配它们。

## 2. `internal` 目录解决什么问题？

**答案：**

Go 工具链会限制 `internal` 下的 package 只能被指定父目录子树中的代码导入。它用来明确仓库或模块的私有实现边界，避免其他模块偶然依赖内部细节。

`internal` 不能代替合理的 package 设计。将整个仓库都放进 internal 仍然可能形成巨大、循环倾向和难以测试的模块。

## 3. interface 应该定义在提供方还是消费方？

**答案：**

通常定义在消费方，由调用者说明自己真正需要的最小能力。例如 Checkout 只需要 `Pay`，就不应该依赖支付 SDK 的几十个方法。

不要为每个 struct 提前建一个同名 interface。只有出现真实替换边界、多实现或测试隔离需求时，才抽取消费方需要的小接口。

## 4. 错误如何跨分层传播？

**答案：**

底层保留可诊断 cause，业务层转换为稳定业务语义，传输层再映射为 HTTP/gRPC 状态和对外错误码。对外不泄露 SQL、磁盘路径、签名密钥和内部堆栈。

不要在每一层同时“打日志再返回”，否则同一错误会重复记录。在有 request/trace 上下文且决定最终响应的边界记录通常更合适。

## 5. Go 项目需要哪些测试？

**答案：**

- 单元测试：纯业务规则、边界值和错误语义。
- 集成测试：真实数据库、消息、HTTP 协议和事务。
- 契约测试：服务边界的请求、响应和兼容性。
- 并发测试：取消、超时、关闭、竞争和泄漏。
- benchmark：热点路径的耗时和分配回归。
- fuzz：解析器、协议、序列化和不可信输入。

测试重点是证明对外行为，不是将私有实现每一行锁死。

## 6. `go test -race` 能证明没有并发问题吗？

**答案：**

不能。race detector 会检查实际执行到的内存访问，能找到许多真实数据竞争，但未覆盖的路径、时序和生产负载仍可能有问题。

在 CI 中运行核心测试的 race 版本，并通过高并发、重复执行、取消和停机场景扩大覆盖面。race 测试成本更高，不用其吞吐数据代表生产性能。

## 7. Go module 如何保证可重复构建？

**答案：**

`go.mod` 声明模块、Go 版本和依赖，`go.sum` 记录模块内容校验。CI 中固定 Go 工具链，检查 `go mod tidy` 后无未提交变化，使用代码评审和安全工具治理依赖升级。

不要把 GOPROXY 当成完整的依赖安全方案。企业还需要私有代理、依赖来源策略、漏洞扫描、许可证检查和可追溯构建产物。

## 8. Go 服务应该有哪些可观测性？

**答案：**

- 结构化日志：请求 ID、Trace ID、操作、结果和稳定错误码。
- 指标：吞吐、错误率、P50/P95/P99、队列、连接池、goroutine、GC 和下游耗时。
- 追踪：跨 HTTP、RPC、消息和数据库的调用链。
- 诊断：受保护的 pprof、运行时指标和必要的故障快照。

高基数字段不应成为指标 label，密钥、Token、完整请求体和隐私数据不应写入普通日志。
