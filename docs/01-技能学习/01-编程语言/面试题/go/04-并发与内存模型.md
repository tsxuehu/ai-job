# Go 面试题：并发与内存模型

## 1. goroutine 和操作系统线程有什么区别？

**答案：**

goroutine 是 Go 运行时调度的并发任务，不是一对一的 OS 线程。它的初始栈较小并可增长，大量 goroutine 可以复用较少的 OS 线程。

goroutine “便宜”不代表可以无限创建。每个 goroutine 仍然持有栈、调度状态和可能的引用；无界创建会造成内存、排队和下游资源压力。

## 2. G、M、P 分别是什么？

**答案：**

- G 表示 goroutine 及其执行状态。
- M 表示执行 Go 代码的操作系统线程。
- P 持有执行 Go 代码所需的调度资源和本地可运行队列。

调度器将 G 安排到持有 P 的 M 上执行，并使用本地队列、全局队列和任务窃取等机制平衡工作。G-M-P 是运行时实现模型，不应把某一版本的每个细节当成语言保证。

`GOMAXPROCS` 主要决定同时执行 Go 代码所需的 P 数量。它不是 goroutine 数量上限，也不代表进程绝对不会拥有更多 OS 线程。

## 3. 无缓冲 channel 和有缓冲 channel 有什么区别？

**答案：**

无缓冲 channel 的发送和接收需要彼此配对，完成一次同步交接。有缓冲 channel 在队列未满时发送可以先完成，队列非空时接收可以先完成。

缓冲大小是背压和容量设计，不是“越大越快”。缓冲过大会隐藏下游变慢，提高内存使用和任务等待时间。

## 4. channel 由谁关闭？关闭后会怎样？

**答案：**

通常由“确定不会再发送数据的一方”关闭，常见是拥有发送生命周期的发送方。接收方不应因为“不想收了”就关闭 channel，应通过 context 或单独信号通知取消。

- 重复关闭 channel 会 panic。
- 向已关闭 channel 发送会 panic。
- 关闭后仍可读取已缓冲数据；耗尽后立即返回零值与 `ok=false`。

## 5. nil channel 和 closed channel 有什么不同？

**答案：**

对 nil channel 发送或接收会永久阻塞，关闭 nil channel 会 panic。对已关闭 channel 接收会立即完成，向它发送会 panic。

nil channel 在 `select` 中可用来动态关闭某个 case，因为该 case 永远不会就绪。这种技巧要配合清晰命名，否则容易形成难以排查的永久阻塞。

## 6. `select` 如何选择 case？

**答案：**

只有一个 case 就绪时执行它；多个 case 同时就绪时，Go 会从中选择一个，不应依赖固定优先级。没有 case 就绪且存在 `default` 时，立即执行 `default`；否则阻塞等待。

在高频循环中使用 `default` 可能形成忙等并占满 CPU。超时和取消通常应监听 timer 或 `ctx.Done()`。

## 7. 什么时用 channel，什么时用 Mutex？

**答案：**

channel 适合传递任务、结果和所有权，以及协调任务生命周期。Mutex 适合保护一小段共享内存不变式。

不要把“不要通过共享内存通信”误解为禁止用锁。一个简单计数器或 map 用锁保护往往更清晰；一条任务流则更适合 channel。

## 8. `RWMutex` 一定比 `Mutex` 快吗？atomic 呢？

**答案：**

不一定。`RWMutex` 在读操作占绝大多数、临界区合适且竞争明显时可能受益，但它的状态和调度成本更高。应通过 benchmark 和 mutex profile 验证。

atomic 适合简单独立状态，例如计数器和状态位。多个字段需要一起满足不变式时，使用锁通常更正确。无锁不等于更简单或一定更快。

## 9. `WaitGroup` 有哪些常见错误？

**答案：**

- 在 goroutine 启动后才 `Add`，与 `Wait` 形成竞争。
- 忘记 `Done`，导致永久等待。
- `Done` 次数超过 `Add`，计数器变成负数并 panic。
- 复制已经使用的 WaitGroup。
- 只等待结束，却没有收集错误和取消其他任务。

需要“子任务失败后取消同组任务”时，应在 WaitGroup 之外设计 context 和错误传播，或使用类似 errgroup 的结构化并发方式。

## 10. `context.Context` 是做什么的？

**答案：**

Context 用来在请求调用链中传播截止时间、取消信号和少量请求级元数据。它不会强行杀死 goroutine；函数和底层 IO 必须主动监听 `ctx.Done()` 或接收 context。

常见约定：

- `ctx` 放在第一个参数，不存入长期结构体。
- 不传 nil context；不确定时使用 `context.Background()` 或 `context.TODO()`。
- 创建 cancel/timeout context 后调用 `cancel`，及时释放 timer 和关联资源。
- `Value` 不用来传递普通业务参数和可选配置。

## 11. 什么是 goroutine 泄漏？

**答案：**

goroutine 已经失去业务价值，但仍永久阻塞或运行，无法退出，就是 goroutine 泄漏。常见原因包括：

- 向没有接收者的 channel 发送。
- 等待永远不会关闭的 channel。
- 忽略 context 取消。
- 网络和下游调用没有超时。
- 后台 ticker、worker 和重试循环没有停止路径。

排查时看 goroutine 数趋势、goroutine profile 中重复的阻塞栈，并在测试中取消请求、关闭服务后验证任务能退出。

## 12. 如何实现有界并发和背压？

**答案：**

使用固定数量 worker、有界任务队列，或在启动任务前获取信号量。当下游处理不过来时，上游必须等待、拒绝、降级或按明确策略丢弃，不能无限堆积内存任务。

资深回答还要说明：并发上限应根据 CPU、下游连接池、平均耗时和容量目标确定；任务必须有取消、结果观察和停机等待路径。

## 13. 什么是 data race 和 happens-before？

**答案：**

两个 goroutine 并发访问同一内存位置，至少一个是写操作，且没有适当同步，就形成 data race。happens-before 关系用来说明一个 goroutine 的写入何时保证能被另一个 goroutine 观察。

使用 channel 操作、Mutex、Once、atomic 等同步原语建立关系。`go test -race` 可以检测实际执行路径上的竞争，但没报错不能证明所有路径都没有竞争。
