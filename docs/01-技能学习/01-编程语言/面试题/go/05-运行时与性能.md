# Go 面试题：运行时与性能

## 1. 栈和堆由谁决定？基础类型也会逃逸吗？

**答案：**

编译器根据值的生命周期和使用方式做逃逸分析，而不是由代码语法直接选择栈或堆。

- 只在当前函数使用的值通常可以在栈上。
- 返回局部值的指针、被长期闭包捕获或交给更长生命周期对象的值可能逃逸。
- `int` 等基础类型也可以逃逸；使用指针则不等于一定逃逸。

可用 `go build -gcflags="-m=2" .` 观察编译器报告，但只在 profile 证明分配是瓶颈时才进行针对性优化。

## 2. Go GC 解决了什么？没解决什么？

**答案：**

GC 负责回收已经不可达的堆对象，降低手工释放内存的风险。它不会自动关闭文件、socket、Response Body、数据库连接、ticker 和 goroutine。

GC 压力与分配速率、存活堆大小和对象可达性有关。优化时先看分配 profile、GC 指标和端到端延迟，不要看到 GC 就盲目调参。

## 3. 有 GC 为什么仍然会内存泄漏？

**答案：**

只要对象仍被可达的 map、slice、缓存、闭包或 goroutine 引用，GC 就不能回收。常见案例是无界缓存、队列堆积、截取小 slice 却保留超大底层数组，以及泄漏 goroutine 保留整条对象链。

还要区分 Go heap 与进程 RSS。线程栈、mmap、cgo/native 库和内核缓冲等可能让 RSS 增长，但不体现为普通 Go heap 对象增长。

## 4. `sync.Pool` 适合做什么？

**答案：**

`sync.Pool` 用来临时复用可随时重建的对象，以降低高频分配压力。Pool 中对象可在任意时候被移除，因此不能用来保存必须存在的缓存数据、连接或业务状态。

放回 Pool 前要重置状态，避免数据泄漏和大对象长期保留。引入 Pool 前应使用 benchmark 和 alloc profile 证明它真的有收益。

## 5. pprof 中常见 profile 分别看什么？

**答案：**

- CPU：程序消耗 CPU 的主要路径。
- heap：当前存活堆对象的采样，常用于分析内存保留。
- allocs：累计分配，用于找高分配路径。
- goroutine：当前 goroutine 栈，用于找阻塞和泄漏。
- mutex：锁竞争等待。
- block：channel、锁等阻塞事件。

先确认问题类型再选 profile。CPU 问题不用 heap profile 猜，内存增长也不只看累计 allocs。

## 6. pprof 和 execution trace 有什么区别？

**答案：**

pprof 主要回答“成本花在哪些调用路径”，适合 CPU、分配、内存保留、锁和阻塞分析。execution trace 记录一段时间中的调度、goroutine 状态、系统调用、GC 和处理器利用等时序事件。

常见顺序是先用服务指标和 pprof 找大头，需要理解调度、串行化和延迟时序时再使用 trace。同时开启多种高成本诊断可能相互干扰。

## 7. 如何写可信的 benchmark？

**答案：**

固定输入和环境，把准备工作排除在计时区间外，用 `b.ReportAllocs()` 观察分配，并防止结果被编译器完全消除。多次运行并使用统计工具比较，不用单次纳秒数据得出架构结论。

微基准只回答局部问题。优化后还要验证真实负载下的吞吐、P95/P99、CPU、内存和正确性。

## 8. Go 1.27 的 goroutine leak profile 有什么价值？

**答案：**

Go 1.27 将 `goroutineleak` profile 正式开放，用于识别永久阻塞、可判定为泄漏的 goroutine。它能帮助从大量正常等待的 goroutine 中突出可疑泄漏。

工具不代替生命周期设计。仍要为每个后台任务定义所有者、取消信号、结果观察、超时和停机等待。
