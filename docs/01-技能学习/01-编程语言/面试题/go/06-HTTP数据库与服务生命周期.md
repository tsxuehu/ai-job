# Go 面试题：HTTP、数据库与服务生命周期

## 1. `http.Client` 应该每次请求新建吗？

**答案：**

不应该。`http.Client` 和其 `Transport` 设计为可复用并支持并发调用。频繁新建 Transport 会丢失连接池复用，增加 DNS、TCP、TLS 和 socket 成本。

通常为不同下游配置长期客户端，设置合理的连接池、空闲连接、各阶段超时和可观测性，而不是所有下游共用一份不受控配置。

## 2. HTTP 超时应该设在哪些层次？

**答案：**

需要区分整体请求 deadline 和 DNS、建连、TLS、等待响应头、读写 body 等阶段超时。服务端还要设置读请求头、读请求、写响应和空闲连接边界。

只设一个很大的总超时可能无法快速区分哪一阶段卡住。外层 context deadline 应向下游传播，内层不能创建比上层剩余时间更长且不受控的请求。

## 3. HTTP Response Body 为什么要关闭？

**答案：**

Response Body 背后持有网络连接和读取状态。忘记关闭会泄漏连接与文件描述符，并最终耗尽连接池。

在需要复用 HTTP/1.x 连接的场景，还通常要把 body 读到 EOF 后关闭。对大 body 不应为了复用连接而无上限丢弃读取，应设置大小上限并在超限时放弃连接复用。

## 4. Go HTTP 服务如何优雅停机？

**答案：**

1. 收到停机信号后先进入不就绪状态，从流量入口摘除。
2. 调用 `Server.Shutdown` 停止接收新连接，等待正在处理的请求。
3. 取消后台 worker、消费者和定时任务，等待 goroutine 退出。
4. 停止时要有总 deadline；超时后记录未完成工作并进入明确的强制终止策略。
5. 最后关闭不再被使用的数据库、消息客户端和观测出口。

仅调用 `Shutdown` 不会自动停止与 HTTP Server 无关的后台 goroutine。

## 5. `sql.DB` 是一条数据库连接吗？

**答案：**

不是。`sql.DB` 是可并发使用的连接池句柄，应长期复用。`sql.Open` 成功不一定代表已建立连接，需要时使用 `PingContext` 验证配置和可达性。通过 `SetMaxOpenConns`、`SetMaxIdleConns`、`SetConnMaxLifetime` 和 `SetConnMaxIdleTime` 约束连接。

池不是越大越好。需要同时考虑数据库总连接上限、服务实例数、请求并发和查询耗时，并监控池等待、使用中连接和查询延迟。

## 6. 使用 `Rows` 有哪些常见错误？

**答案：**

- 忘记 `defer rows.Close()`，导致连接不能及时返回池。
- 只检查 `Scan` 错误，却忘记循环结束后检查 `rows.Err()`。
- 无上限读取大结果集到内存。
- 在迭代期间做长时间外部调用，长期占用连接。
- 没有传入可超时、可取消的 context。

## 7. 事务的安全写法是什么？

**答案：**

开启事务后立即安排 `Rollback`，中间任何失败直接返回，最后显式检查 `Commit` 错误。事务已提交后的 Rollback 通常不会再改变结果。

```go
tx, err := db.BeginTx(ctx, nil)
if err != nil {
	return err
}
defer tx.Rollback()

// 所有相关 SQL 都通过 tx 执行

return tx.Commit()
```

事务尽量短，不在事务内执行不受控的 HTTP 调用、人工等待和长时间计算。

## 8. 超时和重试为什么必须与幂等一起设计？

**答案：**

超时只能说明调用者没有在期限内得到结果，不代表服务端一定没有执行成功。如果盲目重试支付、创建订单或发消息，可能造成重复扣款和重复数据。

通过幂等键、唯一约束、状态机或幂等记录使重复请求得到同一结果。重试只针对明确的瞬时错误，使用次数上限、指数退避和随机抖动，并尊重整体 deadline。
