# Go 面试题：错误、defer 与资源

## 1. Go 为什么把 error 设计成普通值？

**答案：**

`error` 是只含 `Error() string` 的接口。失败作为普通返回值，迫使调用者在当前控制流中选择处理、转换或传播。

项目中应让错误保留“发生了什么”和“原因是什么”，但不要在每一层重复记录同一个错误。日志通常在拥有请求上下文和最终处理责任的边界记录。

## 2. `%w`、`errors.Is` 和 `errors.As` 怎么使用？

**答案：**

`fmt.Errorf("load order: %w", err)` 保留原错误链。`errors.Is` 判断错误链中是否包含某个目标错误；`errors.As` 取出错误链中的某种具体错误类型。

```go
if errors.Is(err, sql.ErrNoRows) {
	return ErrOrderNotFound
}
```

不要通过比较 `err.Error()` 字符串判断错误类型，字符串是给人看的，不是稳定协议。

## 3. `defer` 什么时执行？参数什么时求值？

**答案：**

defer 在当前函数即将返回时执行，多个 defer 按后注册先执行的顺序运行。普通 defer 调用的函数值和实参在执行 defer 语句时就会求值。

```go
name := "pending"
defer fmt.Println(name)
name = "paid"
// 最后打印 pending
```

闭包 defer 则可以在实际执行时读取外层变量，需要明确两者区别。

## 4. defer 能修改命名返回值吗？

**答案：**

可以。返回值赋值后、函数真正返回前会执行 defer，闭包可以修改命名返值。这常用于合并 `Close` 错误，但复杂函数里容易形成隐式行为。

面试中除了说“可以”，还应说明：命名返值应谨慎使用，裸 `return` 不应让返回内容难以追踪。

## 5. panic 和 recover 应该怎么用？

**答案：**

panic 适合表示程序无法继续的内部不变式破坏，不应代替普通业务错误。recover 只能在同一 goroutine 的 deferred 函数中直接调用，用来捕获正在传播的 panic。

常见恢复边界是 HTTP 中间件、goroutine 任务包装器或框架入口。恢复时需要记录堆栈并返回可控错误；恢复后不能继续使用可能已破坏的共享状态。

## 6. 使用 defer 关闭资源就一定正确吗？

**答案：**

不一定。需要确认 defer 所在函数的生命周期。如果在大循环里反复 defer，文件或连接可能要到整个外层函数结束才释放，应把单次处理抽成小函数。

其次，`Close`、`Flush`、`Commit` 本身可能失败。读文件时关闭错误常可降级处理，但写文件和提交事务时通常不能忽略。
