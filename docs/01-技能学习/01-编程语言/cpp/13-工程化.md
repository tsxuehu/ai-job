# C++：工程化

这篇回答“一个可长期维护的 C++ 后端仓库具体怎么组织”。公共的模块化、契约、迁移和发布原则参见 [企业级后端项目工程结构](../../../03-实战项目/企业级项目工程结构.md)。

## 推荐结构

```text
repository/
├── CMakeLists.txt
├── CMakePresets.json
├── cmake/                         # 工具链、警告、sanitizer、依赖辅助
├── apps/
│   ├── api/main.cpp               # HTTP 进程 composition root
│   └── worker/main.cpp            # 后台任务进程 composition root
├── libs/
│   ├── order_domain/
│   │   ├── CMakeLists.txt
│   │   ├── include/company/order/ # 稳定公共头文件
│   │   ├── src/                   # 实现和私有头文件
│   │   └── tests/
│   ├── order_application/
│   └── platform_observability/
├── adapters/
│   ├── order_http/
│   ├── order_postgres/
│   └── order_messaging/
├── contracts/                     # OpenAPI、Proto、事件 schema
├── migrations/
├── tests/
│   ├── integration/
│   ├── contract/
│   └── performance/
├── deploy/
├── ops/
├── docs/
│   ├── architecture/
│   ├── adr/
│   └── runbooks/
└── tools/
```

不存在真实内容时不要创建空目录。小项目可以先保留 `apps + libs + adapters + tests`。

## CMake target 就是主要工程边界

```text
order_domain
      ▲
      │
order_application ◄── order_postgres
      ▲                    ▲
      │                    │
order_http ─────────── api_app（负责组装）
```

- `order_domain` 只依赖标准库或经过严格选择的基础值类型库。
- `order_application` 定义用例和 Storage、Clock、EventPublisher 等端口。
- adapter 依赖端口并实现接口，核心不能反向链接具体 adapter。
- app target 可以同时依赖所有具体实现，因为它是 composition root。
- 使用工具生成 target 依赖图并在评审中检查反向依赖和环。

## 头文件边界

- 公共头文件放 `include/company/module`，调用方不得包含 `src` 中的文件。
- 公共 API 优先暴露值、抽象接口和不透明句柄，不暴露第三方 SDK 类型。
- `target_include_directories` 正确区分 PUBLIC/PRIVATE。
- 大型实现使用 PImpl 或私有实现减少编译耦合，但先评估分配与 ABI 需求。
- 模板定义通常必须对实例化点可见，放入专门的 detail 区域并控制传播。

## 依赖和 ABI

- 固定编译器、C++ 标准、标准库、运行库、架构和关键编译选项。
- 使用 CMake target 管理依赖，不通过全局 include/link 目录污染所有模块。
- Conan、vcpkg 或团队方案只选一个主路径并锁定版本。
- 跨动态库边界明确 allocator、异常、RTTI、对象所有权和符号可见性。
- 需要长期跨编译器稳定时，优先窄 C ABI 或不透明句柄。

## namespace、头文件、C++ module 和 CMake target

这几个概念不在同一层：

| 概念 | 解决的问题 | 能否约束工程依赖 |
|---|---|---|
| `namespace` | 避免名称冲突 | 不能 |
| 头文件 | 声明调用方可见的 API | 只能约定，不能独立约束链接关系 |
| C++20 module | 控制导出内容、改善编译模型 | 能控制可见性，但不等于业务模块 |
| CMake target | 定义源码、公共 API、编译选项和链接依赖 | 能，是主要工程边界 |

因此，订单模块不是“放进 `namespace order`”就完成了，而是建立独立的
`order_domain` target，只公开必要头文件，并只链接被允许的 target。源码仍会经历
预处理、编译、链接和装载；重复定义还必须遵守 ODR（单一定义规则）。

## 应用入口

`apps/api/main.cpp` 只负责：加载配置、初始化日志/指标、创建连接池和 adapter、构造 application service、注册路由、处理信号与优雅停机。业务判断不进入 main、HTTP handler 或数据库 mapper。

关闭顺序保持：停止接收 → 通知任务取消 → 等待 worker/thread → 刷新观测 → 关闭连接 → 析构基础设施。

## 测试组织

- `libs/*/tests`：值对象、状态机、算法和 application 用例。
- `adapters/*/tests`：数据库、序列化、网络库和错误映射。
- `tests/integration`：多 target 与真实基础设施组合。
- `tests/contract`：OpenAPI、事件和 RPC 兼容。
- `tests/performance`：release 构建下的服务容量和组件 benchmark。
- CI 分别构建严格警告、ASan、UBSan、TSan 和生产 Release 配置。

## 常见错误

- 所有源码和头文件放进一个巨大 target，任何模块都能相互 include。
- 全局编译选项、宏和 include path 让 target 行为不可追踪。
- 公共头文件暴露数据库、HTTP、JSON 库和内部容器。
- 为减少 include 随意使用裸指针，却没有所有权和生命周期契约。
- 单元测试链接整个服务，无法独立验证核心。

## 验收

- [ ] 每个 target 有明确职责、公共头文件和允许依赖。
- [ ] domain/application 不链接具体数据库和网络框架。
- [ ] 新环境可通过 Preset 完成配置、构建和测试。
- [ ] Debug、Release、sanitizer 使用相同 target 图而不是不同工程。
- [ ] ABI、所有权、线程和关闭顺序有文档与测试。
- [ ] 部署产物可追溯到编译器、依赖、选项和 commit。
