# C++：模块化、依赖与 IO

C++ 工程问题往往发生在源文件之外：架构边界、翻译单元、链接、ABI、依赖版本和 IO 都属于语言能力的一部分。

## 模块化不是拆头文件

C++ 的 namespace 解决命名冲突，头文件提供声明，C++ module 改善部分编译模型；它们都不会自动形成良好的业务模块。项目更可靠的模块边界通常是一个 CMake target 或 library：拥有小型公共头文件、隐藏实现，并只依赖允许的下游 target。

```text
task_domain        # 值对象和状态机，无数据库/网络依赖
task_application   # 用例与 Storage 端口
task_postgres      # 端口实现
task_http          # HTTP DTO 与 handler
task_server        # composition root
```

- 核心 target 不包含数据库、HTTP 或第三方 SDK 头文件。
- 依赖接口放在需要它的核心侧；具体实现反向依赖接口。
- public header 只暴露稳定类型；实现细节放 private header、源文件或 PImpl。
- CMake `PRIVATE/PUBLIC/INTERFACE` 传播关系应与架构依赖一致。
- 出现 A/B 循环 include 时，先检查职责、数据所有权和依赖方向，不只增加前置声明。

模块间传递领域值或稳定 DTO，不直接暴露内部容器、数据库结构和第三方类型。跨动态库边界还要考虑 allocator、异常、RTTI、标准库与 ABI；长期稳定边界可以评估窄 C ABI 或 PImpl。

## 代码组织与构建阶段

```text
project/
├── CMakeLists.txt
├── include/project/service.hpp
├── src/service.cpp
├── app/main.cpp
└── tests/service_test.cpp
```

1. 预处理：展开 include 和宏。
2. 编译：每个翻译单元生成目标文件。
3. 链接：解析符号并生成程序或库。
4. 装载：操作系统加载可执行文件和动态库。

头文件声明稳定接口，源文件隐藏实现；遵守 One Definition Rule。C++ 模块可减少部分头文件问题，但采用前要验证编译器、构建系统和依赖生态支持。

## CMake 与依赖

- 以 target 为中心声明源码、编译特性和依赖。
- 用 `PRIVATE`、`PUBLIC`、`INTERFACE` 表达依赖传播。
- 固定语言标准、工具链和关键依赖版本，不写本机绝对路径。
- Conan、vcpkg 或其他方案必须记录锁定、许可证、补丁和产物来源。
- 静态库、动态库和编译选项变化可能影响 ABI。

## IO 边界

- 文件：使用 stream 和 filesystem，检查打开、读取、写入和刷新错误。
- 缓冲：减少小系统调用，但要明确刷新时机和失败传播。
- 二进制：明确长度、版本、字节序和上限，不能把对象内存布局直接当协议。
- 网络：选择成熟库，统一处理超时、取消、半关闭和背压。
- 序列化：考虑未知字段、字段演进、恶意输入和大小限制。

```cpp
std::ifstream input(path, std::ios::binary);
if (!input) throw std::ios_base::failure("open failed");
```

## 易错点

- 把 namespace、目录或 C++ module 当成已经完成架构模块化。
- 所有 target 共享一个 include 根目录，任何模块都能导入内部实现。
- 在头文件引入大量实现依赖，导致编译耦合和循环 include。
- 声明存在但定义缺失，或不同编译选项导致 ABI 不兼容。
- 默认认为一次读写会处理完整消息。
- 对输入不设大小、深度和超时限制。

## 验收

- 能画出 target 依赖图，并说明为何没有反向依赖和循环。
- 核心业务可以不链接数据库、HTTP 和具体框架独立测试。
- 能定位预处理、编译、链接、装载各阶段的问题。
- 新环境能按说明完成配置、构建和测试。
- IO 路径具备错误、上限、超时、取消和资源释放处理。
