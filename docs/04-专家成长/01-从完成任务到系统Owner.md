# 从完成任务到系统 Owner

系统 Owner 不是“代码写得最多的人”，而是能够让系统持续产生业务价值，并对风险、质量和演进负责的人。

## 四个责任层次

### 1. 需求责任

- 明确用户、场景、业务指标和不做什么。
- 识别安全、合规、数据和兼容性约束。
- 在开发前定义验收、灰度和回滚条件。

### 2. 交付责任

- 拆分里程碑和风险，管理跨团队依赖。
- 保证测试、迁移、发布、观测和文档同时完成。
- 对延期和范围变化尽早沟通，不到最后一刻才暴露问题。

### 3. 运行责任

- 定义 SLI/SLO、告警和 Runbook。
- 理解容量、依赖、降级、备份和恢复路径。
- 事故中先止损，再恢复和修复，事后推动防复发。

### 4. 演进责任

- 使用业务与技术数据识别瓶颈和技术债。
- 设计兼容迁移、灰度和可逆变更。
- 定期复核成本、复杂度和依赖是否仍然合理。

## 建议实践

- 每个重要变更写一页设计说明和回滚计划。
- 每周检查一次核心业务与系统指标，而非只看错误告警。
- 每季度选择一个有量化结果的稳定性、性能或成本改进。
- 维护服务地图、数据流、依赖、值班手册和已知风险。
- 对重复故障追查系统性原因，而不是只修复当次异常。

## 反模式

- 只对代码合并负责，不关注上线结果。
- 用组件复杂度代替业务价值。
- 没有指标就宣布优化成功。
- 把事故归因于个人粗心而不改进机制。
- 所有知识和操作都依赖某一个人。

## 自我检查

- [ ] 我能说清系统服务的用户和关键业务指标。
- [ ] 我知道主要依赖、容量上限和故障降级路径。
- [ ] 我能独立组织发布、回滚和事故处理。
- [ ] 我维护的文档足以让其他工程师接手。
- [ ] 最近半年至少有一项改进具备前后对比数据。
