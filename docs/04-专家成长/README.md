# 从后端开发者到技术专家

应届阶段可以训练专家所需的方法，但专家能力来自长期承担真实系统责任。本目录用于入职后的 L3—L4 成长，不建议用个人项目经历冒充生产经验。

## 成长方向

### 从任务执行到系统 Owner

重点从“按需求写代码”转向：

- 理解业务目标、用户影响和成功指标。
- 对需求、设计、上线、观测、故障和成本形成闭环。
- 主动识别风险、技术债和系统性改进机会。
- 在信息不完整时做可逆决策，并及时校准。

参见 [从完成任务到系统 Owner](01-从完成任务到系统Owner.md)。

### 从单点技术到系统架构

重点从“知道更多组件”转向：

- 从业务约束、容量和故障模型出发设计系统。
- 用数据比较一致性、可用性、延迟、复杂度和成本。
- 管理迁移过程、兼容性、灰度、回滚和组织协作。
- 通过 ADR、设计评审和复盘沉淀判断依据。

### 从个人产出到组织影响

重点从“自己完成”转向：

- 建立团队可以复用的规范、平台和工程方法。
- 通过设计评审、指导和反馈提升其他工程师。
- 推动跨团队问题解决，建立清晰的责任和接口。
- 衡量技术工作的业务结果和长期维护成本。

参见 [架构与技术影响力](02-架构与技术影响力.md)。

## L3 的主要证据

- 对一个重要服务持续承担需求、交付、SLO 和故障责任。
- 主导一次有数据对比的性能、稳定性或成本改进。
- 完成一次复杂发布、数据迁移或架构演进。
- 写出能改变后续决策的设计文档或事故复盘。
- 指导新人或推动跨团队依赖按计划交付。

## L4 的主要证据

- 解决多个团队共同面对的架构或工程问题。
- 建立被持续采用的平台、标准、评审或治理体系。
- 能在业务速度、风险、组织能力和长期成本之间做判断。
- 培养出可以独立负责系统的工程师。
- 形成可复用的方法，而不是依赖个人英雄主义。

## 每半年复盘

1. 我承担的是任务、模块、服务，还是跨系统结果？
2. 哪项工作真正改善了业务、稳定性、效率或成本？
3. 哪些决策有数据和文档，哪些只是经验判断？
4. 我的工作离开我以后是否还能稳定运行和演进？
5. 我帮助其他工程师或团队提升了什么？
6. 下一阶段最需要扩大的责任边界是什么？

参见 [职业成长复盘](03-职业成长复盘.md)。
