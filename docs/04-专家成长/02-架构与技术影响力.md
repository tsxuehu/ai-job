# 架构与技术影响力

架构能力不是画出更多方框，而是在约束下做出能安全落地、可持续演进的决策。技术影响力不是职位赋予的权力，而是让正确决策被理解、采用并产生结果的能力。

## 架构决策流程

1. 明确业务目标、范围、容量和成功指标。
2. 列出一致性、可用性、延迟、安全、成本和团队约束。
3. 描述当前系统、主要瓶颈和不改变的后果。
4. 比较至少两个可行方案及其失败模式。
5. 选择最小可行且可逆的演进步骤。
6. 定义指标、灰度、回滚和复核日期。
7. 上线后用真实数据验证假设，并更新 ADR。

## 扩大影响力的方法

- 用问题、约束和证据组织讨论，不用资历压制意见。
- 在设计早期邀请受影响团队参与，而不是完成后通知。
- 把复杂方案拆成可独立验证、可回滚的阶段。
- 公开记录决策、异议、风险和后续验证结果。
- 把一次解决方案沉淀成工具、模板、规范或培训。

## 专家需要持续避免的陷阱

- 为展示技术深度引入业务不需要的复杂度。
- 只设计目标架构，不设计迁移路径。
- 忽略值班、测试、文档和团队维护能力。
- 把局部性能提升建立在整体成本或可靠性恶化之上。
- 只有个人能够理解和维护核心系统。

## 证据清单

- [ ] 决策包含业务目标、约束、方案比较和验证指标。
- [ ] 复杂变更存在灰度、兼容和回滚方案。
- [ ] 至少一个方案被其他团队持续采用。
- [ ] 能展示决策前后的业务或工程数据。
- [ ] 能说明一次判断错误以及如何更新方法。
- [ ] 有被指导者或团队能力提升的具体案例。
